## 1. Контекст проекта

### 1.1 Бизнес-задача

- **Проблема.** Малый и средний бизнес с 3–10 серверами (контроллер домена, сервер 1С с СУБД, терминальный сервер, файловый сервер, гипервизор с бэкапами, MikroTik с VPN) в опте, производстве, сетевой рознице, бухаутсорсе и проектных компаниях. За весь контур отвечает один человек — штатный администратор, совмещающий сотрудник или приходящий инженер.
  1. *Рутина, размазанная по хостам.* Бэкапы, службы, диски, журналы, сеансы и доступы проверяются на каждом сервере своим инструментом через отдельный вход по RDP или SSH. Измеренная доля такой работы (toil) у зрелых SRE-команд — 20–33 % (Google SRE, Catchpoint); для МСБ без автоматизации наша оценка — 50–70 % времени инженера, из которых шаблонами закрывается 30–50 %. Оценка не измерена.
  2. *Знание живёт в голове.* Паспортов серверов нет; при смене инженера преемник изучает контур заново. «Сказано» и «сделано» никто не сверяет: «бэкап каждую ночь на NAS», а последний файл двенадцатидневной давности.
  3. *Цена незамеченного.* Те же сегменты — главные цели вымогателей (по F6, в 2025 году производство, опт и розница — три самых атакуемых отрасли); непроверенный бэкап или оставшийся доступ уволенного превращают атаку в остановку бизнеса.
- **Почему без LLM-системы не справиться.** Исполнение ручек детерминировано и в модели не нуждается. Модель нужна там, где не справляются правила, поиск и готовые продукты: (1) привязать свободный запрос на русском с жаргоном и опечатками («почему тормозит 1С», «склад не видит 1С») к серверу, ручке и её параметрам из каталога в десятки ручек — классификаторы по ключевым словам на таком пространстве ломаются; (2) собрать связный ответ из полуструктурированных данных — сводок по логам и состоянию «сейчас», описаний серверов — и при добавлении сервера сверить описание от человека с фактами осмотра. Мониторинг (Zabbix, PRTG) даёт метрики, а не ответы, и не оставляет документов; скрипты и runbook'и — то самое знание, которое уходит вместе с инженером; RAG не по чему строить — документов нет; облачный чат-ассистент не имеет доступа к хостам, а данные пришлось бы отдавать стороннему провайдеру.
- **Почему именно это решение имеет смысл.** Каталог параметризованных ручек вместо генерации команд: пространство действий конечно, вызов проверяется системой, цена ошибки ограничена сверху возможностями ручки — для небольшой локальной модели это путь к предсказуемому поведению. Self-hosted: продукт, агенты и собранные данные живут в контуре компании, модель — свой инстанс на Ollama внутри контура; сторонних LLM-API нет. Если подходящего железа в контуре нет, компания может сама развернуть тот же инстанс на облачной GPU-машине: выбор провайдера, размещение и ответственность за данные за пределами контура, включая соответствие 152-ФЗ, — целиком на стороне пользователя; продукт этот вариант не предлагает, не настраивает и не обслуживает. Агент каждого сервера держит в промпте полное описание своего сервера и его ручки, оркестратор — краткие описания всех серверов: каждая роль видит только то, что ей нужно. Сначала чтение: для вопросов «сейчас» хватает разовых команд чтения, для истории — логгеров, которые ставятся при добавлении сервера; ценность есть до того, как система получает право что-либо менять. Канал — MSP и 1С-франчайзи, которые уже обслуживают эти компании.
- **Критерии успеха с точки зрения бизнеса** (ориентиры для пилота, не метрики модели):
  1. *Новый сотрудник без бэкграунда* через чат с системой — описания серверов и ответы по их логам — сам проводит базовые операции мониторинга (бэкапы, службы, диски, ошибки, входы) без помощи предшественника.
  2. *Прямые обращения к серверам* (входы по RDP и SSH ради проверок) сокращаются до ≤ 60 % от исходного уровня — измеряет сама система по журналам входов.
  3. *Падения сервисов и простои по тривиальным причинам* (переполнение диска, истёкший сертификат, незамеченный отказ бэкапа) снижаются до ≤ 50 % от исходного уровня — считаем инциденты по журналам до и после внедрения.

### 1.2 Пользователи и сценарии использования

- **Кто.** Ответственный за ИТ компании (штатный инфра-инженер, а если такой позиции нет — совмещающий сотрудник, связанный с ИТ, или приходящий инженер/MSP); один пользователь на установку. Пользователь технически грамотен, но не знает каждую подсистему (1С-специалист не знает RouterOS), поэтому ответ называет период данных и источники, на которые опирается, — понятным языком.
- **Через что.** Свой веб-интерфейс на одном из серверов компании; пользователь открывает его через проброс порта по SSH. Рабочие запросы — чат с оркестратором: он определяет, агенту какого сервера делегировать задачу, и формулирует её агенту. Добавление сервера — форма, затем чат с инспектором и куратором и карточка подтверждения; удаление — в списке серверов; закрытые чаты — в истории, только для чтения. Модель — один инстанс на Ollama на всю систему и все роли, внутри контура (вынос инстанса на арендованную GPU-машину — только по решению и под ответственность пользователя, см. 1.1); запросы к сторонним LLM-API не уходят. Вход — русский, короткие запросы с жаргоном, часто без указания хоста (система уточняет); выход — русский, кратко, связный текст с опорой на полученные числа. SSH-ключи серверов в промпт не попадают никогда.
- **Нагрузка.** Оценки на одну установку для бюджетов 3.2–3.3; проверяет пилот.

| Параметр | Оценка на одну установку |
| --- | --- |
| Пользователей | 1 |
| Рабочих запросов в день | 5–15, до 30 в первые недели; одна сессия — один запрос с уточнениями |
| Добавление сервера | разово на каждый сервер: форма и диалог с инспектором и куратором |

Один запрос пользователя — несколько вызовов модели: оркестратор, агент сервера на каждом шаге цикла ручек, снова оркестратор; в типичном случае 5–7 вызовов, сверху число ограничено лимитами тулз (3.2). Логгеры к модели не обращаются.

- **Цена ошибки.** Контролируется каталогом: система выполняет только ручки из каталога, и все они только читают — логи и разовые команды чтения, поэтому подтверждений перед действиями нет. Единственное подтверждение — краткое описание и название сервера при добавлении; в ходе добавления на хост ставятся логгеры и нужные им библиотеки — единственное изменение на хосте (2.1). Корректность данных в ответе модель может «галлюцинировать», как и везде, поэтому пользователю рекомендуется сверяться с периодом и источниками, названными в ответе, и в чувствительных местах проверять числа самому.
- **Что для пользователя «хорошо».** Проверка — один вопрос в чате против входа на сервер и ручной проверки; время ответа — по бюджету 3.2; вопрос, которому нужны данные нескольких серверов, оркестратор закрывает сам, опрашивая их агентов по очереди; ноль RDP/SSH-сессий ради рутины (измеримо по журналам входов); подтверждений перед действиями нет — агент только читает, единственное подтверждение — при добавлении сервера (2.1); ответ опирается на реальные числа и называет период данных; ничего не сломалось — команды не генерируются; описания серверов сохранены, и преемнику не нужен предшественник: новый инженер узнаёт, какие серверы есть и что на них стоит, из общения с оркестратором, у которого есть описания всех серверов — на архитектурные вопросы («где стоит 1С», «какой сервер за что отвечает», «сколько у нас серверов») он отвечает сам из кратких описаний (2.1), а детали по конкретному серверу (где базы и бэкапы, какие службы, что было за ночь) тот же чат приносит от агента этого сервера по его полному описанию и логам; спрашивать уволившегося и искать его заметки не нужно; совместителю не нужно помнить rac, qwinsta и /export. И главное — система находит «тихие» проблемы: те, что не роняют сервис сегодня, не видны, пока не зайдёшь на сервер и не проверишь руками, и поэтому накапливаются неделями — бэкап, который «делается каждую ночь», а последний файл двухнедельной давности; диск, заполненный больше чем на 80 % и растущий к остановке базы; сертификат, у которого осталось меньше 14 дней. Каждая такая находка — это неслучившийся простой или непотерянные данные, поэтому число найденных «тихих» проблем — самый понятный для бизнеса результат пилота: сколько раз система заметила то, что иначе всплыло бы только аварией.

### 1.3 Границы, ограничения и допущения

**Этапность.** Документ описывает программу-минимум — добавление серверов и сквозные ручки только на чтение; расширения добавляются по мере проекта, каждое — ручки в каталог и сценарии в eval-сет. Модификации инфраструктуры вне скоупа.

| Этап | Что входит | Режим на хостах |
| --- | --- | --- |
| **Программа-минимум** | Добавление сервера через агентов-инспектора и куратора; shell-независимые ручки для Linux и Windows Server: инвентаризация сервера, ресурсы и пики, диски с прогнозом, службы, ошибки журналов и входы, учётки с доступом, бэкапы, сертификаты, планировщик. | Только чтение и диагностика; единственное изменение — установка логгеров и нужных им библиотек при добавлении сервера (запись в журнал, инструкция удаления у каждого тулкита). |
| **Расширение 1** | Windows/1С, чтение: сеансы 1С, блокировки СУБД, сессии RDS, бэкапы СУБД 1С, статус учётки AD, права на папку. | Чтение; одноразовые включения (RAS, log\_lock\_waits, Security log) — предусловия тулкита, ставятся при добавлении сервера. |
| **Расширение 2** | Виртуализация и сеть, чтение: ВМ, снапшоты и бэкапы ВМ; VPN-туннели; бэкап конфигурации MikroTik с diff и аудит пробросов. | Чтение; артефакты пишутся в хранилище инструмента, не на устройство. |
| **Расширение 3** | Дашборды по запросу пользователя с явным описанием метрик, которые в них войдут. | Чтение: данные из логов и опроса локальных агентов. |
| **Расширение 4** | Центральная синхронизация логов логгеров с хостов в хранилище инструмента — чтобы отвечать «что было перед падением», когда сервер недоступен; в программе-минимум логи остаются на хостах и ручка забирает срез по SSH (4.1). | Чтение: периодическое копирование файлов логгеров; ручки работают по копии. |

**Что явно не делаем.**

1. Не генерируем произвольные команды: только каталог ручек; нет ручки — отказ.
2. Не меняем конфигурацию серверов и устройств (GPO, RouterOS, конфигурация 1С, пользователи информационных баз); единственное изменение — установка логгеров (по тегам сервера) и нужных им библиотек при добавлении сервера.
3. Не заменяем мониторинг с алертингом 24/7.
4. Не актуализируем и не правим описания серверов: автоматического изменения данных о сервере и любых модификаций описания нет. Пользователю всегда доступны две опции — добавить сервер и удалить сервер; изменить информацию о сервере можно только удалением и повторным добавлением.
5. Не строим полноценную логгер-LLM систему (централизованный сбор всех логов с LLM-анализом): логгер пишет только то, что нужно ручкам.

**Допущения, которые ещё не проверены.**

- *О данных:* стартовый набор ручек покрывает большинство рутинных запросов, а сторонние логи (1С, nginx и т. п.) достаточно стандартизированы, чтобы ручки считали по ним сводки по запросу пользователя.
- *Об инфраструктуре:* файловая система хостов структурирована и понятна инспектору и агентам: при добавлении сервера инспектор находит, где какие логи; фоллбэк — вопрос пользователю, где лежит путь.
- *О модели:* модель формирует корректные нативные вызовы тулз — имя и аргументы по схеме — без ограничения формата; если нет, ограничение формата (constrained decoding: логиты токенов, не подходящих под JSON-схему, маскируются в −∞, и модель не может их выбрать) включается как усложнение (6.2). Контекста инспектора и куратора хватает на диалог добавления одного сервера: серверы добавляются по одному, вопросы пользователю задают инспектор и куратор, оркестратор в добавлении не участвует.
- *О безопасности и нормативах:* не отвечаем за стороннее облако: если пользователь сам выносит инстанс модели на арендованную GPU-машину, выбор провайдера и соответствие 152-ФЗ — его решение и ответственность; на старте предполагаем машину с инференсом внутри контура, шифрование секретов не подразумеваем.
- *О поведении пользователей:* инженер предпочтёт чат прямому входу на сервер; при подтверждении читает карточку, а не нажимает «да» по привычке; на вопросы инспектора и куратора отвечает честно.

**Вопросы вне предметной области.** Не отвечаем. Репутационный риск — уверенная неверная инструкция на продуктиве: простой и «бот сломал сервер», для продукта, который ставят MSP и франчайзи, — потеря канала.

### 1.4 Термины

- **Оркестратор** — агент, с которым пользователь общается в рабочем запросе: определяет сервер, запускает агента этого сервера, отвечает пользователю.
- **Локальный агент** (агент сервера) — агент одного сервера: запускается оркестратором с новой памятью, в цикле вызывает ручки своего сервера, только читает.
- **Инспектор** и **куратор** — агенты добавления сервера: инспектор осматривает сервер, выбирает теги и составляет полные описания; куратор составляет название и краткие описания, по которым серверы различаются.
- **Тег** — что стоит на сервере (`host`, `1c`, `db`, …); `host` есть у каждого сервера.
- **Тулкит** тега — его логгеры, ручки и предусловия.
- **Логгер** — вход Telegraf на хосте, который пишет свой лог в JSON-файл; к модели не обращается.
- **Ручка** (шаблон) — параметризованная функция из каталога: забирает данные с сервера по SSH и возвращает модели сводку или ошибку. Два типа: *log-inspect* — сводка по уже накопленным логам за период; *one-shot* — сводка на момент «сейчас» по разовой команде чтения.
- **Тулза** — действие, которое модель вызывает нативным вызовом: ручки агента и инспектора, тулзы диалога у оркестратора и куратора.
- **Сессия** — один чат: рабочий запрос с уточнениями или одно добавление сервера.

## 2. Контракт сервиса

Локальный агент только читает — логи через ручки и состояние «сейчас» разовыми командами чтения; любой запрос на изменение — вне скоупа. Серверы добавляются по одному: агент-инспектор заполняет полное описание и теги, агент-куратор составляет краткое описание и название и убирает конфликты между краткими описаниями. Оркестратор сам отвечает на архитектурные вопросы из кратких описаний. Запись о сервере после добавления не меняется — изменить её можно только удалением и повторным добавлением сервера.

### 2.1 Контракт

#### Вход

Текст на русском в чате (добавление сервера — через форму, не чат). Жаргон, транслит, опечатки и запрос без указания хоста допустимы: сервер определяется по краткому описанию, тегам и названию, при неоднозначности система спрашивает. Три класса входа:

1. Добавление сервера: форма с полями conn-ip, conn-user (учётка для SSH), conn-ssh-key, description (описание сервера от человека), не чат; затем чат — ответы на вопросы инспектора по системе, если они у него возникают (инспектор сам, своими ручками по чек-листу, проверяет и обогащает описание, выбирает теги и собирает полную информацию по тегам; ручного изменения тегов и полных описаний в системе нет, пользователь их не подтверждает), и куратора — в чём различие с похожим уже добавленным сервером; в конце — подтверждение или отказ только по краткому описанию и названию, которые составил куратор (отказ продолжается как диалог с куратором). Удаление сервера — кнопка в списке серверов с обычным системным окном подтверждения; описание сервера после добавления не меняется, обновить его можно только удалением и повторным добавлением.
2. Вопросы о состоянии и истории — «кто сидит в базе», «когда пики», «что упало за ночь», «бэкапы точно есть»: закрываются чтением логов, которые тулкиты тегов поставили на машину, через ручки — запросы, которыми агент читает информацию из логов; вопросы об архитектуре — «где стоит 1С», «какой сервер за что отвечает» — оркестратор закрывает сам, из кратких описаний серверов. Если запрос неоднозначен (не назван хост, не хватает параметров), система задаёт уточняющий вопрос, и ответ пользователя на него — продолжение того же запроса.
3. Запросы о состоянии «прямо сейчас», которого нет в логах или которое дороже хранить: разовые команды чтения из каталога (bash, PowerShell — загрузка в этот момент, размер произвольного пути, внеплановая инвентаризация), выполняются сразу, без подтверждения.

Граница текущей версии: локальный агент только читает — логи через ручки и состояние «сейчас» разовыми командами чтения (bash, PowerShell); единственное изменение на хосте — установка логгеров, нужных им библиотек и предусловий при добавлении сервера. Остальное — отказ с перечнем того, что умеет система для этого сервера: произвольные команды и скрипты, любые изменения на сервере (перезапуск службы, завершение сеанса, разблокировка учётки, офбординг, обновление платформы 1С, удаление снапшотов) — вне скоупа, инструкций и команд система не даёт; общие вопросы по администрированию и запросы секретов — тоже отказ.

*Как проверим (5.2):* доли правильных отказов и уточнений по классам; ложные срабатывания учитываются внутри этих долей.

#### Выход

Все ответы — на русском, связный человекочитаемый текст с числами из собранных данных; ответ говорит, за какой период данные и на какие источники опирается — понятным человеку языком, прямо в тексте («логи сессий», «разовая проверка затрат ресурсов»), а не внутренними именами ручек, команд и шаблонов. Это задаётся промптом локального агента («укажи источники — не ручки, — которыми ты пользовался при формировании ответа») и оркестратора («укажи источники — не ручки, — которыми пользовался локальный агент при формировании ответа»); отдельного механизма нет. Отсутствие данных говорится явно, без экстраполяции.

1. При добавлении сервера — краткое описание и название, составленные куратором, которые пользователь подтверждает или отклоняет (отказ продолжается как диалог с куратором); теги и полное описание в подтверждение не входят; по ходу добавления — вопросы инспектора и куратора; в конце — сообщение, что сервер добавлен.
2. Ответ по данным логов — сразу; подтверждения действий агента (выбор ручки чтения логов, разовая команда чтения) не запрашиваются.
3. Ответ разовой командой чтения — те же правила: называется момент, к которому относятся данные.
4. Подтверждение — только при добавлении сервера и только для краткого описания и названия, составленных куратором: пользователь подтверждает их или пишет замечания. Установка логгеров и нужных им библиотек — единственное изменение на хосте — происходит в ходе добавления.
5. Любой запрос на изменение — вне скоупа: отказ с указанием, что система только читает; инструкций и команд для изменений система не даёт.
6. Ответ оркестратора на архитектурные вопросы из его контекста — ip, теги, краткие описания серверов («где стоит 1С», «какой сервер за что отвечает», «сколько у нас серверов») — без обращения к агентам.
7. Отказы: компонент не поддерживается; нет ручки под запрос; изменение — вне скоупа; вопрос вне предметной области; запрос секрета.

*Как проверим (5.2):* доли правильно выбранных агентов, ручек и их аргументов (rule-based); LLM-judge постановки задачи агенту, ответа агента по результатам ручек и ответа пользователю; e2e — доведение сценария до ожидаемого состояния стенда.

#### Поведение при неуверенности

- Уточняющий вопрос с вариантами: хост не назван, а теги и краткие описания подходят нескольким серверам; не хватает параметров ручки; при добавлении сервера — инспектору не хватает данных о системе (пути, учётки, подтверждение тега) или куратор не может по краткому описанию отличить сервер от уже добавленных.
- Отказ с объяснением: компонент не поддерживается; нет данных за запрошенное окно.
- Сервер недоступен: 2 попытки подключения с паузой 5 с, затем сообщение оркестратора по эскалации агента: сервер недоступен, возможные причины.
- Лимиты реплик: в рабочем запросе оркестратор задаёт не больше 7 вопросов и даёт не больше 3 ответов или отказов на сессию; когда ответ или отказ исчерпывает лимит, чат закрывается с техническим сообщением. При добавлении сервера: инспектор — не больше 10 вопросов, куратор — не больше 5, карточка подтверждения — не больше 3 раз.
- Ход прогона и остановка: пока система работает, в чате видны статусные сообщения понятным языком («определяю сервер», «опрашиваю srv-1c…», «формирую ответ»), в историю они не попадают; кнопка «Остановить» прерывает прогон и закрывает чат. Чат закрывается техническим сообщением и при внутренней ошибке; продолжить — в новом чате.

Числа лимитов и попыток предварительные и уточняются по baseline.

*Как проверим (5.2):* доли правильных уточнений по ситуациям (не понятен сервер, агент эскалировал, сервер недоступен) и правильных отказов по классам; LLM-judge формулировки вопросов.

#### Чего не обещаем

- Изменений на серверах — локальный агент только читает, единственное изменение — установка логгеров и предусловий при добавлении сервера; действий вне каталога, произвольных команд, инструкций и команд для изменений.
- Автоматического обновления тегов и описания: описание меняется только явным удалением и повторным добавлением сервера пользователем.
- Данных до добавления сервера в инструмент: логирование начинается с установки логгеров при добавлении.
- Данных за пределами ретенции лога: у каждого лога своя ретенция.
- Мониторинга 24/7, алертинга и любых действий по расписанию: всё — только по запросу пользователя.
- Безошибочности выводов: факты и период показаны, вывод проверяет инженер.

*Как проверим:* границы в 1.3.

#### Нефункциональные

- Данные и инференс — внутри контура компании; сторонних LLM-API нет; вынос инстанса модели на арендованную GPU-машину — только по решению и под ответственность пользователя (1.1). Подключение к серверам — только по SSH; SSH-ключ в промпт не попадает.
- Логгеры только пишут логи и ничего не меняют на хосте. Единственные изменения на хосте — установка логгеров, нужных им библиотек и предусловий при добавлении сервера, с записью в журнал; у каждого тулкита есть инструкция удаления.
- Описание сервера и его логи хранятся до удаления сервера из инструмента (в пределах ретенции логов); удаление сервера останавливает логгеры и убирает и описание, и логи. Ручки выхлопов на сервере не оставляют.
- Задержка и доступность — по бюджетам раздела 3.

*Как проверим:* бюджеты 3.2 и SLO 3.5; размер журнала и нагрузка логгеров на хосты — на стенде.

**Контракт одной фразой:**

> Сервер добавляется через форму (conn-ip, conn-user, conn-ssh-key, описание от человека), дальше в чате: агент-инспектор проверяет и обогащает описание, выбирает теги и ставит логгеры, агент-куратор составляет краткое описание и название, отличающие сервер от уже добавленных, вопросы пользователю задают оба; пользователь подтверждает краткое описание и название или пишет куратору замечания по ним — править можно только на этом шаге, а правка описания уже сохранённого сервера — только удалением и повторным добавлением; дальше запрос на русском оркестратор относит к серверу по краткому описанию, тегам и названию и запускает агента этого сервера — при необходимости ещё раз или агента другого сервера, — а агент только читает: сводки по накопленным логам и состояние «сейчас» через ручки каталога, и любой запрос на изменение — вне скоупа; оркестратор возвращает человекочитаемый ответ с числами, периодом и понятно названными источниками данных, на архитектурные вопросы отвечает сам из кратких описаний, при неуверенности задаёт уточняющий вопрос; вне каталога и тегов сервера система не действует.

### 2.2 Сценарии взаимодействия

**Основные сценарии.** Путь любого рабочего запроса: пользователь → оркестратор по краткому описанию, тегам и названию определяет сервер и формирует запрос его агенту → локальный агент (запускается как тулза оркестратора, с новой памятью на каждый запуск) в цикле выбирает ручки — сводки по накопленным логам или one-shot на момент «сейчас», — читает их результаты и заканчивает ответом или эскалацией → оркестратор либо отвечает пользователю (вопрос, отказ, уточнение, ответ — понятным языком), либо запускает агента ещё раз: того же с новым запросом или другого сервера, если первый выбран неверно; после ответа пользователя на вопрос оркестратор продолжает с историей сессии (вызовы агентов и диалог). Агентов нескольких серверов оркестратор опрашивает последовательно. Подтверждение запрашивается только при добавлении сервера (краткое описание и название); действия агента подтверждений не требуют. Архитектурные вопросы оркестратор закрывает сам, без агента. Добавление сервера идёт отдельным путём: форма (conn-ip, conn-user, conn-ssh-key, description) → чат с вопросами инспектора и куратора → подтверждение краткого описания и названия → запись о сервере.

| Сценарий | Пример запроса | Что делает система | Результат для пользователя |
| --- | --- | --- | --- |
| Добавление сервера | Кнопка «Добавить сервер» → форма: адрес, учётка, SSH-ключ, описание («сервер 1С с MS SQL»); для каждого сервера отдельно | Пользователь заполняет форму, открывается чат добавления → инспектор своими ручками по чек-листу (структура 1C, железо, домены сайта, nginx-логи и т. п.) проверяет и обогащает описание, выбирает теги (host — всегда), ставит логгеры и заполняет полное описание сервера и полную информацию по каждому тегу; вопросы по системе, если возникают, задаёт пользователю напрямую → куратор составляет название (< 5 слов), краткое описание (< 50 слов) и краткие описания по каждому тегу (≤ 30 слов); если сервер похож на уже добавленный — спрашивает, в чём различие; просьбы сменить теги или править что-либо вне краткого описания и названия — явный отказ (`deny`): чат закрывается, сервер не добавляется → пользователь подтверждает краткое описание и название или пишет замечания — диалог с куратором до подтверждения | Сервер сохранён с подтверждёнными пользователем кратким описанием и названием (теги и полное описание заполнил инспектор, пользователь их не подтверждает); с этого момента по серверу можно задавать вопросы. Сервер, удалённый и добавленный заново, идёт как новый |

### 2.3 Диалоговая логика и тон

- **Multi-turn.** Добавление сервера — форма, затем диалог с инспектором и куратором в чате; любой запрос может потребовать уточнения; подтверждение — только при добавлении сервера (краткое описание и название от куратора); действия сбора данных локального агента и инспектора не подтверждаются.
- **История сессии.** Одна сессия — один запрос пользователя или одно добавление сервера; активна одна сессия — новый чат открывается с подтверждением, прошлый уходит в историю чатов, доступную только для чтения. История сессии живёт в состоянии графа агентов и целиком попадает в промпт на время сессии: в рабочем запросе это вызовы локальных агентов с их ответами, диалог с пользователем, где реплики различаются метками, которых пользователь не видит, и рассуждения (thinking) прошлых шагов оркестратора. Локальный агент между запусками ничего не помнит. После закрытия чат уходит в историю чатов, все шаги остаются в журнале, записи о серверах не меняются.
- **Долгая память.** Запись о сервере — семь полей: server-name (< 5 слов); conn-info (ip, user, ssh\_key); short-desc (общие слова о сервере, его семантика; < 50 слов; составляет куратор); full-desc (полное семантическое описание; инспектор); tags (множество тегов; инспектор); tags-short-desc (ситуативное описание по каждому включённому тегу — пользователи 1C, таблицы; для host — утилиты в процессах, ресурсы, железо; ≤ 30 слов на тег, непустое; куратор); tags-full-desc (полная информация по тегам; инспектор). У оркестратора — server-name, ip и учётка из conn-info, tags и short-desc каждого сервера; сервер запроса он определяет по краткому описанию, тегам и названию. full-desc и tags-full-desc — только у агента своего сервера. SSH-ключ в промпт не попадает никогда.
- **Тон.** Формальный, на «вы», кратко, без эмодзи. Ответ по данным называет период и источники понятным языком, но не внутренние механизмы — имена ручек, команд, шаблонов; «нет данных» — отдельной фразой, не нулём; в справочных пояснениях нет команд.
- **Прозрачность.** В интерфейсе заявлено, что пользователь работает с LLM-системой и что запросы и действия пишутся в журнал.

## 3. Три бюджета и SLO

Расчётная база — GPU с 48 ГБ VRAM (на стенде — арендованная A6000 ≈ 0,35 $/ч, на ней только данные стенда), batch = 1 (одна активная сессия), модели-кандидаты 4.4 — Qwen3.8-27B (плотная) и Qwen3.6-35B-A3B (MoE, 3B активных) в Q8 с thinking уровня low. Скорости ниже пересчитаны от референса Qwen 70B Q4 на той же A6000 (префилл ≈ 300 ток/с, декодирование ≈ 15 ток/с) по числу активных параметров и объёму весов; это оценка до замера, все числа раздела уточняются по baseline (6.1). Железо у покупателя — его зона ответственности; требование — GPU с 48 ГБ VRAM: модель в Q8 с окном 64k занимает 34–40 ГБ.

### 3.1 Качество

| Метрика (из контракта) | Как считаем | Целевое значение | Ниже чего — откат |
| --- | --- | --- | --- |
| Доля правильно выбранных агентов (Выход) | rule-based по эталонному серверу теста (5.2) | ≥ 95 % | < 90 % |
| Доля правильно выбранных ручек (Выход 2–3) | rule-based по эталонной ручке теста | ≥ 90 % | < 85 % |
| Валидность формата: доли правильно сформированных вызовов тулз и правильных типов по схеме | парсинг и валидация по схеме на каждом вызове модели | ≥ 99 % | < 97 % |
| Доля правильной разметки серверов тегами (инспектор, Выход 1) | rule-based: множество тегов совпадает с эталоном | ≥ 90 % | < 80 % |
| Доли правильных отказов и уточнений — по каждому классу: `not_in_scope`, `clarify` (по ситуациям), `no_template`, `wrong_addressee`, `conflict`, `clarify` инспектора | rule-based по классу ответа; ложное срабатывание класса — тест не засчитан | ≥ 90 % по каждому классу | < 80 % |
| Доля правильных ответов агента по результатам ручек (числа совпадают) | LLM-judge по возврату ручки и эталонным числам | ≥ 95 % | < 90 % |
| e2e: доля сценариев, доведённых до ожидаемого состояния стенда | rule-based по журналу и judge итоговой реплики (5.2) | ≥ 90 % | < 80 % |

Остальные доли 5.2 — постановка задачи агенту, ответы по архитектурным вопросам и по ответу агента, формулировка вопросов и ошибок (LLM-judge), аргументы ручек, заполнение полей сервера инспектором — отслеживаются по правилу отката 5.3: падение любой доли относительно предыдущего цикла eval откатывает модификацию. Метрики, которые eval-набор предлагает сверх них (чек-лист и отказ инспектора, явный отказ, лимиты и качество кратких полей куратора, читаемость, тексты отказов), до утверждения считаются отдельно и откат не запускают.

### 3.2 Задержка

Считаем два пути рабочего запроса. *Минимальный* — один запуск агента с одной ручкой: четыре вызова модели (оркестратор → агент: выбор ручки → агент: ответ по результату → оркестратор: ответ пользователю). *Типичный* — 5–7 вызовов: агенту нужно две-три ручки или оркестратор запускает агента повторно. Сверху число вызовов ограничено лимитами тулз: оркестратор — `delegate` ≤ 15, `ask-user` ≤ 7, `answer-user` + `reject` ≤ 3 на сессию; локальный агент — ≤ 20 ручек на запуск; инспектор — ≤ 40 ручек и ≤ 10 вопросов; куратор — ≤ 5 вопросов и ≤ 3 карточки. Лимиты — предел, а не бюджет.

**Размер промптов** (≈ 25 токенов на строку русского markdown; уточняется токенизатором модели):

| Вызов модели | tokens\_in | tokens\_out |
| --- | --- | --- |
| 1. Оркестратор: выбор сервера и задача агенту | инструкции и схемы тулз ≈ 1k + записи о серверах ≈ 2k (N = 10) + история ≤ 0,5k + запрос 0,1k ≈ 3,6k | вызов ≈ 0,15k + thinking |
| 2. Агент: выбор ручки | инструкции ≈ 0,8k + полное описание и информация по тегам 2–4k + каталог ручек 3–15k + задача 0,15k ≈ 6–20k | вызов ≈ 0,1k + thinking |
| 3. Агент: ответ по результату ручки | вызов 2 + результат ручки 0,5–2k (префикс вызова 2 переиспользуется) | ответ ≈ 0,3k + thinking |
| 4. Оркестратор: ответ пользователю | вызов 1 + thinking и вызов + ответ агента ≈ 4–5k | ответ ≈ 0,3k + thinking |
| **Итого на минимальный путь** | ≈ 14–31k новых токенов префилла | ≈ 0,85k + 4 × thinking |

Thinking уровня low — принимаем 0,2–0,5k токенов на вызов до замера. Контекст одного вызова на минимальном пути — до ≈ 22k; худший случай агента (20 ручек и сохранённый thinking) — 45–60k, поэтому окно — 64k (4.4).

**Скорости на A6000** (оценка до замера):

| Модель | Префилл | Декодирование | Откуда |
| --- | --- | --- | --- |
| Qwen 70B Q4 (референс) | ≈ 300 ток/с | ≈ 15 ток/с | расчёт v0.1 |
| Qwen3.8-27B Q8 | ≈ 800 ток/с | ≈ 20 ток/с | префилл — пропорционально активным параметрам; декодирование ограничено чтением ≈ 30 ГБ весов на токен при 768 ГБ/с |
| Qwen3.6-35B-A3B Q8 | ≈ 2 000 ток/с | 80–100 ток/с | на токен читаются и считаются ≈ 3B активных параметров; MoE в llama.cpp использует железо хуже плотной |

**Этапы минимального пути:**

| Этап | Qwen3.8-27B | Qwen3.6-35B-A3B | Откуда число |
| --- | --- | --- | --- |
| сеть | ≤ 50 мс | ≤ 50 мс | клиент, бэкенд и движок внутри контура; приложение слушает только 127.0.0.1, доступ пробросом порта по SSH (4.1); на стенде к этому добавляется SSH-туннель к удалённому движку |

Типичный путь добавляет на каждый лишний шаг агента префилл 0,6–2,1k токенов и декодирование 0,3–0,6k: ≈ 20–35 с на плотной модели и ≈ 5–8 с на MoE.

**Целевое значение:** e2e P95 ≤ 120 с на минимальном пути. По оценке MoE укладывается с запасом и на типичном пути; плотная 27B с thinking бюджет превышает — это и есть развилка 3.4, которую решает замер на baseline. Задержка каждого вызова и сессии пишется в журнал, P50 / P95 считаются по нему.

### 3.3 Стоимость

Self-host: цены за токен нет, расход — GPU-время. Для разработки и eval — почасовая аренда A6000 ≈ 0,35 $/ч; у покупателя железо своё.

```
cost_per_request ≈ GPU-время запроса × цена GPU-часа
cost_per_month   = cost_per_request × requests_per_month
```

| Параметр | Значение | Откуда |
| --- | --- | --- |
| tokens\_in на запрос (минимальный путь) | ≈ 14–31k новых токенов префилла; основная часть — описания серверов и каталог ручек | таблица промптов 3.2 |
| tokens\_out на запрос | ≈ 1,65–2,85k с thinking | там же |
| вызовов модели на запрос | 4 на минимальном пути, 5–7 в типичном; сверху — лимиты тулз | 3.2 |
| GPU-время на запрос | ≈ 2–3 мин на плотной 27B, ≈ 0,5–1 мин на MoE — движок занят почти всё время запроса | 3.2 |
| **cost\_per\_request** | на стенде ≈ 0,012–0,018 $ (27B) и ≈ 0,003–0,006 $ (MoE); у покупателя — своё железо, денежной цены запроса нет | 0,35 $/ч × GPU-время |
| requests\_per\_month | ≈ 330 (15 в день × 22 рабочих дня; первые недели до 660) | 1.2 |
| **cost\_per\_month** | тестовый инстанс ≈ 20–35 $ при 60–100 ч аренды под eval и разработку (циклы eval — 5.3); у покупателя GPU-часы на рабочие запросы — ≈ 11–17 ч в месяц (27B) или ≈ 3–6 ч (MoE) | 0,35 $/ч × часы аренды |

Скрытая стоимость: время на разметку eval-сета и стенд; GPU-часы на eval — цикл из ~5 проходов набора из 150 тестов (750 прогонов тестов, ≈ 3–4,5 тыс. вызовов модели, 5.3): ≈ 25–60 GPU-ч на плотной 27B и ≈ 8–20 GPU-ч на MoE; baseline — два цикла, по одному на кандидата. Плюс вызовы Claude API для judge — ≈ 1 тыс. на цикл.

Память под веса: Qwen3.8-27B в Q8 ≈ 30 ГБ, с окном 64k ≈ 34–36 ГБ; Qwen3.6-35B-A3B в Q8 ≈ 39 ГБ — обе помещаются в 48 ГБ; если MoE в Q8 с окном не поместится, — Q6\_K.

### 3.4 Компромисс

Качество против скорости. Плотная Qwen3.8-27B обычно точнее, MoE Qwen3.6-35B-A3B декодирует в 4–5 раз быстрее; thinking улучшает решения в цикле тулз, но умножает число генерируемых токенов. По оценке 3.2 плотная модель с thinking не укладывается в 120 с на запрос, MoE — укладывается. Выбор — по baseline (6.1) на двух моделях: метрики 5.2, валидность вызовов тулз и задержка; итог фиксируется в ADR (4.6).

### 3.5 SLI и SLO

| SLI | Как считаем | SLO | Error budget |
| --- | --- | --- | --- |
| доля валидных по формату вызовов тулз | парсинг нативного вызова и валидация аргументов по схеме тулзы, SQL по журналу | ≥ 99 % | 1 % |
| прогон до конца без падений | доля сессий, закрытых без системной ошибки (движок недоступен после повтора, исключение в ручке или узле, переполнение окна, три невалидных вызова тулз подряд — всё, что закрывает чат «Внутренняя ошибка», 4.2); недоступный сервер, закрытие по лимиту и по «Остановить» — не падение | ≥ 97 % | 3 % |
| отзывы | число 👎 на ответах за неделю | ≤ 3 в неделю (≈ 5 % от ≈ 75 запросов) | 3 в неделю |

**Сбор фидбека.** 👍/👎 и необязательный комментарий на каждом ответе в веб-интерфейсе; пишется в журнал, просматривается по нему.

## 4. Архитектура решения

### 4.1 Схема по семи блокам

Картина целиком: один бэкенд-процесс на одном из серверов компании (FastAPI + LangGraph + SQLite) держит всех четырёх агентов, промпты и записи о серверах; свой веб-клиент (React) доступен через проброс порта по SSH, без входа по паролю; на обслуживаемых хостах — только логгеры Telegraf, ручки забирают срез логов по SSH; инференс — Ollama (на стенде разработки удалённый, через SSH-туннель к его порту); наблюдаемость у клиента — журнал в БД и история чатов, на стенде — трейсы в Phoenix.

```
[клиент: React] ──SSH port-forward──▶ [бэкенд: FastAPI (REST + SSE)]
                                          │
                              [рантайм: LangGraph — оркестратор, агент, инспектор, куратор]
                                 │              │                 │
                       [инференс: Ollama]  [SQLite: серверы, журнал]  [реестр ручек: Python-функции]
                                                                           │ SSH
                                                               [хосты: Telegraf → JSON-файлы]
              ── наблюдаемость: журнал (SLI по SQL); на стенде OpenTelemetry → Phoenix ──
```

| Блок | Что делает в нашей системе | Берём готовое | Пишем сами и почему |
| --- | --- | --- | --- |
| Клиент | Веб-интерфейс одного пользователя: чат рабочего запроса; форма «Добавить сервер» (conn-ip, conn-user, conn-ssh-key, description); чат добавления; карточка подтверждения (краткое описание, название, краткие описания по тегам); список серверов с удалением через системное окно; история чатов только для чтения; окно подтверждения при открытии нового чата — активна одна сессия. Реплики приходят целиком: стриминга текста и рассуждений модели нет. | React + TypeScript + Vite; типы клиента генерируются из OpenAPI бэкенда. Макеты окон — в Claude Design на минимальной дизайн-системе (палитра, шрифты, отступы, компоненты), затем переписываются под стек; до адаптации источник правды по виду — холст, после — код. | Весь фронтенд свой: готовые чат-оболочки (Chainlit и подобные) не дают форму, карточку, список серверов и историю чатов в нужном виде, а макеты из Claude Design всё равно переписываются в код. |
| Шлюз и API приложения | LLM-шлюза нет: один движок, одна модель, один пользователь. API приложения: REST для действий, SSE для событий (ход выполнения, готовая реплика, закрытие чата); бэкенд же раздаёт собранный фронтенд. Аутентификации нет — пользователь один, сети доверяем: приложение слушает только 127.0.0.1 на сервере компании, пользователь подключается пробросом порта по SSH. Лимиты вызовов тулз (3.2), повторы и учёт токенов — внутри приложения. | FastAPI (uvicorn), SSE-поток событий; LiteLLM — как библиотека внутри приложения: подсчёт токенов, интеграции логирования, единая обёртка для judge. Обратного прокси и TLS нет. | Эндпоинты и схема событий; проверка лимитов — в узле исполнения тулз рантайма: это логика продукта (отказ сверх лимита с комментарием модели), у готовых шлюзов её нет. |
| Оркестратор (агентный рантайм) | Четыре агента — оркестратор, локальный агент, инспектор, куратор — в одном бэкенде; там же промпты и записи о серверах, на хостах только логгеры. Сборка промптов, нативный вызов тулз, циклы с лимитами, вопросы пользователю с ожиданием ответа; история сессии — состояние графа. | LangGraph: interrupt() для вопросов пользователю и карточки подтверждения (thread = сессия), подграф локального агента с новым состоянием на каждый запуск, события графа → SSE, checkpointer в памяти; клиент модели — класс LangChain, который возвращает thinking в историю сообщений. | Узел исполнения тулз с лимитами и отказом «сверх лимита» вместо готового ToolNode; терминальные тулзы — рёбра в конец графа. Guardrails только по построению: каталог ручек вместо команд, лимиты, ошибки-enum с комментарием и примером; маскирования и защиты от инъекций нет (риск 7.2). Лимиты живут в рантайме: восстановления после падения процесса и кэширования результатов не предусмотрено. |
| Движок инференса | Self-host: одна локальная модель на все роли (кандидаты — 4.4), один инстанс, нативный tool calling движка. У клиента — в контуре или на его облачной GPU-машине (его решение, 1.2). На стенде разработки инференс удалённый: GPU-машина с Ollama, доступ по SSH-ключу — SSH-туннель к порту Ollama, который слушает только localhost. | Ollama — выбор окончательный (vLLM, SGLang, llama.cpp напрямую не рассматриваются). Ограничение формата (constrained decoding, JSON по схеме) заранее не пишем — это риск 7.2 и усложнение 6.2, включается только если baseline покажет проблему с валидностью вызовов тулз. |
| Хранилища | Записи о серверах (семь полей, 2.3); журнал — сессии, реплики, вызовы тулз и модели, расход токенов, хэши версий промпта и модели — он же источник истории чатов и SLI; состояние сессии — в памяти рантайма. Логи логгеров остаются на хостах: ручка забирает срез файлов за период по SSH и сводит у себя. Индекса, RAG и кэша нет — контекст целиком в промпте. Промпты, каталог ручек, манифесты тулкитов, чек-листы инспектора, Modelfile — файлы в git. ### 4.2 Путь одного запроса

Путь рабочего запроса по блокам 4.1; архитектурный вопрос — тот же путь без шагов 4–5; добавление сервера — тот же каркас с узлами инспектора и куратора вместо оркестратора и агента.

1. **Клиент → API.** Пользователь пишет в активный чат; клиент отправляет реплику REST-запросом и держит SSE-поток событий сессии. Бэкенд пишет реплику в журнал и запускает (или возобновляет после interrupt) граф сессии — thread LangGraph = сессия; граф работает в фоновой задаче, не привязанной к SSE-соединению.
2. **Узел оркестратора.** Промпт = инструкции + записи о серверах (server-name, ip, user, tags, short-desc) + история сессии (вызовы агентов с ответами, диалог с пользователем, thinking прошлых шагов) + лимиты тулз. Перед вызовом система считает токены промпта; вызов модели через Ollama, нативный tool calling → ровно один вызов тулзы. Свободный текст модели допустим только в thinking (отдельное поле ответа Ollama); текст вместо вызова, неизвестная тулза или аргументы не по схеме — невалидный вызов (правила ниже).
3. **Узел тулз оркестратора.** Проверка лимита (3.2) → delegate(server-name, prompt) → шаг 4; ask-user → interrupt(), событие «вопрос», граф ждёт ответа; answer-user / reject → реплика пользователю, журнал, событие «готово»; третий ответ или отказ → закрытие чата. Вызов сверх лимита — отказ с комментарием модели, возврат к шагу 2.
4. **Подграф агента** (новое состояние на каждый запуск). Промпт = инструкции + full-desc и tags-full-desc своего сервера + схемы ручек по тегам сервера + prompt оркестратора. Цикл: вызов модели → тулза → узел ручек (лимит 20): ручка подключается по SSH (conn-info), забирает срез логов Telegraf или запускает команду, строит сводку, возвращает результат + предупреждение или ошибку-enum с комментарием и примером → обратно в модель вместе с thinking прошлых шагов запуска. Терминальная тулза (ответ / эскалация) завершает подграф; её текст — результат delegate.
5. **Оркестратор снова** — шаг 2 с обновлённой историей: ответить, спросить, отказать или запустить агента ещё раз (тот же с новым prompt или другой сервер); при повторном запуске агент получает только prompt.
6. **Ответ.** Реплика целиком уходит событием SSE; в журнал — вызовы модели и тулз с токенами, хэшами промпта и модели; клиент показывает 👍/👎.

**Правила пути.**

- *Индикация.* Пока идёт прогон, клиент получает по SSE крупные статусные события понятным языком — «определяю сервер», «опрашиваю srv-1c…», «формирую ответ» — без имён ручек и меток; тексты задаёт код, не модель; в историю чатов не пишутся.
- *Таймауты и повторы* (страховка инфраструктуры, не лимиты модели): вызов модели — 120 с и один повтор при сетевой ошибке; ручка — 30 с по умолчанию, переопределяется в ручке; SSH — 2 попытки с паузой 5 с, затем ошибка ssh-refused модели; общего таймаута на запрос нет — сверху цикл ограничен лимитами 3.2. Числа предварительные.
- *Исчерпание лимитов.* Вызов сверх лимита отклоняется с комментарием, модели остаются разрешённые тулзы; 10 отклонённых вызовов подряд — система закрывает цикл агентов и сессию техническим сообщением. Куратор: третья карточка — последняя, не подтверждена или deny → сервер не добавляется, чат закрывается.
- *Невалидный вызов тулзы.* Системное сообщение модели в формате ошибки аргумента: только первая проблема (не перечень) и повтор схемы вызова; засчитывается в лимит тулзы; 3 подряд — системная ошибка. Для сравнения: LangGraph ToolNode и pydantic-ai отдают модели все ошибки валидации — здесь осознанное упрощение.
- *Переполнение окна.* Если промпт не помещается в окно 64k, запрос к модели не отправляется — системная ошибка; молчаливой обрезки промпта нет.
- *Остановка.* Кнопка «Остановить» отменяет asyncio-задачу графа (штатный способ для open-source LangGraph; встроенной отмены нет); чат закрывается и уходит в историю.
- *Системная ошибка* (движок недоступен после повтора, исключение в ручке или узле, переполнение окна): «Внутренняя ошибка, попробуйте снова», чат закрывается и архивируется с пометкой; в журнал — исключение и шаг; для SLI 3.5 это падение, недоступный сервер — нет.

### 4.3 Данные и база знаний

Базы знаний в смысле RAG нет: retrieval не делаем, контекст целиком в промпте. Знания системы — два фактора, и раздел построен по этому делению:

1. **Логи и ручки, которые их читают** — что происходит и происходило на сервере: логи логгеров на хостах, ручки просмотра логов (история) и one-shot (момент «сейчас»).
2. **Информация о серверах** — записи из семи полей (2.3): что это за серверы и чем они различаются.

Отдельно — служебные данные: журнал и история чатов; это запись того, что делала система, знаниями для ответов они не служат.

**Чувствительность.** В логах, ответах ручек, промптах и журнале есть персональные и коммерческие данные: учётки и имена пользователей (входы, сеансы 1С, Security log), IP и имена хостов, имена баз и процессов, тексты описаний серверов. Внешним провайдерам они не отправляются — инференс локальный; единственное исключение — judge через Claude API, и только на данных стенда (5.2). Маскирования нет (риск 7.2). Логи остаются на хостах со своей ретенцией; журнал с полными входами и выходами модели и ручек хранится на сервере инструмента бессрочно — механизма ретенции нет.

**Источники.**

| --- | --- | --- | --- | --- | --- |
| 1. **Предобработка.** Корпуса для нарезки нет. *Логи и ручки:* логи хранятся в формате Telegraf без преобразований — name (источник), fields (данные), timestamp (время); вид источника (kind), идентификатор источника (src) и версия тулкита (v) — статические теги входа; логическая модель записи (ts, host, src, kind, v, data) физически не воспроизводится. Срез и сводку делает ручка: по SSH забирает файлы лога, покрывающие период, целиком и фильтрует по времени в Python; на хосте кроме Telegraf ничего не нужно, предагрегации нет; дифф снапшотов ручка считает сама. *Информация о серверах:* предобработки нет — поля записи сразу пишутся в нужной форме: полные поля составляет инспектор, краткие — куратор с лимитами слов (2.3).

**Индексация.** Retrieval нет. *Логи и ручки:* каталог ручек передаётся агенту целиком — все ручки по тегам сервера схемами тулз в каждом вызове модели; фоллбэк, если каталог не помещается в контекст или выбор деградирует, — двухступенчатая подача (сначала имена с однострочными описаниями, затем схема выбранной ручки); помещается ли — замер на baseline, риск 7.2. Сами логи в промпт не попадают — только сводки ручек. *Информация о серверах:* записи целиком в промпте: оркестратору — название, ip, учётка, теги и краткое описание каждого сервера; агенту — полное описание своего сервера и полная информация по его тегам.

**Обновление.** *Логи и ручки:* логи пишутся непрерывно, частота и ретенция — у каждого лога свои: периодические — со своим интервалом, событийные — при новом событии; ретенция — ротация файла этого лога. Конфиг логгеров фиксируется при добавлении сервера: при обновлении каталога или тулкита ранее добавленный сервер продолжает писать логи прежней версии, обновить — удалить сервер и добавить заново; версия тулкита видна в каждой записи (тег v), ручка при несовпадении отвечает «нет данных» или предупреждением. Ручки обновляются релизом, каждый релиз — прогон eval (5.3). *Информация о серверах:* записи не обновляются и не правятся — только удаление и повторное добавление. *Служебные:* журнал не чистится.

**Качество знаний** — по двум осям, соответствующим двум факторам знаний.

| Свойство | 1. Логи и ручки | 2. Информация о серверах |
| --- | --- | --- |
| Покрытие | есть ли лог и соответствующая ручка под вопрос и с какого момента идёт логирование — с добавления сервера в инструмент; раньше данных нет (ответ «нет данных за окно», 2.1), вглубь окно ограничено ещё и ретенцией лога | есть ли запись с информацией о сервере — добавлен ли сервер в инструмент |
| Актуальность | почти тривиальна: вопросы «сейчас» покрывают one-shot-ручки, историю с момента добавления сервера — ручки просмотра логов | записи не актуализируются: модификаций нет, правка — удалением и повторным добавлением сервера |
| Консистентность | противоречий нет | конфликты между описаниями (одинаковые или похожие краткие описания) разрешает куратор при добавлении: сравнивает с уже добавленными серверами и спрашивает пользователя о различии |

### 4.4 Модель и промпты

- **Модель.** Одна локальная модель на все четыре роли, один инстанс Ollama. Выбирается по baseline (6.1) из двух кандидатов: Qwen3.8-27B — плотная, с гибридным вниманием (полное внимание только в 16 из 64 слоёв, поэтому длинный контекст дешёвый), август 2026, Apache-2.0; Qwen3.6-35B-A3B — MoE с 3B активных параметров, апрель 2026, Apache-2.0, декодирует в разы быстрее. Развилка — качество против скорости (3.4): сессия — 5–7 вызовов модели в типичном случае, и thinking умножает число генерируемых токенов. Критерии — метрики 5.2, валидность вызовов тулз, задержка; итог — ADR. Gemma 4 31B и T-pro-it-2.0 — запасные кандидаты на случай, если обе Qwen провалятся на русском. Квантизация — Q8: 27B ≈ 30 ГБ, с окном 64k ≈ 34–36 ГБ; MoE ≈ 39 ГБ, при нехватке памяти — Q6\_K.
- **Промпты.** Из чего собирается: инструкции роли; контекст — у оркестратора записи о серверах (название, ip, учётка, теги, краткое описание), у агента — полное описание сервера и полная информация по тегам; схемы тулз (у агента — все ручки по тегам сервера, 4.3); история сессии вместе с thinking прошлых шагов; результаты тулз. Retrieval нет. Язык — русский, идентификаторы (имена ручек, тулз, параметров) — латиницей. Шаблоны — файлы в git рядом с кодом, хэш версии пишется в журнал на каждый вызов. *Thinking* включён во всех ролях и сохраняется в истории: у оркестратора, инспектора и куратора — на всю сессию чата, у агента — на весь запуск; между запусками агента и между сессиями чата — нет. Так делают современные агентные модели: сохранение рассуждений между шагами повышает согласованность решений и сокращает повторные рассуждения (у Qwen3.6 это обученная опция, у Qwen3.8 — поведение по умолчанию). Уровень рассуждения на baseline — низкий.
- **Ограничения.** Окно контекста — 64k токенов всем ролям, задаётся явно: по умолчанию Ollama выбирает окно по объёму VRAM и молча обрезает промпт, если он длиннее. Перед каждым вызовом система считает токены и при переполнении не отправляет запрос — это системная ошибка (4.2). Само окно 64k качество не меняет — оно в пределах родного контекста моделей (262k), масштабирование позиций не включается; качество падает от фактической длины промпта (исследования Chroma «Context Rot» и NoLiMa), поэтому длина промптов по ролям видна в журнале, а длинные промпты агента — риск 7.2. Предел вывода — 8k токенов (thinking низкого уровня + ответ). Параметры выборки — из карточки модели: с thinking — temperature 1.0, top\_p 0.95, top\_k 20; без thinking — 0.7 / 0.8 / 20 и presence\_penalty 1.5. Жадной выборки нет: карточки предупреждают о бесконечных повторах, а детерминизм не нужен — eval гоняется ~5 раз при temperature > 0 (5.3).
- **Версионирование и откат.** Своя сборка модели для Ollama (Modelfile): GGUF-файл с контрольной суммой, параметры окна и выборки, собственное имя; Modelfile лежит в git рядом с промптами, версия Ollama зафиксирована в развёртывании, хэш модели пишется в журнал на каждый вызов. Причина — теги моделей в Ollama изменяемы, а разбор вызовов тулз и вставка thinking в историю зависят от версии Ollama. Смена модели, параметров или Ollama — новый Modelfile, прогон eval (5.3), переключение; откат — прежний Modelfile. Промпты обновляются тем же циклом через git.
- **Дообучение.** Не делаем.

| Обслуживаемые серверы (Linux, Windows Server) | ручки: срез логов, разовые команды чтения, осмотр инспектором; установка логгеров при добавлении; остановка логгеров при удалении | SSH по ключу и учётке из формы добавления; клиент SSH — бэкенд | компания-клиент: серверы, учётки, ключи |
| Telegraf на хостах | логгеры: пишут логи в JSON-файлы с ротацией | конфиг входов по тегам ставится при добавлении сервера и дальше не меняется; файлы читают ручки по SSH | мы — конфиги и свои сборщики; Telegraf — open source |

Мессенджеров, CRM, тикет-систем и интеграций с мониторингом нет: всё общение — в своём веб-интерфейсе. Сетевые устройства (MikroTik, RouterOS) — в расширении 2 (1.3).

**Интерфейс пользователя.** Окна: чат рабочего запроса; форма «Добавить сервер»; чат добавления; карточка подтверждения; список серверов с удалением; история чатов только для чтения; окно подтверждения нового чата. В чате реплики системы приходят целиком — стриминга текста и рассуждений нет; пока система работает, видны статусные сообщения понятным языком («определяю сервер», «опрашиваю srv-1c…», «формирую ответ»), они не сохраняются в истории; кнопка «Остановить» прерывает прогон и закрывает чат. Источники данных называются прямо в тексте ответа понятным языком, без имён ручек. Все реплики рабочего запроса пишет оркестратор; внутренних меток пользователь не видит. На каждом ответе — 👍/👎 и необязательный комментарий. Карточка подтверждения показывает краткое описание, название и краткие описания по тегам; пользователь подтверждает или пишет замечания куратору; карточка отправляется не больше 3 раз. Чат закрывается техническим сообщением по лимиту, по «Остановить» и при внутренней ошибке; продолжить — в новом чате. В интерфейсе заявлено, что пользователь работает с LLM-системой и что действия пишутся в журнал. Макеты окон делаются в Claude Design на минимальной дизайн-системе и затем переписываются в код (4.1).

### 4.6 Инфраструктура и развёртывание

- **Стек.** Процесс на сервере, без оркестрации и serverless: один бэкенд-процесс (FastAPI + LangGraph + SQLite) на одном из серверов компании слушает 127.0.0.1 и раздаёт собранный фронтенд; Ollama — сервис на машине с GPU в контуре компании (вынос на облачную GPU-машину — решение пользователя, 1.1); на обслуживаемых хостах — Telegraf. Версия Ollama и Modelfile модели зафиксированы в развёртывании (4.4).
- **Среды.** Две. *Стенд разработки и eval*: бэкенд у разработчиков, инференс на арендованной GPU-машине с Ollama через SSH-туннель, тестовые хосты с логгерами, judge — Claude API, трейсы — Phoenix; здесь гоняется eval (5.3) и baseline. *Установка у клиента*: тот же бэкенд на сервере компании, Ollama в контуре, трейсинг выключен — только журнал в БД. Данные клиента на стенд и в Claude API не попадают.
- **Вычисления.** GPU с 48 ГБ VRAM под модель (на стенде — A6000): Qwen3.8-27B в Q8 с окном 64k — 34–36 ГБ, Qwen3.6-35B-A3B в Q8 — ≈ 39 ГБ (при нехватке — Q6\_K). Бэкенд — CPU и диск: SQLite с записями о серверах и журналом (≈ 2 МБ в день), состояние сессии — в памяти процесса. Логи — на хостах (ориентир 20–50 МБ в месяц на хост). Индекса и кэша нет.
- **Масштабирование и отказоустойчивость.** Нагрузка одной установки ограничена одной активной сессией одного пользователя: вызовы модели идут последовательно (batch = 1), очереди нет; рост числа клиентов — новые установки, каждая со своим железом, общего сервиса нет. Отказ движка — повтор вызова, затем системная ошибка и закрытие чата; резервной модели нет — инстанс один. Недоступный хост — ошибка ручки и сообщение пользователю, а не сбой системы. Падение процесса бэкенда — активная сессия теряется (состояние в памяти, восстановления нет); записи о серверах и журнал сохраняются в SQLite.
- **Доступ.** Аутентификации и авторизации в приложении нет: пользователь один, сети доверяем; к интерфейсу есть доступ у того, кто может пробросить порт по SSH на сервер инструмента. Журнал виден только на сервере инструмента; пользователю в интерфейсе — только история чатов. SSH-ключи серверов хранятся в записях о серверах и в промпт не попадают.

**E2E и node-isolate.** Тест e2e проверяет систему целиком: правильно ли узлы передают запрос друг другу и хватает ли каждому контекста, чтобы делегировать, ответить или передать вопрос пользователю; поведение одного узла проверяется в node-isolate. Где сценарий требует ответа пользователя, действует правило плана «один такт — один прогон»: тест покрывает один такт, а многотактовый сценарий — цепочка тестов, в которой вопрос или карточка прошлого такта зафиксированы как начало транскрипта, остальное окружение — живое. Итоговый такт добавления — подтверждение карточки и проба: рабочий запрос в новой сессии по только что добавленному серверу проверяет, что краткого описания хватает оркестратору, а полных полей и ручек — агенту.

**Коды сценариев.** В начале `readme.md` каждого теста — код сценария: `MR-1a`…`MR-8b` — пункты Main-Run, `IN-1a`…`IN-4` — пункты Init, `X-LIM`, `X-MULTI`, `X-CHK`, `X-FIELDS` — проверки вне плана, `SYS` — системные тесты; всего 31 код. Генератор набора пишет реестр и собирает из него `SCENARIOS.md` и `scenarios.json`: по коду находятся e2e-тест и его узловые тесты по звеньям (оркестратор → агент → оркестратор; инспектор → куратор; проба). Разрыв e2e локализуется прогоном узловых тестов того же кода.

**Исключительные сценарии 2.2.** Строки о поведении модели покрыты тестами eval-сета, строки о поведении системы — системными тестами:

### 5.2 Метрики

Метрики разведены по четырём узлам — оркестратор, локальный агент, инспектор, куратор, — плюс общие проверки формата и вердикт e2e; каждая считается либо rule-based по эталону теста, либо LLM-judge по фиксированным критериям. В `readme.md` тестов у метрик короткие идентификаторы — в таблицах они в скобках. Метрики с пометкой «предложение» предложены набором тестов сверх утверждённых: до утверждения они считаются отдельно и откат не запускают.

**Классы ответов по узлам.** Каждый узел проставляет класс своим ответом — вызванной тулзой: у оркестратора `delegate` → `delegated`, `ask-user` → `clarify`, `answer-user` → `answered`, `reject` → `not_in_scope`; локальный агент заканчивает запуск тулзой `answer` (после ручек → `executed`) или `escalate` с видом (`no_template`, `wrong_addressee`, ошибка ручки, `ambiguous`); у инспектора `submit` → `filled`, `ask-user` → `clarify`; у куратора `QA` → `conflict`, `confirmation` → `consistent`, а явный отказ `deny` класса не имеет и проверяется по тулзе. Rule-based доли считаются сравнением класса и его полей с эталоном теста. Классы — внутренние: пользователь их не видит, в контракт они не входят.

| Узел | Класс | Когда | Поля, которые проверяются |
| --- | --- | --- | --- |
| оркестратор | `not_in_scope` | запрос вне скоупа: изменение, команда, общий вопрос, секрет, неподдерживаемый компонент, действие по расписанию; по плану тестов (предложение) — слишком много серверов, нет подходящего сервера | — |
| оркестратор | `clarify` | не хватает данных для маршрутизации или ответа. Тесты делятся на три ситуации, которые задаёт тест, а не агент: A — не понятно, какого агента вызывать; B — агент эскалировал выбор ручки, оркестратор уточняет у пользователя; C — нет доступа к серверу: не отвечает или ключ отклонён | варианты серверов (A); сервер и причины (C) |
| оркестратор | `delegated` | задача передана агенту сервера | `delegate_to`, текст задачи |
| оркестратор | `answered` | ответ без делегации — по записям о серверах (ip, теги, краткие описания) | — |
| локальный агент | `no_template` | под запрос нет ни ручки над логами, ни разовой команды | — |
| локальный агент | `wrong_addressee` | запрос не по скоупу агента: просят про 1С, а в тегах только `backup` и в описании про 1С ничего | — |
| локальный агент | `ambiguous` (вид эскалации, предложение) | подходят несколько ручек, нужен ответ пользователя — ситуация B у оркестратора | — |
| локальный агент | `executed` | ручка выбрана и выполнена, запуск закончен `answer` | `template_id`, аргументы |
| инспектор | `filled` | поля сервера заполнены | теги, полное описание, полная информация по тегам |
| инспектор | `clarify` | вопрос пользователю по системе | поле, по которому вопрос |
| куратор | `conflict` | краткие описания не различают серверы | какие серверы |
| куратор | `consistent` | конфликтов нет | — |
| куратор | `deny` (тулза, без класса) | просьба вне краткого описания и названия: теги, полное описание, другой сервер, данные подключения | — |

Как оркестратор отвечает на эскалации агента, в документах не задано; эталоны набора (предложение): `no_template` → `reject` с перечнем возможностей; `wrong_addressee` → `delegate` агенту другого сервера; `ssh-refused` → `ask-user`, ситуация C; `ambiguous` → `ask-user`, ситуация B. Итоговое `answer-user` после ответа агента в `orch-no-delegation` не считается: там оценивается только judge, а `orch-no-delegation` — по первому решению оркестратора. Отказ инспектора при неверном SSH идёт через `ask-user`, но в `insp-clarify` не входит — для него отдельная метрика `insp-refusal`.

**Rule-based метрики.** Каждая метрика — доля тестов данного типа, где ответ узла совпал с эталоном. Эталон лежит в тесте рядом со сценарием: ожидаемый класс, ситуация, идентификаторы и значения полей.

Ложные срабатывания считаются внутри той же метрики: `not_in_scope`, `clarify`, `no_template`, `wrong_addressee`, `conflict`, инспекторский `clarify` и `deny` проставлены там, где ожидался ответ или делегация, — тест не засчитан. Отдельной доли неправильных отказов нет.

**LLM-judge метрики.** Judge получает контекст узла, его ответ и эталонные факты теста и выносит вердикт по каждому критерию: выполнен или нет. Тест засчитан, когда выполнены все критерии метрики; доля — по тестам.

Три критерия: (1) язык понятен пользователю — нет внутрисистемных терминов; (2) суть донесена верно; (3) куратор указал на правильные серверы — именно те, между описаниями которых конфликт. Тест засчитан при всех трёх | ответ куратора, эталонные пары серверов | Исключение «конфликт описаний» |
| куратор | качество кратких полей (`judge-cur-summary`, предложение) | (1) краткое описание — роль и отличительные признаки сервера, без точечных фактов; (2) нет фактов, которых нет в артефакте инспектора или ответах пользователя; (3) краткие описания по тегам ситуативны — пользователи и базы 1С, СУБД, ресурсы; (4) название узнаваемо; без разговорных оборотов, личных имён и сведений о доступе | артефакт инспектора, ответы пользователя, поля куратора | Выход 1 |
| куратор | текст явного отказа (`judge-cur-deny`, предложение) | (1) причина понятна, без внутренних терминов; (2) нет имитации выполнения; (3) правка «позже» не обещана — после `deny` чат закрывается | реплика `deny` | Вход 1; 2.2 |

Judge — Claude API, в него уходят только данные стенда; на первом проходе каждый judge-вердикт сверяется вручную.

**Как считаем.**

- Единица — тест в своём типе (5.1); варианты внутри теста — наблюдения одного теста: тест засчитан, когда засчитаны все его варианты. Каждый тест гоняется ~5 раз при temperature > 0 (5.3): цикл — 150 тестов × 5 = 750 прогонов тестов, ≈ 1 000 наблюдений, распределённых по метрикам.
- Rule-based: совпадение с эталоном — 1, иначе 0; поле с допуском сравнивается по допуску из теста.
- LLM-judge: вердикт по каждому критерию — выполнен или нет; тест засчитан только при всех выполненных; шкалы баллов нет.
- Общие метрики формата считаются на каждом вызове модели во всех тестах, а не по тестам.
- E2E: тест засчитан, когда выполнены `e2e-expected-state` и judge итоговой реплики — ответа, вопроса или карточки; разрыв цепочки в любом звене — тест не засчитан. Узловые проверки, которые e2e-тест перечисляет (например, «вопрос задан?» у куратора), — части его вердикта; метрики узлов по журналу e2e нужны для локализации разрыва и в доли node-isolate не входят.
- Системные тесты проверяют правила системы, а не модель: результат — «прошёл / не прошёл», в доли не входит. Где настоящая модель не воспроизводит нужную последовательность вызовов надёжно — 10 вызовов сверх лимита, три невалидных вызова, исчерпание карточек, — её заменяет скриптовая заглушка с заданной последовательностью вызовов.
- Не входят в доли до решения: тест и вариант e2e со статусом «ждёт решения» (метрики GPU) и e2e-тест, которому нужна ещё не реализованная ручка.
- Предложены набором тестов, документами пока не зафиксированы: вердикт e2e и содержание `e2e-expected-state`; засчитывание теста по всем вариантам; прочтение «все числа перенесены» как «обязательные числа из эталона есть, остальные совпадают»; правило цепочки для `local-handle-choice`; соответствие `QA` и `confirmation` классам куратора; проба после добавления; скриптовая модель в системных тестах; эталоны ответа на эскалации агента (выше).
- Итоговая оценка — композиция долей rule-based и LLM-judge; решения об откате принимаются по каждой доле отдельно (5.3): падение любой доли по классу относительно предыдущего цикла.

Классы ошибок, которые ловим отдельно: ложный отказ (класс отказа там, где ожидался ответ или делегация), неверный агент, неверная ручка или её аргументы, выдуманные числа в ответе, невалидный вызов тулзы, разрыв цепочки e2e.

### 5.3 Процедура

- Когда гоняем: при каждой модификации ручек, промптов, параметров модели или смене модели (новый Modelfile, новая версия Ollama).
- Одна модификация — один цикл: так точно известно, что вызвало регрессию.
- Canary-набор на релиз: весь eval-сет (150 тестов) и системные тесты; порог отката — регрессия по любому классу метрик; упавший системный тест — дефект системы, релиз не выходит.
- Тесты на распределении, а не на одном примере: ~5 прогонов каждого теста при temperature > 0; rule-based — доля успешных по классу, judge — доля тестов, где выполнены все критерии, e2e — доля сценариев, доведённых до ожидаемого состояния.
- Что считаем регрессией и что делаем: падение любой доли по классу относительно предыдущего цикла или ниже порога отката 3.1 — откат модификации (для модели — возврат к прежнему Modelfile). В малых классах — уточнение B (1 тест), уточнение C, `no_template` и `wrong_addressee` (по 2 узловых теста) — одна ошибка сдвигает долю на 10–20 процентных пунктов; пока классы не пополнены, регрессией по ним считается падение больше чем на одно наблюдение за цикл (предложение).
- Baseline (6.1) — весь набор на каждой из двух моделей-кандидатов, по отдельному циклу.
- Как гоняем: node-isolate — на фикстурах, без стенда; e2e и системные тесты — на стенде: перед тестом снапшот и засев под сценарий, после — сброс; такты многотактового сценария идут цепочкой.
- Сколько стоит: проход — ≈ 600–900 вызовов модели (node-isolate — один-два вызова на наблюдение, e2e рабочего запроса — 5–7, e2e добавления — до 20–30 вместе с осмотром инспектора); системные тесты добавляют немного — часть из них идёт со скриптовой моделью. Цикл — ≈ 3–4,5 тыс. вызовов: по скоростям 3.2 (≈ 30–50 с на вызов у плотной 27B, ≈ 10–15 с у MoE) это ≈ 25–60 GPU-ч на 27B и ≈ 8–20 GPU-ч на MoE; при batch = 1 это и время цикла — сутки-двое на 27B. В бюджет 3.3 (60–100 ч аренды в месяц) помещаются 1–2 цикла на 27B или 3–6 на MoE — это предел частоты модификаций; узловые тесты изменённой роли — быстрый предварительный прогон перед циклом (предложение). Judge — ≈ 1 тыс. вызовов Claude API на цикл.
- Где гоняем: на стенде (4.6); трейсы прогона — в Phoenix, вызовы и токены — в журнале.
- Ручной ревью: ответы каждого класса — по усмотрению; judge-вердикты первого прохода — все (≈ 180).

### 5.4 Контроль качества в рантайме

- Каждый вызов тулзы система проверяет по схеме: имя, аргументы, типы. Невалидный вызов — сообщение модели с первой проблемой и схемой вызова, засчитывается в лимит тулзы; три подряд — системная ошибка. Ограничение формата на уровне декодирования — только как усложнение (6.2).
- Лимиты тулз проверяет система; вызов сверх лимита — отказ с комментарием модели; десять подряд — закрытие сессии. Таймауты вызова модели, ручки и SSH — 4.2.
- Ручка сама проверяет свои аргументы и возвращает ошибку-enum с комментарием (какие значения допустимы) и примером; если логгер перестал писать — предупреждение вместе с результатом.
- Перед каждым вызовом модели — подсчёт токенов промпта; переполнение окна — системная ошибка, а не молчаливая обрезка.
- Инфраструктурный сбой (движок недоступен после повтора, исключение в ручке или узле) — техническое сообщение и закрытие чата (4.2); недоступный сервер — обычная ошибка ручки, не сбой.
- Текст пользователю — свободный формат, без валидации; при неуверенности оркестратор задаёт вопрос пользователю (ask-user) в пределах лимита.
- 👍/👎 на каждом ответе; SLI 3.5 считаются по журналу.

### 7.1 Структурные ограничения модели и чем закрываем

| Каталог ручек сервера не помещается в контекст агента или выбор ручки деградирует на большом каталоге; все ручки по тегам сервера подаются сразу | не измерена: каталог от 3–5 тыс. токенов (5–10 ручек на тег) до ≈ 15 тыс. (около сотни ручек на сервере host + 1c + db) — оценка | переполнение окна или неверный выбор ручки; падают метрики выбора ручки и аргументов (5.2), растёт префилл (3.2) | замер на baseline (6.1); фоллбэк — двухступенчатая подача: имена с однострочными описаниями, затем схема выбранной ручки (+1 вызов модели на шаг) |
| Длинный промпт агента снижает качество (context rot): каталог ручек, описания, результаты до 20 ручек и сохранённый thinking — до 45–60 тыс. токенов при окне 64k | не измерена; по исследованиям (Chroma «Context Rot», NoLiMa) деградация есть у всех моделей уже на десятках тысяч токенов | неверный выбор ручки или пропуск фактов в ответе агента на серверах со многими тегами и длинными циклами | длина промптов по ролям в журнале; замер на baseline; фоллбэк — двухступенчатая подача каталога ручек (6.2) |

Непроверенные допущения из 1.3, которые могут всё сломать: логи на хостах достаточно стандартны, чтобы ручки считали по ним сводки; инспектор и агенты ориентируются на машинах (где логи, службы, задания); модель формирует валидные нативные вызовы тулз без ограничения формата. Все три проверяются на baseline (6.1) и тестах node-isolate.

### 7.3 Безопасность, соответствие, этика

- **Персональные данные.** В логах, ответах ручек, промптах и журнале есть учётки и имена пользователей (входы, сеансы 1С, Security log), IP и имена хостов, имена баз и процессов, тексты описаний серверов. Всё это остаётся в контуре компании: инференс локальный, сторонних LLM-API нет; judge Claude API работает только на данных стенда. Маскирования нет. Логи живут на хостах со своей ретенцией и удаляются вместе с сервером; журнал хранится на сервере инструмента бессрочно. Если пользователь выносит модель на облачную GPU-машину, соответствие 152-ФЗ — его решение и ответственность (1.1).
- **Prompt injection.** Через вывод ручек (логи, имена процессов, записи событий) текст попадает в промпт. Защиты нет — принятый остаточный риск качества (7.2): модель может только выбрать ручку из каталога и её аргументы, выполнить текст из лога она не может, все ручки только читают, вызовы ограничены лимитами.
- **Нежелательный контент.** Отдельных фильтров на входе и выходе нет: пользователь один и доверенный; вопросы вне предметной области, запросы секретов и изменений — отказ оркестратора; ответ модель собирает только из результатов ручек и записей о серверах.
- **Действия с последствиями.** Агенты только читают. Единственное изменение на хосте — установка логгеров, нужных им библиотек и предусловий при добавлении сервера, с записью в журнал и инструкцией удаления у каждого тулкита; при удалении сервера логгеры останавливаются. Удаление сервера — системное окно подтверждения, выполняет код без модели. Произвольных команд нет, инструкций для изменений система не даёт.
- **Прозрачность.** В интерфейсе заявлено, что пользователь работает с LLM-системой и что запросы и действия пишутся в журнал; ответ называет период и источники данных.
- **Логи.** Журнал (сессии, реплики, полные входы и выходы модели с thinking, вызовы и результаты ручек, фидбек) хранится в SQLite на сервере инструмента бессрочно; доступ — у того, кто имеет доступ к этому серверу; пользователь в интерфейсе видит только историю чатов. SSH-ключи серверов в промпт и в журнал вызовов модели не попадают. Трейсы Phoenix — только на стенде.

- Метрики эксплуатации: доступность — SLI «прогон до конца без падений»; задержка — P50 / P95 сессии и вызовов по журналу; стоимость — GPU-время на сессию; 👎 за неделю.

## 9. Ресурсы

- **Люди.** Два автора — Тураев П. Н. и Мотовилов А. А.: бэкенд и агенты, фронтенд, тулкиты и ручки, стенд, eval-сет и разметка — своими силами.

- **Отдача.** По критериям 1.1: входы по RDP и SSH ради проверок — до ≤ 60 % исходного уровня; простои по тривиальным причинам — до ≤ 50 %; число найденных «тихих» проблем за пилот; новый сотрудник проводит базовый мониторинг без предшественника.

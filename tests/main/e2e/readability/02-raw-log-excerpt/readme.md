# main/e2e/readability/02 — неструктурируемые данные: сырая выборка журнала обращений

Сценарий плана: **MR-1d** — Читаемость ответа пользователю — не сырые данные тулз, а показательные с комментариями; данные разрозненные, неструктурируемые, большого объёма. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-1d — неструктурируемые данные. Логгер ошибок веб-сервера с полуночи перестал писать (после ротации журнала nginx ему нечего читать): ручка `web.errors` возвращает сводку по 23:59 и предупреждение «источник не обновлялся с 00:00» (design doc 4.1, 5.4), и за остаток ночи единственный путь к ответу — сырая выборка журнала обращений (`web.access_excerpt`). Агент должен пройти цепочку ручек (сводка с предупреждением → выборка), а оркестратор — превратить строки лога в понятный ответ: что сломалось, когда, что не удалось узнать.

1. Засев: с 22:00 накануне бэкенд каталога сайта отвечает 502 (остановлен php-fpm для /catalog), импорт прайса даёт 504; ротация журнала ошибок nginx в 00:00 с правами, недоступными учётке сбора.
2. Запрос утром: «Сколько ошибок было у сайта за ночь?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Засев — шаг 1; права и php-fpm восстанавливаются после теста.

## Вход

Запрос шага 2. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор → агент web-01: `delegate` — сколько ошибок у сайта за ночь.
- Агент: `web.errors` → сводка по 23:59 и предупреждение «источник не обновлялся с 00:00»; следующая ручка — `web.access_excerpt` (коды 5xx, остаток ночи или вся ночь, ≤ 200 строк) или `host.log_excerpt` по access.log; `answer` — до полуночи по сводке, после — оценка по выборке с оговоркой о неполноте.
- Оркестратор → пользователь: ошибки шли почти всю ночь, в основном на каталоге (502), на импорте прайса (504); до полуночи — число по журналу ошибок, после — оценка; журнал ошибок с полуночи не обновлялся; без строк лога, IP и user-agent'ов; без `chmod`.
- Признаки разрыва: агент остановился на «после полуночи данных нет» (слабый, но не ошибочный ответ `[предл.]`); «после полуночи ошибок 0»; сырые строки лога в ответе пользователю; число строк выборки выдано за точное число ошибок; выдуманная причина остановки журнала; инструкция исправить права; `ask-user` с просьбой починить права.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Пользователь получает понятный ответ: ошибки на сайте шли с вечера до утра — главным образом недоступен каталог (502), не проходит импорт прайса (504), единичные ошибки в корзине; до полуночи — точное число по журналу ошибок, после — оценка по выборке; журнал ошибок веб-сервера с полуночи не обновлялся (причина системе не видна); источники названы понятным языком.
- Ошибки: строки лога; «ошибок не было»; точное число после полуночи как установленное; `chmod`; «nginx упал» как факт; «права после ротации» как установленная причина.

## Эталон

- Цепочка: `delegate` → web-01; агент — `web.errors` (результат с предупреждением) → `web.access_excerpt` или `host.log_excerpt` (access.log, фильтр 5xx), `answer`; один запуск; `ask-user` — 0; `answer-user`.
- Итог: число до полуночи — из сводки `web.errors`; группы ошибок после полуночи (502 каталог, 504 импорт) и границы времени — из выборки; оговорка о неполноте есть.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22]; `judge-readability` `[предл.]` — ответ читается без подготовки: не сырой вывод ручек, главное выделено и прокомментировано, длинные перечни свёрнуты в итоги с примерами, объём соразмерен вопросу.
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `local-handle-choice` (цепочка). Узлы — `local/handle-choice/14`, `orchestrator/report/14`.

## Основания

Транскрипт плана: данные «не структурируемые»; предупреждение «источник не обновлялся с …» вместе с результатом (design doc 4.1, 5.4); [AR-26]; [UC-22].

## Данные

Живой стенд M, запрос, эталонная цепочка (адресат, обязательные ручки, число запусков и вопросов), рубрики judge. Фактические числа берутся из журнала прогона (сводки ручек), не из этого описания.

# main/e2e/readability/01 — данные большого объёма: журнал регистрации 1С за день

Сценарий плана: **MR-1d** — Читаемость ответа пользователю — не сырые данные тулз, а показательные с комментариями; данные разрозненные, неструктурируемые, большого объёма. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-1d — читаемость ответа пользователю при данных большого объёма: за день в журнале регистрации 1С десятки тысяч событий. Проверяется вся цепочка: агент возвращает итоги, а не список; оркестратор выделяет главное (ошибки, отмены, пики) и комментирует, а не пересказывает счётчики и не вставляет таблицу на экран.

1. Засев: рабочий день накануне с активностью 10–12 пользователей 1С (десятки тысяч событий), серией ошибок прав доступа у тестовой учётки утром, несколькими блокировками днём и всплеском отменённых транзакций у одного пользователя.
2. Запрос: «Что было в журнале регистрации 1С за вчера?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Засев — шаг 1 (сценарий нагрузки 1С на стенде).

## Вход

Запрос шага 2. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор → агент srv-1c: `delegate` — сводка журнала регистрации за вчера: ошибки, предупреждения, активность.
- Агент: `1c.eventlog` за вчера (допустимо + `1c.eventlog_excerpt` по пользователю с ошибками); `answer` — итоги с числами, не список событий.
- Оркестратор → пользователь: главное первым — ошибки и что за ними стоит, отмены; общая картина одной-двумя фразами; числа из сводки; без списка событий.
- Признаки разрыва: агент вернул сырой список (сотни строк) и оркестратор его пересказал; пропущены ошибки; выдуманные причины ошибок как факты; таблица из всех счётчиков без выделения главного.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Пользователь получает короткий ответ с выделенным главным: число ошибок и их группы с пользователями и временем, отменённые транзакции, пики активности; общее число событий — одной цифрой; источник — журнал регистрации 1С; период — вчера.
- Ошибки: список событий или таблица на экран; пропуск ошибок; «всё нормально» без чисел; выдуманные причины.

## Эталон

- Цепочка: `delegate` → srv-1c; агент — `1c.eventlog` (window = вчера), `answer`; один запуск; `ask-user` — 0; `answer-user`.
- Итог: числа ошибок и отмен — из сводки; длина ответа — не больше нескольких абзацев `[предл.]`.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22]; `judge-readability` `[предл.]` — ответ читается без подготовки: не сырой вывод ручек, главное выделено и прокомментировано, длинные перечни свёрнуты в итоги с примерами, объём соразмерен вопросу.
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `local-handle-choice`. Узлы — `orchestrator/report/13`, `local/answer-from-return/09`.

## Основания

Транскрипт плана: «отдельно проверяется читаемость данных пользователю (не сырые json тулзов, а показательные с комментариями)… данные… большого объёма»; критерий читаемости в метриках v0.2 отсутствует — рубрика `[предл.]` (файл-обращение).

## Данные

Живой стенд M, запрос, эталонная цепочка (адресат, обязательные ручки, число запусков и вопросов), рубрики judge. Фактические числа берутся из журнала прогона (сводки ручек), не из этого описания.

# main/e2e/data-mismatch/02 — на сервере не логируется запрошенная метрика (GPU)

Сценарий плана: **MR-5b** — Несовпадение запрошенных данных — на сервере не логируется запрошенная метрика. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-5b. Спрашивают о видеокарте сервера, на котором её нет и метрика GPU не собирается. Оркестратор не знает этого из контекста и не должен отказывать из памяти; агент проверяет оборудование на сервере; ответ — «видеокарты нет», без чисел.

Запрос: «Как загружена видеокарта на сервере 1С за сутки?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

## Вход

Запрос. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор: вопрос о GPU на srv-1c — `delegate` srv-1c (не отказ из памяти: оркестратор не знает, что видеокарты нет).
- Агент: `host.load_profile(gpu)` → ошибка (или сразу) → `host.now_inventory` `[предл.]`; `answer`: GPU нет, метрика не собирается.
- Оркестратор → пользователь: на srv-1c видеокарты нет, данных о загрузке GPU нет, момент проверки; допустимо предложить acc-01.
- Признаки разрыва: `reject` или `answer-user` «GPU нет» без обращения к серверу; агент `no_template` («не поддерживается»); проценты загрузки GPU в ответе.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Ответ: на srv-1c видеокарты нет — данных о загрузке GPU нет; момент проверки назван; допустимо предложить acc-01, где GPU есть.
- Ошибки: проценты загрузки GPU; «такой вопрос пока не поддерживается»; «GPU нет» без проверки на сервере (по памяти).

## Эталон

- Цепочка: `delegate` → srv-1c; агент — `host.now_inventory` (допустимо после `host.load_profile(gpu)` с ошибкой) `[предл.]`, `answer`; один запуск; `ask-user` — 0; `answer-user`.
- Итог: факт «GPU нет» и момент — из сводки.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice`, `local-handle-choice`. Узлы — `local/handle-choice/08`, `orchestrator/report/08`.

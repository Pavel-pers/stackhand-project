# main/e2e/data-mismatch/01 — нет данных за запрошенный период

Сценарий плана: **MR-5a** — Несовпадение запрошенных данных — нет данных за запрошенный период. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-5a. Ручка есть, но запрошенный период — до установки логгеров. Окно «сентябрь» должно пройти по цепочке без подмены, ошибка `no-data-for-period` — превратиться в честное «данных нет», не в ноль. В фикстурах e2e сервер определяется однозначно; перевыбор сервера — только node-isolate (MR-5c).

Запрос: «Какая была нагрузка на сервер 1С в сентябре?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Стенд добавлен в систему после 2026-09-30 — данных за сентябрь нет.

## Вход

Запрос. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор → агент: окно «сентябрь» проходит без подмены — `delegate` за сентябрь; агент вызывает `host.load_profile` за сентябрь и получает `no-data-for-period` с самой ранней записью.
- Агент → оркестратор: `answer` — данных за окно нет (самые ранние — с даты установки); окно не подменено.
- Оркестратор → пользователь: «за сентябрь данных нет» — не ноль и не октябрь.
- Признаки разрыва: оркестратор подменил окно («за последний месяц»); агент молча вызвал ручку за октябрь и ответил его числами; агент эскалировал `no_template`; в ответе числа нагрузки.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Ответ по образцу контракта: «За сентябрь данных о нагрузке srv-1c нет»; не «0 %», без оценок по октябрю. Называть доступное окно не требуется [UC-13].
- Ошибки: нули; данные октября; «не поддерживается».

## Эталон

- Цепочка: `delegate` → srv-1c; агент — `host.load_profile` (окно — сентябрь 2026) → `no-data-for-period`, `answer`; ручек с другим окном — 0 `[предл.]`; один запуск; `ask-user` — 0; `answer-user` (или `reject` — засчитывается).
- Итог: в ответе нет чисел нагрузки.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice`, `local-handle-choice`, `local-handle-args` (окно), `judge-local-error`. Узлы — `local/handle-choice/07`, `answer-from-return/04`, `orchestrator/report/07`.

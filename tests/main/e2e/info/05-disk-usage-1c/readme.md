# main/e2e/info/05 — диски сервера 1С

Сценарий плана: **MR-1e** — Получение информации — другие вопросы по накопленным данным (диски, задание импорта, входы, время бэкапа по планировщику): старые e2e v0.1, в транскрипте пункт 1 назван общо. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Наследник старого e2e/01 (код MR-1e — другие вопросы по накопленным данным: рост и прогноз по томам). Полный путь: оркестратор по контексту выбирает srv-1c, агент читает накопленные данные о томах, оркестратор пишет ответ. Карточки подтверждения нет [UC-07].

Запрос: «Посмотри заполненность дисков на сервере с 1С».

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

## Вход

Запрос. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор: «сервер с 1С» → srv-1c по краткому описанию; вопросов нет; `delegate` — заполненность томов и когда закончится место.
- Агент: `host.volumes_usage` (с ростом и прогнозом), не one-shot; `answer` — тома с процентами, свободным местом, ростом и прогнозом.
- Оркестратор → пользователь: ответ, самый заполненный том первым, период наблюдений, источник понятным языком.
- Признаки разрыва: другой агент; `host.now_resources` или `host.path_size` вместо накопленных данных о томах; числа не из сводки; карточка подтверждения перед чтением.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Пользователь получает ответ за один ход: проценты и свободное место по томам srv-1c совпадают со сводкой в журнале; самый заполненный том назван первым; прогноз — как в сводке; период наблюдений назван.
- Состояние стенда не изменилось.
- Ошибки: другой агент; «ресурсы сейчас»; числа расходятся с журналом; выдуманные причины роста; карточка подтверждения.

## Эталон

- Цепочка: `delegate` → srv-1c; агент — `host.volumes_usage`, `answer`; один запуск; `ask-user` — 0; `answer-user`.
- Итог: тома и проценты — из сводки.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice`, `local-handle-choice`. Узлы — `orchestrator/delegated/01`, `report/01`, `local/handle-choice/01`, `answer-from-return/01`.

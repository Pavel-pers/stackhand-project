# main/e2e/info/01 — динамика параметра: загрузка за сутки и за час (CPU / GPU)

Сценарий плана: **MR-1a** — Получение информации — динамика параметра (монитор CPU за последний день). Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-1a — динамика изменения параметра (монитор CPU за последний день). Полный путь на живом стенде: оркестратор → агент → сводка по накопленным метрикам → ответ. Сервер и период ясны из запроса — уточняющих вопросов быть не должно, ответ приходит за один ход.

Три отдельные сессии (история между сессиями не переносится [K §2.3]):
1. A — «Какая была загрузка процессора на сервере 1С за последние сутки?»
2. B — «Какая загрузка CPU на srv-1c за последний час?»
3. C (GPU, ждёт решения о метриках GPU) — «Как была загружена видеокарта на сервере распознавания документов за сутки?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Засев для C: за 2–3 ч до прогона на acc-01 запущена пачка распознавания документов в acc-ocr, чтобы в окне был пик загрузки GPU.

## Вход

Три запроса A, B, C — три такта в трёх сессиях.

## Цепочка

- Пользователь → оркестратор: сервер назван («сервер 1С», «srv-1c», «сервер распознавания документов») — уточнения не нужны; `delegate` с запросом, который несёт сервер, что измерить (CPU; в C — GPU) и период (сутки или час).
- Агент: по запросу выбирает сводку по накопленным метрикам за окно (`host.load_profile` или `host.load_peaks`), не one-shot; не переспрашивает и не эскалирует; `answer` с числами за окно — среднее, пики со временем.
- Оркестратор → пользователь: `answer-user` с этими числами и названным периодом.
- Признаки разрыва: `ask-user` «какой сервер?» или «за какой период?»; агент эскалировал `wrong_addressee` или `no_template` — запрос не донёс, что нужно; агент прочитал не то окно, что в запросе; числа в ответе не из сводки (из памяти или выдуманы); повторный `delegate` без нужды.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- В каждой сессии пользователь получает ответ за один ход: среднее, пики со временем, период; вопросов нет.
- Числа — те, что вернул агент (журнал); причины пиков не придуманы; имён ручек нет.
- Состояние стенда не изменилось.
- Ошибки: вопрос «какой сервер?»; `host.now_resources` вместо истории; окно не то; числа расходятся с журналом; выдуманная причина пика.

## Эталон

- Цепочка (журнал): A, B — `delegate` → srv-1c, агент — `host.load_profile`/`host.load_peaks` (cpu) за 24 ч (A) / 1 ч (B), `answer`; C — `delegate` → acc-01, `host.load_profile` (gpu) за 24 ч; один запуск агента на сессию; `ask-user` — 0; итог — `answer-user`.
- Итог: ответ содержит среднее и максимум из сводки; период назван.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice`, `local-handle-choice`, `local-handle-args` (окно). Узлы — `orchestrator/delegated/04`, `report/04`, `local/handle-choice/02`, `/09`, `answer-from-return/02`.

## Основания

Транскрипт плана, пункт 1 (динамика параметра); [K §2.2] «Вопрос по данным, один сервер»; [UC-08]; [AR-24]. GPU в документах не упоминается — сессия C считается после решения (README, открытые пункты); пик GPU на стенде — засев теста.

Живой стенд M, запрос, эталонная цепочка (адресат, обязательные ручки, число запусков и вопросов), рубрики judge. Фактические числа берутся из журнала прогона (сводки ручек), не из этого описания.

# main/e2e/info/02 — единовременное значение: что грузит сервер прямо сейчас

Сценарий плана: **MR-1b** — Получение информации — единовременное значение (CPU сейчас). Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-1b — единовременное значение параметра (CPU сейчас). «Сейчас» должно дойти от запроса до ручки — агент выполняет one-shot (тип B), а не читает историю. На стенде засеяна известная нагрузка — виновник известен заранее.

1. Засев: за минуту до запроса на srv-1c запущена нагрузка на CPU на 5 минут (известный процесс, например stress-ng на 4 ядра).
2. Запрос: «Что сейчас грузит сервер 1С?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Засев нагрузки — шаг 1 сценария; после теста процесс завершается сам.

## Вход

Запрос шага 2. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор: «сейчас» и «сервер 1С» — сервер и момент ясны, вопросов нет; `delegate` с запросом о текущем моменте.
- Агент: по запросу выбирает one-shot `host.now_resources`, а не сводку за сутки; `answer` — снимок на момент выполнения: загрузка и процессы-виновники, среди них процесс засева.
- Оркестратор → пользователь: виновник с долей CPU и памяти, общая загрузка, момент снятия.
- Признаки разрыва: «сейчас» потерялось — запрос «за сутки» и сводка по логам; агент эскалировал `no_template` при one-shot в перечне; в ответе нет процесса из сводки или назван другой; предложение завершить процесс.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Пользователь получает ответ за один ход: процесс-виновник из засева с его долей CPU и памяти, общая загрузка, момент снятия.
- Сравнение с обычной нагрузкой (есть в примере контракта) — желательно, не обязательно (вторая ручка `host.load_profile` за час допустима [AR-26]).
- Состояние стенда не изменено системой (процесс засева не тронут).
- Ошибки: сводка за сутки вместо «сейчас»; виновник не назван или назван не тот; «нагрузка нормальная»; предложение завершить процесс с командой.

## Эталон

- Цепочка: `delegate` → srv-1c; агент — `host.now_resources` (допустимо + `host.load_profile` за час), `answer`; один запуск; `ask-user` — 0; `answer-user`.
- Итог: виновник в ответе = процесс засева (по сводке в журнале); момент назван.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice`, `local-handle-choice`. Узлы — `orchestrator/delegated/05`, `local/handle-choice/03`.

# main/e2e/info/03 — комплексный вопрос: «когда лучше делать бэкапы?»

Сценарий плана: **MR-1c** — Получение информации — комплексный вопрос («когда лучше делать бэкапы»: агент смотрит логи нагрузки и выбирает окно). Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-1c — комплексный вопрос: ответ не лежит ни в контексте оркестратора, ни в одной ручке; агент должен посмотреть логи загруженности сервера за несколько суток и выбрать время с меньшей нагрузкой; текущее время бэкапа — из заданий планировщика. Проверяется, что оркестратор ставит составной запрос, агент сочетает две ручки (цикл [AR-26]), а ответ пользователю — рекомендация с числами, без инструкций по переносу задания.

Запрос: «Когда лучше делать бэкапы на сервере 1С?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Стенд проработал не меньше 7 суток после добавления — есть профиль нагрузки за неделю с дневными пиками (засев: рабочая нагрузка 1С в будни 09:00–19:00) и фактические запуски бэкапа в 02:00.

## Вход

Запрос. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор: сервер не назван, но бэкап баз — только у srv-1c; уточнять не нужно; «ночью» или «в 02:00» из `tags-short-desc` — не ответ; `delegate` srv-1c с составным запросом: по нагрузке за несколько суток найти спокойные окна, учесть текущий бэкап, предложить окно.
- Агент: `host.load_profile` (cpu, ≥ 7 суток, по часам) + `host.sched_jobs` (задание бэкапа); `answer` с окнами наименьшей нагрузки и текущим временем бэкапа по факту.
- Оркестратор → пользователь: рекомендация с опорой на числа агента; период назван; ночной пик объяснён бэкапом только если это сказал агент; без инструкций, как перенести задание.
- Признаки разрыва: `answer-user` «ночью» без `delegate`; `ask-user` «какого сервера?»; агент вызвал одну ручку за сутки и ответил по ней; агент `no_template`; в ответе выдуманные часы; инструкция `crontab`; «я перенесу бэкап».

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Пользователь получает рекомендацию за один ход: самые спокойные окна с нагрузкой по данным агента (на стенде — ночь и раннее утро), текущее время бэкапа по планировщику, вывод — оставить или сдвинуть; период данных назван.
- Без команд и инструкций [UC-06]; система ничего не переносит.
- Ошибки: «делайте ночью» без чисел; выдуманные часы; `answer-user` из контекста; `crontab -e`; «перенёс».

## Эталон

- Цепочка: `delegate` → srv-1c; агент — `host.load_profile` (window ≥ 7 суток, step = hour) и `host.sched_jobs` (обязательно обе `[предл.]`), `answer`; один запуск; `ask-user` — 0; `answer-user`.
- Итог: окна и числа — из сводок; время бэкапа — из планировщика, не из описания.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22]; `judge-readability` `[предл.]` — ответ читается без подготовки: не сырой вывод ручек, главное выделено и прокомментировано, длинные перечни свёрнуты в итоги с примерами, объём соразмерен вопросу.
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice`, `judge-orch-task`, `local-handle-choice` (цепочка). Узлы — `orchestrator/delegated/12`, `report/12`, `local/handle-choice/12`, `answer-from-return/10`.

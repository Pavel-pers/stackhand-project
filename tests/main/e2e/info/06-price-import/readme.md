# main/e2e/info/06 — импорт прайса из 1С на сайт

Сценарий плана: **MR-1e** — Получение информации — другие вопросы по накопленным данным (диски, задание импорта, входы, время бэкапа по планировщику): старые e2e v0.1, в транскрипте пункт 1 назван общо. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Наследник старого e2e/02 (код MR-1e). Оркестратор по контексту (сайт забирает прайс из 1С) выбирает web-01, а не srv-1c, хотя в запросе есть «1С»; агент читает задания планировщика и последние запуски задания импорта; ответ говорит, что импорт не отработал, и не придумывает причину, которой система видеть не может. Второй запуск агента srv-1c для проверки публикации — допустим [UC-26], не обязателен.

1. Засев: с вечера накануне прогона на gw-01 блокируется трафик web-01 → srv-1c:8080 — импорты падают по таймауту.
2. Запрос: «Прайс на сайте вчерашний — выгрузка из 1С отработала?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Засев — шаг 1; блокировка снимается после теста.

## Вход

Запрос шага 2. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор: в запросе «1С», но импорт выполняет сайт («раз в час забирает прайс из 1С») — `delegate` web-01 по краткому описанию.
- Агент web-01: `host.sched_jobs` (задание импорта прайса); `answer` — время последнего успеха, неудачные запуски с кодами, текст ошибки подключения из вывода задания, если он есть.
- Оркестратор → пользователь: «не отработала с …», факты, без выдуманной причины; допустимо второй `delegate` srv-1c — доступна ли публикация 1С (`web.errors`/`host.service_events` у srv-1c) — и свод в одном ответе.
- Чего система знать не может: блокировку на gw-01 — это засев; у web-01 данных о шлюзе нет, поэтому «1С упала» или «шлюз заблокировал» как факт — выдуманная причина.
- Признаки разрыва: `delegate` srv-1c первым по слову «1С»; агент не нашёл задание (запрос не сказал, о каком задании речь); «всё в порядке»; инструкция снять блокировку.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Пользователь получает ответ за один ход: время последнего успешного запуска и число неудачных запусков с кодами — как в журнале; текст ошибки подключения из вывода задания (если он есть в сводке); вывод «прайс не обновлялся с …»; причина сверх факта не утверждается.
- Ошибки: первый `delegate` srv-1c; «всё в порядке»; «1С упала» как факт; инструкция снять блокировку.

## Эталон

- Цепочка: `delegate` → web-01; агент — `host.sched_jobs`, `answer`; допустимо второй `delegate` → srv-1c; `ask-user` — 0; `answer-user`.
- Итог: последний успех и число неудачных запусков — из сводки.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice`, `local-handle-choice`. Узлы — `orchestrator/delegated/02`, `report/02`.

## Основания

[UC-04], [UC-08], [UC-26]; критерий «причины не выдуманы» [M].

## Данные

Живой стенд M, запрос, эталонная цепочка (адресат, обязательные ручки, число запусков и вопросов), рубрики judge. Фактические числа берутся из журнала прогона (сводки ручек), не из этого описания.

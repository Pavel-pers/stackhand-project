# main/e2e/info/04 — «во сколько у нас делается бэкап?»

Сценарий плана: **MR-1e** — Получение информации — другие вопросы по накопленным данным (диски, задание импорта, входы, время бэкапа по планировщику): старые e2e v0.1, в транскрипте пункт 1 назван общо. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт 1 транскрипта, простой вопрос по накопленным данным (код MR-1e; наследник старого host-info/03). Сложность в трёх звеньях: сервер не назван (оркестратор находит его по кратким описаниям — бэкап упомянут только у srv-1c), в `tags-short-desc` есть «pg_dump в 02:00» (ответ из памяти без проверки — ошибка: нужны фактические запуски), а агент должен прочитать задания планировщика, а не ответить из своего полного описания.

Запрос: «Во сколько у нас делается бэкап?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Стенд проработал не меньше двух ночей после добавления — в планировщике srv-1c есть фактические запуски задания бэкапа в 02:00.

## Вход

Запрос. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор: сервер не назван; оркестратор находит его по кратким описаниям без вопроса; «02:00» из контекста — подсказка, не ответ; `delegate` srv-1c: во сколько запускается бэкап баз, сколько длится, как прошли последние запуски.
- Агент: `host.sched_jobs` (задание бэкапа), не `answer` из описания; `answer` — расписание и фактические запуски за последние дни.
- Оркестратор → пользователь: время, длительность, результат последних запусков, период проверки.
- Признаки разрыва: `answer-user` «в 02:00» без `delegate`; `ask-user` «бэкап какого сервера?»; `delegate` web-01 или acc-01; у агента в журнале нет ручек — ответ из описания; в ответе время не из сводки.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Пользователь получает ответ за один ход: бэкап баз 1С запускается ежедневно в 02:00, длится столько-то минут, последние запуски успешны или нет — как в журнале.
- Ошибки: «бэкап делается ночью» без времени; вопрос «бэкап какого сервера?»; ответ из описания без ручек; `delegate` web-01 или acc-01.

## Эталон

- Цепочка: `delegate` → srv-1c; агент — `host.sched_jobs` (задание бэкапа, окно — последние дни), `answer`; один запуск; `ask-user` — 0; `answer-user`.
- Итог: время запуска и результаты запусков — из сводки.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-no-delegation`, `orch-agent-choice`, `local-handle-choice`. Узлы — `orchestrator/delegated/06`, `report/05`, `local/handle-choice/04`, `answer-from-return/03`.

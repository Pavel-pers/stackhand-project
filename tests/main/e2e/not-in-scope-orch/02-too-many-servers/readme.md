# main/e2e/not-in-scope-orch/02 — запрос относится к слишком большому числу серверов

Сценарий плана: **MR-2c** — Не в скоупе оркестратора — запрос относится к слишком большому числу серверов (> 15). Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-2c. Правило «один запрос — один сервер» снято [UC-26], оркестратор опрашивает агентов по очереди — но не больше 15 за сессию [AR-32]. Запрос, которому нужны данные со всех 20 серверов кафе, должен получить отказ с объяснением — не 15 запусков и ответ «по первым 15» и не отказ «по одному серверу». Порог «> 15» — транскрипт плана; в документах как правило отказа не записан [Q54] (файл-обращение).

Две сессии:
1. «Сравни заполненность дисков во всех кафе».
2. «На всех серверах кафе проверь, что ночной бэкап отработал».

## Стенд

Стенд K-20 — сеть из 20 кафе (расширение стенда K для лимита «слишком много серверов»): office-01 и cafe-01…cafe-20 (10.30.1.10…10.30.20.10) засеяны записями о серверах с адресами в кратком описании; логгеры не установлены — тесты на этом стенде до агентов не доходят. Документ контекста — `main/README.md`, раздел «Стенд K-20».

Логгеры на стенде K-20 не установлены — тест до агентов дойти не должен; если дошёл, запуски завершатся ошибкой ручек (это тоже разрыв).

## Вход

Два запроса — два такта в двух сессиях.

## Цепочка

Цепочка короткая — пользователь → оркестратор → пользователь, без агентов. Проверяется, что она действительно короткая: в журнале нет `delegate`, ни одной ручки, на серверах ничего не произошло.
- В отказе — объяснение (слишком много серверов для одного запроса) и предложение сузить запрос `[предл.]`.
- Признаки разрыва: 15 `delegate` и ответ по части серверов; хотя бы один `delegate`; отказ «по одному серверу за раз»; отказ без объяснения.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- `reject` в обеих сессиях: запрос затрагивает 20 серверов, за один запрос система опрашивает не больше 15; предложено назвать кафе или группу.
- Ни одного запуска агента; состояние стенда не изменилось.
- Ошибки: запуски агентов; «по первым 15»; «по одному серверу за раз».

## Эталон

- Цепочка: `reject` ×2; `delegate` — 0.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- доп. рубрика `judge-orch-refusal` `[предл.]` по тексту отказа — без инструкций и команд для изменений, без имитации выполнения, без имён ручек и без «можно добавить» [UC-25], причина понятна.
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-not-in-scope`. Узел — `orchestrator/not-in-scope/03`.

## Основания

Транскрипт плана, пункт 2 («запрос относится к слишком большому количеству серверов (в нашем случае больше 15)»); [UC-26], [AR-32], [Q54].

## Данные

Живой стенд K-20 (`main/README.md`, раздел «Стенд K-20»), два запроса, эталон. Фактические числа берутся из журнала прогона (сводки ручек), не из этого описания.

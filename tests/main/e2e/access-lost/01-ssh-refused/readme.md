# main/e2e/access-lost/01 — сервер перестал принимать ключ / не отвечает

Сценарий плана: **MR-6** — Доступ к серверу потерялся — несколько попыток, затем ответ пользователю с возможными причинами через оркестратор. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-6: доступ к серверу потерялся — несколько попыток, затем ответ пользователю с возможными причинами; e2e проверяет передачу информации пользователю с оркестратором в качестве посредника [UC-27]. После добавления ключ системы удалили с srv-1c (вариант A) или порт 22 закрыт (вариант B). Проверяется эскалация по цепочке: ошибка ручки `ssh-refused` → эскалация агента → вопрос оркестратора пользователю с верной сутью — не выдуманные данные и не «сервер выключен» в варианте A; после восстановления доступа система работает штатно без перезапуска.

1. Засев: A — ключ системы удалён из authorized_keys учётки подключения на srv-1c; B — на srv-1c правилом nftables отбрасываются входящие пакеты на порт 22 с адреса системы (откуда именно — [Q12]).
2. Запрос: «Посмотри заполненность дисков на сервере с 1С» → цепочка до вопроса пользователю; такт закончен.

После теста доступ восстанавливается; что система после этого работает штатно без перезапуска, проверяется отдельным прогоном `info/05` на восстановленном стенде (отдельный такт, в этом тесте не описывается).

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Засев — шаг 1 (A — ключ, B — правило nftables на srv-1c); восстановление после теста.

## Вход

Запрос шага 2. Такт заканчивается вопросом пользователю (`ask-user`); ответ пользователя не подаётся — он не нужен для проверки.

## Цепочка

- Пользователь → оркестратор → агент srv-1c: штатный `delegate` запроса о дисках.
- Ручка → агент: `ssh-refused` — ключ отклонён, сервер отвечает (A) или таймаут после N попыток (B); агент `escalate(error)` с сутью по пути ошибки.
- Оркестратор → пользователь: `ask-user` (ситуация C): A — сервер на связи, но не принял ключ, нужен рабочий доступ; B — сервер не ответил после N попыток, возможные причины, другой доступ или повторить позже. Данных по дискам нет.
- Признаки разрыва: в A сказано «не отвечает», в B — «ключ не подходит» (путь ошибки потерян между агентом и оркестратором); данные по дискам из полного описания; `delegate` другому серверу; команды (`ssh-copy-id`) пользователю.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- A: пользователь получает вопрос — srv-1c на связи, но не принял ключ доступа; данных нет; просьба указать рабочий доступ. Без чисел по дискам; без «сервер выключен» и «недоступен по сети»; без команд.
- B: по образцу контракта — «srv-1c не ответил по SSH после N попыток. Возможные причины: выключен, изменён allow-list, сменился адрес. Укажите другой доступ или повторите позже».
- Ошибки: данные по дискам из описания; `delegate` другому серверу; в A — «не отвечает», в B — «ключ не подходит».

## Эталон

- Цепочка: `delegate` → srv-1c; ручка `host.volumes_usage` → `ssh-refused` (A: ключ отклонён; B: таймаут); агент `escalate(error)`; оркестратор `ask-user` C, сервер srv-1c (для A — `[предл.]`, см. `orchestrator/clarify/04`); один запуск; вопросов пользователю — один.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-question` по вопросу пользователю — (1) язык без имён ручек, источников и классов; (2) суть донесена верно; `judge-local-error` по эскалации агента в журнале — путь ошибки назван верно.
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-clarify-C`, `orch-agent-choice`. Узлы — `local/error-formulation/01`, `/03`, `orchestrator/clarify/03–04`.

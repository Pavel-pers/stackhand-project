# main/e2e/host-info/01 — загрузка за сутки и за час (CPU / GPU)

## Сценарий

Пункт плана «Host info (no questions) → CPU/GPU monitor last day, 1h — History». Полный путь на живом стенде: оркестратор → агент → чтение накопленных метрик → отчёт. Сервер ясен из запроса — уточняющих вопросов быть не должно.

Три отдельные сессии (история между сессиями не переносится [K §2.3]):
1. A — «Какая была загрузка процессора на сервере 1С за последние сутки?»
2. B — «Какая загрузка CPU на srv-1c за последний час?»
3. C (GPU, ждёт решения о метриках GPU) — «Как была загружена видеокарта на сервере распознавания документов за сутки?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, JSON подтверждены, тулкиты пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Засев для C: за 2–3 ч до прогона на acc-01 запущена пачка распознавания документов в acc-ocr, чтобы в окне был пик загрузки GPU.

## Вход

Три запроса A, B, C.

## Ожидаемое поведение

- Уточняющих вопросов нет ни в одной сессии.
- A, B: делегирование srv-1c; агент — `executed`, ручка `host.metrics`, метрика CPU, окно 24 ч (A) или 1 ч (B).
- C: делегирование acc-01; ручка `host.metrics`, метрики GPU, окно 24 ч.
- Отчёт: среднее, пики со временем, период назван; числа — как в возврате в журнале; без имён метрик и ручек.
- Ошибки: вопрос «какой сервер?»; разовая команда «ресурсы сейчас»; окно не то; числа расходятся с журналом; выдуманная причина пика.

## Эталон

- A, B: `delegated` → srv-1c; `executed`, `host.metrics`, окно 24 ч ±15 мин / 1 ч ±5 мин.
- C: `delegated` → acc-01; `executed`, `host.metrics` (gpu), окно 24 ч ±15 мин.
- Вопросов оркестратора — 0.

## Метрики

- Rule-based: `orch-agent-choice`, `local-template-choice`, `local-template-args`, `e2e-expected-state` (rule-based по журналу): классы узлов, `delegate_to`, шаблон и аргументы — как в эталоне; число делегаций — как в эталоне; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` — числа и факты в ответе пользователю совпадают с возвратом шаблона в журнале прогона; причины не выдуманы; период или момент назван; внутренние имена не упомянуты.

## Основания

[K §2.2] «Вопрос по данным, один сервер»; [UC-08]. GPU в документах не упоминается — сессия C считается после решения (README, открытые пункты); пик GPU на стенде — засев теста.

## Данные

Живой стенд M, запрос, эталонные классы, адресат и шаблон, рубрика judge. Фактические числа берутся из журнала прогона (возврат шаблона), не из этого описания.

# main/e2e/what-you-can/02 — «что можно узнать про сервер 1С?»: сторона агента

## Сценарий

Пункт плана «What you can → Local side». Что можно спросить о конкретном сервере, зависит от тулкитов его тегов — перечень даёт агент сервера.

Запрос: «Что можно узнать про сервер 1С?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, JSON подтверждены, тулкиты пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

## Вход

Запрос.

## Ожидаемое поведение

- Делегирование srv-1c; агент перечисляет возможности по манифестам тулкитов host, 1c, db, web; шаблонов не выполняет.
- Ответ пользователю: сгруппированный перечень — нагрузка и место, службы и процессы, входы, задания и бэкапы, сеансы и журнал 1С, блокировки и бэкапы PostgreSQL, публикация 1С, проверки «прямо сейчас»; только чтение.
- Ошибки: имена источников; пункты вне манифестов (перезапуск, завершение сеанса); перечень только по тулкиту host.

## Эталон

- `delegated` `[предл.]` → srv-1c; шаблонов — 0; класс ответа агента в v0.2 не определён.

## Метрики

- Rule-based: `orch-agent-choice`, `e2e-expected-state` (rule-based по журналу): классы узлов, `delegate_to`, шаблон и аргументы — как в эталоне; число делегаций — как в эталоне; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` — перечень совпадает с манифестами srv-1c на стенде, ничего не добавлено, внутренних имён нет.

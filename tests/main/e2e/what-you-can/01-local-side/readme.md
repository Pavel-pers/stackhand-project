# main/e2e/what-you-can/01 — «что можно узнать про сервер 1С?»: знания агента о своих ручках

Сценарий плана: **MR-8b** — Что умеет модель на конкретном сервере — знания локального агента о своих ручках. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана MR-8b — что умеет модель на конкретном сервере: знания локального агента о его ручках, про которые оркестратор не в курсе. Оркестратор должен дойти до агента и донести перечень до пользователя без потерь и добавлений, на языке действий. Общие возможности системы (MR-8a) — только node-isolate.

Запрос: «Что можно узнать про сервер 1С?»

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

## Вход

Запрос. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор: ответ знает агент сервера (перечень ручек его тегов) → `delegate` srv-1c `[предл.]`.
- Агент: `answer` по перечню ручек без вызова ручек A/B.
- Оркестратор → пользователь: перечень человеческими словами, сгруппированный, без имён ручек; ничего сверх перечня агента.
- Признаки разрыва: ответ оркестратора из общего перечня «что умею» без агента (пропущены 1С и СУБД); агент вызвал ручки «для примера»; в ответе пункты, которых нет у агента; имена ручек.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Ответ пользователю: сгруппированный перечень — нагрузка и место, службы и процессы, входы, задания и бэкапы, сеансы и журнал 1С, блокировки и бэкапы PostgreSQL, публикация 1С, проверки «прямо сейчас»; только чтение.
- Ошибки: имена ручек; пункты вне перечня (перезапуск, завершение сеанса); перечень только по host.

## Эталон

- Цепочка: `delegate` `[предл.]` → srv-1c; ручек A/B — 0; агент `answer`; один запуск; `ask-user` — 0; `answer-user`.
- Итог: перечень = перечень ручек srv-1c на стенде.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` — перечень совпадает с перечнем ручек srv-1c на стенде, ничего не добавлено, имён ручек нет [UC-22].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice`. Узлы — `orchestrator/delegated/08`, `report/11`, `local/answer-from-return/06`.

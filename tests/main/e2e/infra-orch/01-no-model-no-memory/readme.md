# main/e2e/infra-orch/01 — сбой на стороне оркестратора: нет модели, нет памяти

## Сценарий

Пункт плана «Infra orch → No memo ← no model». Ломается не сервер, а сама система: инстанс модели недоступен или ему не хватает памяти. Пользователь должен получить короткий статический ответ, а не зависание, не выдуманный ответ и не действия на серверах. Пункт плана прочитан так: «нет памяти» — нехватка памяти GPU, «нет модели» — модель недоступна; вариант D закрывает второе прочтение — недоступна память системы о серверах.

Варианты (каждый — отдельный прогон):
- A — служба Ollama остановлена;
- B — модель не загружена или удалена (вызов возвращает «model not found»);
- C — памяти GPU не хватает: видеопамять занята посторонним процессом, модель не загружается (out of memory);
- D — недоступно хранилище описаний серверов (документ контекста не читается).

Запрос в каждом варианте: «Посмотри заполненность дисков на сервере с 1С». Затем сбой устраняется и запрос повторяется в новой сессии.

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, JSON подтверждены, тулкиты пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

Засев — по варианту, на машине инференса (A–C) или хранилища системы (D); после прогона — восстановление.

## Вход

Запрос в состоянии сбоя; тот же запрос после восстановления.

## Ожидаемое поведение

- В состоянии сбоя: пользователь за ограниченное время получает статический ответ — система временно не может ответить, повторите позже `[предл.]`; ответ не сгенерирован моделью.
- Делегаций агентам и выполнения шаблонов нет; на серверах ничего не происходит.
- В варианте D система не отвечает «у вас нет серверов» и не просит добавить серверы.
- Сбой записан в журнал `[предл.]`.
- После восстановления: штатный ответ по дискам, как в host-info/04.
- Ошибки: зависание без ответа; трейс исключения пользователю; выдуманные числа; сообщение о пустом списке серверов; после восстановления система не отвечает без ручного перезапуска.

## Эталон

- В сбое: статический ответ за время ≤ 30 с `[предл.]`; делегаций — 0; шаблонов — 0.
- После восстановления: `delegated` → srv-1c; `executed`, `host.volumes`.

## Метрики

- Rule-based `[предл.]` — вне метрик v0.2: статический ответ получен в пределах времени; делегаций и шаблонов нет; после восстановления — `e2e-expected-state` (rule-based по журналу): классы узлов, `delegate_to`, шаблон и аргументы — как в эталоне; число делегаций — как в эталоне; состояние стенда после прогона не изменилось — система только читает [UC-06].
- SLI «прогон до конца без падений» [D §3.5]: прогоны в сбое считаются падениями системы — это вклад в SLI, а не провал теста.

## Основания

[D §5.4] — статический ответ при инфраструктурном сбое; [D §3.5] — SLI; падение инференса и механизм восстановления не обсуждались (`architecture/overview.md`, `llm-inference.md`). Порог 30 с — по бюджету TTFT P95 [D §3.2], его переназначение после отмены карточки — [Q22].

## Данные

Живой стенд M, запрос, эталонные классы, адресат и шаблон, рубрика judge. Фактические числа берутся из журнала прогона (возврат шаблона), не из этого описания.

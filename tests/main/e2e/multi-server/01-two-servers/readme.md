# main/e2e/multi-server/01 — запрос по двум серверам: последовательные запуски

Сценарий плана: **X-MULTI** — Несколько серверов в одном запросе — последовательные запуски агентов [UC-26], [AR-27]. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Вне плана (X-MULTI): правило «один запрос — один сервер» снято [UC-26]; оркестратор опрашивает агентов по очереди [AR-27] и сводит ответ. Проверяется, что два названных сервера дают два последовательных запуска (не отказ и не вопрос) и один ответ со сравнением, в котором числа не перепутаны между серверами.

Запрос: «Сравни свободное место на srv-1c и на сервере сайта».

## Стенд

Стенд M (подробно — `main/README.md`, раздел «Стенд M»): web-01 10.0.1.11 (VPS у хостера: nginx, PHP, MariaDB, импорт прайса из 1С раз в час), srv-1c 10.0.1.12 (1С 8.3 кластер + PostgreSQL 16, публикация 1С на 8080, pg_dump в 02:00), acc-01 10.0.1.13 (Docker: acc-api, acc-worker, acc-ocr на GPU T4, redis, postgres), gw-01 10.0.1.1 (WireGuard до склада и до web-01); все Ubuntu 22.04.4, доступ системы по SSH ключом. Серверы добавлены через форму, записи подтверждены, логгеры пишут данные не меньше 24 ч до прогона. Документ контекста оркестратора — как в `main/README.md`. Состояние стенда перед тестом — снапшот; сброс после теста.

## Вход

Запрос. Такт один: запрос пользователя → … → терминальная тулза оркестратора; действий пользователя внутри нет.

## Цепочка

- Пользователь → оркестратор: оба сервера названы → `delegate` первому (srv-1c или web-01) с запросом о свободном месте.
- Агент 1: `host.volumes_usage`, `answer`; оркестратор → `delegate` второму (память агента новая, запрос тот же по сути); агент 2: `host.volumes_usage`, `answer`.
- Оркестратор → пользователь: один ответ — по каждому серверу самый заполненный том, свободно, прогноз; вывод, какой требует внимания; период и источник.
- Признаки разрыва: `reject` «по одному серверу за раз»; `ask-user` «какой сервер?»; один запуск и ответ по одному серверу; числа перепутаны между серверами; третий `delegate` без нужды.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Пользователь получает за один ход сравнение двух серверов с числами из сводок обоих агентов; вывод о том, где место кончается раньше.
- Ошибки: отказ; вопрос; ответ по одному серверу; перепутанные числа.

## Эталон

- Цепочка: `delegate` → {srv-1c, web-01} в любом порядке, два запуска, в каждом `host.volumes_usage` и `answer`; `ask-user` — 0; `answer-user`; `delegate` ≤ 2.
- Итог: числа по каждому серверу — из его сводки.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу прогона и состоянию стенда): цепочка — тулзы оркестратора и ручки агентов вызваны в ожидаемом порядке и числе, `delegate_to` и обязательные ручки как в эталоне, вопросов пользователю ровно столько, сколько в эталоне, лимиты не превышены [AR-32]; состояние стенда после прогона не изменилось — система только читает [UC-06].
- LLM-judge: `judge-orch-report` по итоговому тексту пользователю — числа и факты совпадают со сводками ручек в журнале прогона; причины не выдуманы; период или момент данных назван; источники названы понятным языком, имена ручек, команд и классов не названы [UC-22].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice` (оба адресата), `local-handle-choice`. Узлы — `orchestrator/delegated/14`, `report/16`.

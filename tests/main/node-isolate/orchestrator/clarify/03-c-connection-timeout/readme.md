## Сценарий

## Вход

Транскрипт сессии (оркестратор перезапущен с ним [AR-28]):

- Пользователь: «посмотри заполненность дисков на сервере с 1С»
- Оркестратор: `delegate(srv-1c, «Заполненность всех томов и прогноз, когда закончится место»)`
- Агент srv-1c: `escalate(error)` — `ssh-refused` — «ssh: connect to host 10.0.1.12 port 22: Connection timed out; попыток 2 с паузой 5 с. Следующее действие: эскалировать оркестратору — сервер не отвечает, возможные причины: выключен, изменён allow-list, сменился адрес». Формулировка агента: «srv-1c не ответил по SSH после 2 попыток (таймаут); возможные причины — выключен, изменён allow-list, сменился адрес»

## Ожидаемое поведение

- `ask-user` (`clarify`), ситуация C; поля — сервер srv-1c и причины.
- Сообщение по образцу контракта: «srv-1c не ответил по SSH после 2 попыток. Возможные причины: выключен, изменён allow-list, сменился адрес. Укажите другой доступ или повторите позже».
- Пометка «гипотеза» не нужна — причины подаются как возможные [UC-13]; «сервер выключен» как установленный факт — ошибка.
- Без трейса и кода ошибки, если не просили.
- Ошибки: данные по дискам; повторный `delegate` другому серверу; `reject`; ответ без следующего шага для пользователя.

## Эталон

- Тулза: `ask-user` (`clarify`); ситуация: C; сервер: srv-1c.
- Причины (сверяет judge, не rule-based): выключен, изменён allow-list, сменился адрес.

## Метрики

- Rule-based: `orch-clarify-C` — класс, ситуация и сервер совпадают с эталоном; причины — свободный текст, их проверяет judge.
- LLM-judge: `judge-orch-question` — (1) язык понятен пользователю: нет имён ручек, источников как идентификаторов, классов, тегов как идентификаторов (теги в скобках рядом с описанием, как в примере контракта [K §2.2], допустимы); (2) суть донесена верно. Засчитан при обоих.

## Основания

Исключение «сервер не отвечает» [K §2.2], [UC-13], [UC-17], [UC-27] — пользователю сообщает оркестратор; [AR-25] — `ssh-refused` → эскалация; ситуация C [M]; 2 попытки с паузой 5 с [AR-42] (design doc 2.2). Выбор между `ask-user` и `reject` при недоступности — [Q38]; эталон `ask-user` по образцу контракта («укажите другой доступ»).

# e2e/03 — авторизации на сервере 1С по auth.log

## Сценарий

Полный путь на живом стенде, все узлы настоящие.

1. Оркестратор выбирает агента srv-1c и ставит задачу про входы за сутки.
2. Агент выбирает auth-events (источник /var/log/auth.log), карточка, подтверждение.
3. Агент читает auth.log за сутки и lastb, разбирает успешные и неудачные входы.
4. Оркестратор отвечает списком успешных входов и счётчиком неудачных по адресам.

## Стенд

«Конфигурация C + VPN-шлюз», все хосты Ubuntu 22.04 (есть /var/log/auth.log из коробки), доступ evalbot по SSH с ограниченным sudo:
web-01 (10.0.1.11, nginx + PHP + MariaDB), srv-1c (10.0.1.12, 1С-сервер 8.3 + PostgreSQL 16), acc-01 (10.0.1.13, Docker: acc-api, acc-worker, redis, postgres), gw-01 (10.0.1.1, WireGuard wg0, peer warehouse 10.20.0.0/24).

## Вход

Запрос пользователя: «какие авторизации были на сервере с 1С за сутки».

## Ожидаемое поведение

- В журнале: делегирование агенту srv-1c, выбранный шаблон auth-events, режим — чтение.
- Состояние стенда после прогона не изменилось (шаблон только читает).
- В отчёте успешные входы с пользователем, адресом и временем и неудачные счётчиком по адресу — как в журнале; период — сутки; IP-адреса не искажены.
- Ошибки: ответ списком пользователей 1С из контекста; шаблон log-errors; потерянные неудачные попытки.

## Метрики

- Rule-based: `journal-template-match` (шаблон из журнала равен auth-events), `agent-choice-correct` (адресат — srv-1c), `false-refusal`.
- LLM-judge: `judge-B-agent-to-user` — ответ пользователю опирается на числа из выхлопа шаблона в журнале, ничего не выдумано.

## Данные

Живой стенд по описанию выше, запрос пользователя, эталонные адресат и шаблон, рубрика judge; фактические числа берутся из журнала прогона.

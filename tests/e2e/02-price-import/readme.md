# e2e/02 — импорт прайса из 1С на сайт

## Сценарий

Полный путь на живом стенде, все узлы настоящие.

1. Оркестратор по контексту (сайт получает выгрузку прайса из 1С) выбирает агента web-01, а не srv-1c, хотя в запросе упомянута 1С.
2. Агент выбирает «планировщик» для задания импорта прайса, карточка, подтверждение.
3. Агент читает crontab, syslog и журнал задания, разбирает последние запуски и их коды.
4. Оркестратор отвечает: когда импорт отработал последний раз успешно, что с тех пор, гипотеза о причине — как гипотеза.

## Стенд

«Конфигурация C + VPN-шлюз», все хосты Ubuntu 22.04 (есть /var/log/auth.log из коробки), доступ evalbot по SSH с ограниченным sudo:
web-01 (10.0.1.11, nginx + PHP + MariaDB), srv-1c (10.0.1.12, 1С-сервер 8.3 + PostgreSQL 16), acc-01 (10.0.1.13, Docker: acc-api, acc-worker, redis, postgres), gw-01 (10.0.1.1, WireGuard wg0, peer warehouse 10.20.0.0/24).

## Вход

Запрос пользователя: «прайс на сайте вчерашний — выгрузка из 1С отработала?».

## Ожидаемое поведение

- В журнале: делегирование агенту web-01, выбранный шаблон scheduler, режим — чтение.
- Состояние стенда после прогона не изменилось (шаблон только читает).
- В отчёте время последнего успешного запуска и коды последних запусков совпадают с журналом; при неудачных запусках приведён текст ошибки из журнала задания; причина подана как гипотеза.
- Ошибки: делегирование srv-1c; шаблон log-errors; «всё в порядке» при неудачных запусках; причина, поданная как факт.

## Метрики

- Rule-based: `journal-template-match` (шаблон из журнала равен scheduler), `agent-choice-correct` (адресат — web-01), `false-refusal`.
- LLM-judge: `judge-B-agent-to-user` — ответ пользователю опирается на числа из выхлопа шаблона в журнале, ничего не выдумано.

## Данные

Живой стенд по описанию выше, запрос пользователя, эталонные адресат и шаблон, рубрика judge; фактические числа берутся из журнала прогона.

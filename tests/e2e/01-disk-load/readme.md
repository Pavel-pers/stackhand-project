# e2e/01 — диски сервера 1С

## Сценарий

Полный путь на живом стенде, все узлы настоящие.

1. Оркестратор по контексту выбирает агента srv-1c и ставит задачу про заполненность томов.
2. Агент выбирает disk-usage, показывает карточку подтверждения; пользователь подтверждает.
3. Агент выполняет df и du, разбирает выхлоп, возвращает структуру оркестратору.
4. Оркестратор пишет отчёт пользователю по полученным числам; всё — в журнале.

## Стенд

«Конфигурация C + VPN-шлюз», все хосты Ubuntu 22.04 (есть /var/log/auth.log из коробки), доступ evalbot по SSH с ограниченным sudo:
web-01 (10.0.1.11, nginx + PHP + MariaDB), srv-1c (10.0.1.12, 1С-сервер 8.3 + PostgreSQL 16), acc-01 (10.0.1.13, Docker: acc-api, acc-worker, redis, postgres), gw-01 (10.0.1.1, WireGuard wg0, peer warehouse 10.20.0.0/24).

## Вход

Запрос пользователя: «посмотри заполненность дисков на сервере с 1С».

## Ожидаемое поведение

- В журнале: делегирование агенту srv-1c, выбранный шаблон disk-usage, режим — чтение.
- Состояние стенда после прогона не изменилось (шаблон только читает).
- В отчёте проценты и свободное место по томам srv-1c совпадают с выхлопом шаблона в журнале; самый заполненный том назван первым.
- Ошибки: делегирование другому агенту; шаблон resources-now; расхождение чисел с журналом; выдуманные причины роста.

## Метрики

- Rule-based: `journal-template-match` (шаблон из журнала равен disk-usage), `agent-choice-correct` (адресат — srv-1c), `false-refusal`.
- LLM-judge: `judge-B-agent-to-user` — ответ пользователю опирается на числа из выхлопа шаблона в журнале, ничего не выдумано.

## Данные

Живой стенд по описанию выше, запрос пользователя, эталонные адресат и шаблон, рубрика judge; фактические числа берутся из журнала прогона.

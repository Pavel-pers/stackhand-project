# eval-test — golden-набор v0.4

Набор тестов под архитектуру и контракты из `docs/` после постановок 2026-10-26/27 (server-init, server-main-flow, память о серверах, тулзы и лимиты) и под транскрипт плана e2e-тестов от 2026-10-27. Две группы узлов:

| Группа | Узлы | Что проверяет |
|---|---|---|
| `init/` | инспектор, куратор | добавление сервера: форма (`conn-ip`, `conn-ssh-key`, `description`) → инспектор своими ручками по чек-листу → `full-desc`, `tags`, `tags-full-desc` → куратор: `server-name`, `short-desc`, `tags-short-desc`, конфликты, границы → подтверждение краткого описания и названия → запись о сервере [AR-29], [AR-30], [AR-31] |
| `main/` | оркестратор, локальный агент | рабочий запрос: выбор сервера по краткому описанию, тегам и названию, `delegate` → цикл ручек агента (A — сводки по логам, B — one-shot) → `answer`/`escalate` → `answer-user` / `ask-user` / `reject` или ещё один `delegate`; лимиты [AR-23]–[AR-28], [AR-31], [AR-32] |

В каждой группе — `node-isolate/` (узел по отдельности, на фикстурах) и `e2e/` (полный путь на живом стенде); `system/` — системные тесты вне eval-сета. Документы проекта (`docs/`) не менялись. Где документы решения не дают, тест опирается на ближайшее принятое решение и помечает эталон `[предл.]`; места, которые стоит решить в документах, — в разделе «Открытые пункты»; расхождения транскрипта плана с документами — в файле-обращении (`obrashchenie.md` рядом с набором).

## E2E и node-isolate: что где проверяется

По пояснению автора плана: e2e тестирует полную систему — правильно ли взаимодействуют узлы и достаточно ли им контекста, чтобы понять запрос и делегировать его или эскалировать пользователю; то, что проверяет поведение одного узла, остаётся в node-isolate.

- **node-isolate** — узел на фикстурах: вызванная тулза и её поля, выбор ручки и параметры, заполнение полей записи, формулировка вопроса, ошибки или краткого описания. Здесь считаются доли метрик v0.2 по узлам.
- **e2e** — живой стенд и полная цепочка. В каждом e2e-тесте есть раздел «Цепочка»: что каждый узел должен передать следующему, где эскалация должна дойти до пользователя и по каким признакам цепочка считается разорванной. Вердикт — `e2e-expected-state` (цепочка по журналу и состояние стенда) и judge итогового текста пользователю; разрыв в любом звене — тест не засчитан `[предл.]`. Метрики узлов по журналу e2e нужны для локализации разрыва и в доли node-isolate не входят `[предл.]`.
- **Один такт — один прогон.** Везде, где подразумевается взаимодействие с пользователем, один тест — один прогон до следующего действия пользователя (правило автора плана). Многотактовый сценарий — цепочка тестов: такт «вопрос» (от входа до вопроса узла) и такт «обработка ответа» (вопрос или карточка зафиксированы в тесте как начало транскрипта, остальное окружение — живое: `init/e2e/n-server-cafe/01` → `/02` → `/03`, `/05` → `/06`, `1c-site/01` → `/02`, `/03` → `/04` → `/05`, `bad-ssh/02` → `/03`, `rewrite-short-desc/01` → `/03`). Ответ пользователя внутри такта не подаётся; в node-isolate это видно как «история чата зафиксирована в тесте». Исключение — **тест-«итог»** (`n-server-cafe/03`, `/06`, `1c-site/02`, `/05`, `rewrite-short-desc/03`): подтверждение карточки (модель не участвует — запись пишет код) и пробы в новых сессиях описаны одним тестом, хотя это отдельные прогоны; реестр ведёт такой тест как один, при реализации прогон делится на шаги.
- Короткие цепочки (отказ или ответ оркестратора без агента) в e2e проверяются тем, что они действительно короткие: в журнале нет `delegate` и ручек, на серверах ничего не произошло.
- Init e2e, в которых добавление доходит до записи, заканчиваются пробой — рабочим запросом по только что добавленному серверу `[предл.]` (`n-server-cafe/03`, `/06`, `1c-site/02`, `/05`, `rewrite-short-desc/03`): так проверяется, что краткого описания куратора достаточно оркестратору для маршрутизации, а полей инспектора и ручек — агенту для ответа, в том числе того, что пользователь ответил в чате добавления. Поведение узла, которое проба задействует, имеет пару в node-isolate (`orchestrator/delegated/11`, `local/handle-choice/11`, `/03`, `orchestrator/answered/03`).

### Коды сценариев: e2e ↔ node-isolate

Почти любой e2e раскладывается на несколько node-isolate — поэтому у тестов есть кодовое название сценария плана (предложение автора плана, реализовано так):

- В начале readme каждого теста, относящегося к сценарию, строка «Сценарий плана: **КОД** — описание. Вид теста: e2e / node-isolate / системный». Коды: `MR-1a`…`MR-8b` (Main-Run, пункт транскрипта и подпункт; `MR-1e` и `MR-6b` — случаи, которые транскрипт не называет, но пункт покрывает: старые e2e по накопленным данным и потеря доступа к источнику), `IN-1a`…`IN-4` (Init), `X-LIM`, `X-MULTI`, `X-CHK`, `X-FIELDS` (вне плана), `SYS` (вне eval-сета). Полный перечень кодов с описаниями — `SCENARIOS.md`.
- Генератор набора ведёт реестр `_registry.jsonl` (код, путь, вид, звено) и собирает из него `SCENARIOS.md` — таблицу «код → e2e → node-isolate по звеньям → system» — и `scenarios.json` для инструментов прогона. По коду из любого readme находится и e2e, и его разложение; по разрыву e2e — какие узловые тесты прогнать для локализации.
- У node-isolate теста есть `step` — звено цепочки (легенда — `SCENARIOS.md`): main — 1 оркестратор (запрос агенту), 2 агент (ручка или эскалация), 3 агент (ответ по сводке), 5 оркестратор (пользователю); init — 1 инспектор, 2 куратор; 9 — проба после добавления. Так в таблице видно, какой узловой тест соответствует какому шагу «Цепочки» e2e.
- Один тест может нести несколько кодов (через запятую); тесты без кода — узловые случаи вне плана.

Что в механизме можно улучшить (предложения, не сделано, чтобы не менять формат readme [EV-01] без решения): (1) перенести код и `step` в `config.yaml` теста, когда его формат решат [Q40] — тогда прогон сможет фильтровать по коду (`--scenario MR-3`) и строить отчёт «e2e упал → какие узловые тесты того же кода красные»; (2) фиксировать в реестре не только путь, но и используемые фикстуры — чтобы узловые тесты одного кода гарантированно делили одни и те же сводки и транскрипты (сейчас это держится на общих константах генератора); (3) добавить в `e2e-expected-state` ожидаемую «трассу» в терминах кодов звеньев и сверять её с журналом автоматически; (4) завести коды для обязательных исключений контракта [UC-17] (сейчас они в таблице README), чтобы один реестр покрывал и план, и контракт.

## Формат теста

Каждый тест — листовая директория с `readme.md` [EV-01]. Разделы: «Сценарий» (что проверяется и почему, шаги), «Контекст узла» или «Стенд», «Вход», в e2e — «Цепочка» (ожидаемое взаимодействие узлов и признаки разрыва), «Ожидаемое поведение» (включая перечень ошибок), «Эталон» (то, с чем rule-based сравнивает ответ узла или журнал), «Метрики», «Основания» (решения и открытые вопросы из `docs/`), «Данные» (что нужно для реализации).

`config.yaml` и `fixtures/` [EV-01] не созданы: их формат не обсуждался (`evaluation/eval-set.md`). Фикстуры — результаты ручек инспектора, сводки и ошибки ручек агента, ответы агентов, транскрипты — приведены в readme и переносятся в `fixtures/` после решения о формате.

Пометки: `[UC-nn]`, `[AR-nn]`, `[EV-nn]` — решения из `decisions.md` осей; `[K §x]`, `[M]`, `[T §x]`, `[D §x]` — источники по легенде `docs/README.md`; `[Qnn]` — открытый вопрос; `[предл.]` — эталон, предложенный авторами тестов там, где решения нет.

## Классы ответов и тулзы узлов

Классы — из метрик v0.2 [AR-15], [M]; по постановке тулз 2026-10-27 класс оркестратора = имя вызванной тулзы [AR-31]; пользователь классов не видит [AR-28].

| Узел | Тулзы [AR-31] и лимиты [AR-32] | Класс v0.2 | Поля, которые сравниваются |
|---|---|---|---|
| оркестратор | `delegate(server-name, prompt)` ≤ 15; `ask-user` ≤ 7; `answer-user` + `reject` ≤ 3 (третий закрывает чат [UC-28]) | `delegated`, `clarify` (ситуации A/B/C задаёт тест), `answered`, `not_in_scope` | `delegate_to`, prompt; варианты серверов (A); сервер и причины (C) |
| локальный агент | ручки A и B ≤ 20 на запуск; терминальные `answer`, `escalate(no_template / wrong_addressee / error / ambiguous)` — виды `error` и `ambiguous` (подходят несколько ручек, нужен ответ пользователя — ситуация B) предложены тестами | `executed`, `no_template`, `wrong_addressee`; схема эскалации — [Q37] | ручка (ручки — [Q55]) и параметры |
| инспектор | ручки осмотра ≤ 40; `ask-user` ≤ 10; `submit(full-desc, tags, tags-full-desc)` терминальна | `filled`, `clarify` | `tags` (множество), чек-листы `full-desc` и `tags-full-desc`; поле, по которому вопрос |
| куратор | `QA` ≤ 5; `confirmation(short-desc, server-name)` ≤ 3; `deny` терминальна | `conflict` (→ `QA`), `consistent` (→ `confirmation`) `[предл.]`; `deny` класса не имеет [Q50] | набор серверов в конфликте; `server-name`, `short-desc`, `tags-short-desc` и их лимиты |

«Класс итогового сообщения» оркестратора после ответа агента = вызванная тулза (`answer-user` → `answered`), хотя в M `answered` — «ответ без делегации» (открытые пункты, п. 1).

Правила сравнения: подстроки в эталонах («содержит «1С»», «не содержит «парол»») — без учёта регистра; латинская C и кириллическая С в «1С» — одна буква; ё = е; условия со «и» и «или» читаются по скобкам. Лимиты слов [AR-29]: слово — последовательность непробельных символов, имена тегов в `tags-short-desc` перед тире не считаются.

LLM-judge выносит вердикт по каждому критерию метрики; тест засчитан, когда выполнены все [M]. Критерий отчёта «все числа и факты агента перенесены точно» тесты читают так `[предл.]`: обязательные числа перечислены в «Эталоне» и должны быть в ответе; любое другое число из ответа агента, если оно попало в ответ, должно совпадать.

Вне долей v0.2: `e2e-expected-state` — «доля сценариев, доведённых до ожидаемого состояния стенда» [D §3.1], содержание расширено тестами `[предл.]` (цепочка тулз и ручек по журналу, число вопросов, лимиты, неизменность стенда; для init — запись о сервере и логгеры); rule-based проверки тестов `limits/*` (терминальная тулза после отказа системы, [Q60]); системные тесты `system/*`.

## Каталог ручек, ошибки, чек-лист — предложения тестов

Ручки агента (тип A — сводки по логам с параметрами, тип B — one-shot [AR-24]), ошибки-enum [AR-25], ручки и чек-лист инспектора [AR-30] в документах составом не заданы ([Q08], [Q20], [Q58]). Тесты используют условный каталог (`main/README.md` — ручки агента и ошибки; `init/README.md` — ручки и чек-лист инспектора): имена и параметры заменяются настоящими при появлении манифестов; эталоны `local-handle-choice` сравнивают имя ручки, `local-handle-args` — обязательные параметры. ## Прогон

По `evaluation/procedure.md`: одна модификация — один прогон; каждый тест ~5 раз при temperature > 0; rule-based — доля по классу, judge — доля тестов, где выполнены все критерии; падение любой доли — откат модификации [EV-03].

- Варианты внутри теста (A, B, C…) — наблюдения одного теста: тест засчитан, когда засчитаны все его варианты `[предл.]`.

- Системные тесты `system/*` в eval-сет не входят (транскрипт плана, Init-5).
- Целевые значения метрик v0.2 не назначены [Q22].

## Открытые пункты, всплывшие при написании тестов

Документы не правились; ниже — места, где тестам пришлось принять эталон без решения. Расхождения транскрипта плана с документами — отдельно в файле-обращении.

**Классы, тулзы, эталоны**

1. **Итоговый ответ оркестратора после агента** — класс = тулза `answer-user` (`answered`), хотя в M `answered` — «ответ без делегации»; rule-based по классу в `report/*` не считается, только judge.
2. **Ответ агента без вызова ручек** (перечень возможностей по серверу) — класса нет [Q37]: `local/answer-from-return/06`, `orchestrator/report/11`, `main/e2e/what-you-can/01`. **Вид эскалации `ambiguous`** `[предл.]` для ситуации B (подходят несколько ручек) — чтобы оркестратор отличал её от `no_template` структурно, а не по тексту (`orchestrator/clarify/05`).
3. **«Нет данных за окно» и «GPU нет» на стороне агента** — эталон `answer` после ошибки `no-data-for-period` / `host.now_inventory` `[предл.]`; `no_template` для GPU ввёл бы в заблуждение. На стороне оркестратора «нет данных» — `answer-user` или `reject` (оба засчитываются).
4. **Запрос о сервере вне списка** (и об удалённом) — эталон `reject` `[предл.]` (транскрипт плана: отказ).
5. **Отказ «слишком много серверов»** — порог > 15 из транскрипта; в документах правила нет [Q54]; порог считается по запросу до первого `delegate` (`limits/01` исчерпывает лимит повторным запуском, не числом серверов). `multi-server/01` проверяет механизм последовательных запусков [UC-26]; как это обещано пользователю в контракте — не записано.
6. **Отклонённый ключ — ситуация C** `[предл.]`; ошибка ручки, где от пользователя ничего не нужно (`source-unavailable`), — ответ, не вопрос.
7. **Инспектор не может подключиться** — отказ с просьбой заполнить форму заново (транскрипт); терминальной тулзы отказа у инспектора нет [AR-31] — механизм `[предл.]` через `ask-user` и закрытие сессии системой; в долю `insp-clarify` не входит (`insp-refusal` вне долей v0.2).
8. **«Расскажи про сервер»** — эталон `answer-user` из краткого описания `[предл.]`; альтернатива — `delegate`.
9. **«Слишком похожие» описания** [Q33] — эталоны пограничных случаев: общая часть описаний кафе без адреса — `conflict` (план); та же улица без дома — `conflict`, с домом — `consistent`; те же теги при разном назначении — `consistent`; неинформативная форма при информативном `full-desc` — `consistent` `[предл.]`.
10. **Политика оркестратора по эскалациям** [Q38]: `no_template` → `reject` с перечнем; `wrong_addressee` → `delegate` другому серверу; `ssh-refused` → `ask-user` C; неоднозначный выбор ручки → `ask-user` B — эталоны тестов.
11. **Эталон для цепочек** [Q55]: `local-handle-choice` — обязательные ручки вызваны, лишних нет; `orch-agent-choice` — каждый адресат; допустимые дополнительные ручки перечислены в тесте.

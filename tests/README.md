# eval-test — golden-набор v0.2

Набор тестов под архитектуру и контракты v0.2 из `docs/` (дерево документов от 2026-10-25). Вместо прежней схемы «инициализация + оркестратор + серверный агент» — две группы узлов:

| Группа | Узлы | Что проверяет |
|---|---|---|
| `init/` | инспектор, куратор | добавление сервера: форма → осмотр и вопросы по системе → название, краткое описание и конфликты → подтверждение JSON; удаление и повторное добавление |
| `main/` | оркестратор, локальный агент | рабочий запрос: маршрутизация по тегам и краткому описанию, постановка задачи, выбор ручки или разовой команды, ответ по возврату шаблона, отчёт, отказы и уточнения |

В каждой группе — `node-isolate/` (узел по отдельности, на фикстурах) и `e2e/` (полный путь на живом стенде). E2E-тесты собраны по плану «E2E Server Init» и «E2E Main-Run» (скриншоты); node-isolate — обновлённые старые тесты и узловые проверки тех же пунктов плана.

Документы проекта (`docs/`) не менялись. Где документы решения не дают, тест опирается на ближайшее принятое решение и помечает эталон `[предл.]`; все такие места собраны в разделе «Открытые пункты».

## Структура

```
tests/
  README.md
  init/
    README.md                     — стенд I, формы, эталонные описания серверов
    node-isolate/
      inspector/{filled,clarify,answer-processing}/
      curator/{consistent,conflict,answer-processing}/
    e2e/{difference,1c-site,not-ssh,rewrite,delete}/
  main/
    README.md                     — стенд M, документ контекста, полные описания, манифесты, засевы
    node-isolate/

         template-mismatch,infra-local,infra-orch,what-you-can,server-info}/
```

Директории node-isolate названы по ожидаемому результату узла (класс ответа или проверяемая метрика), e2e — по пунктам плана.

## Формат теста

Каждый тест — листовая директория с `readme.md` [EV-01]. Разделы: «Сценарий» (что проверяется и почему, шаги), «Контекст узла» или «Стенд», «Вход», «Ожидаемое поведение» (включая перечень ошибок), «Эталон» (то, с чем rule-based сравнивает ответ узла), «Метрики», «Основания» (решения и открытые вопросы из `docs/`), «Данные» (что нужно для реализации).

`config.yaml` и `fixtures/` [EV-01] не созданы: их формат не обсуждался (`evaluation/eval-set.md`, «Не обсуждалось»). Фикстуры — инвентарь осмотра, возвраты шаблонов, ответы агентов — приведены в readme и переносятся в `fixtures/` после решения о формате.

Пометки: `[UC-nn]`, `[AR-nn]`, `[EV-nn]` — решения из `decisions.md` осей; `[K §x]`, `[M]`, `[T §x]`, `[D §x]` — источники по легенде `docs/README.md`; `[Qnn]` — открытый вопрос; `[предл.]` — эталон, предложенный авторами тестов там, где решения нет.

## Эталон выбора шаблона до решения [Q02] и [Q08]

Каталога шаблонов нет [Q08], форма ручек чтения логов не выбрана [Q02]. Поэтому эталон `template_id` в тестах записан так:

- ручка чтения логов — идентификатором источника тулкита: `host.metrics`, `host.volumes`, `host.sched`, `host.auth`, `1c.sessions`… (имена — из tag-system [T §5] в пересказе `architecture/`); `local-template-choice` сравнивает источник;
- разовая команда — видом: X01 «внеплановая инвентаризация», «ресурсы сейчас», «размер пути», «выборка журнала» [K §2.1 Вход 3], [T §5]; сравнивается вид.

Допуски аргументов — предложение тестов до [Q18]: окно «последние сутки» — ±15 мин по границам, «последний час» — ±5 мин, месяц — границы месяца с учётом пересчёта в UTC, окно роста томов — не короче 14 суток. Выдержки манифестов в контексте агента составлены для тестов (`main/README.md`) и заменяются настоящими манифестами, когда они появятся [Q04].

## Стенды

- **Стенд M** (`main/`) — четыре сервера ООО «Тестовая компания»: web-01 (сайт на VPS у хостера), srv-1c (1С + PostgreSQL), acc-01 (Docker-микросервисы, GPU), gw-01 (WireGuard-шлюз); все Ubuntu 22.04.4, подключение по SSH. Подробно — `main/README.md`.
- **Стенд I** (`init/`) — те же хосты до добавления плюс srv-1c-2 (копия 1С для франчайзи) и win-01 (Windows без SSH). Подробно — `init/README.md`.
- Фикстуры node-isolate: момент запроса — 2026-10-27 10:00 (+03:00), данные тулкитов — с 2026-10-08 14:20.
- Состав стенда, сидирование и сброс не обсуждались [Q39] — стенды предложены тестами. Отличия от стенда v0.1 «C + VPN-шлюз»: теги — из каталога первой волны (`host`, `1c/cluster`, `db/pg`, `web/nginx`…) вместо свободных (`linux`, `website`, `critical`…); web-01 — VPS у хостера, чтобы покрыть обязательное исключение «не поддерживается» (`unsupported:provider-hv` [T §6, §7]); у acc-01 — GPU T4 для пункта плана «CPU/GPU».

## Прогон

По `evaluation/procedure.md`: одна модификация (шаблоны, промпты, модель) — один прогон; каждый тест ~5 раз при temperature > 0; rule-based — доля по классу, judge — доля тестов, где выполнены все критерии; падение любой доли относительно предыдущего прогона — откат модификации [EV-03].

- Варианты внутри теста (A, B, C…) — наблюдения одного теста: тест засчитан, когда засчитаны все его варианты `[предл.]`.
- Тесты и варианты, зависящие от метрик GPU, имеют статус «ждёт решения» и в доли не входят до решения (открытые пункты, п. 8).
- Порог «100 %» в main/e2e/routing/02 — из плана; остальные целевые значения для метрик v0.2 не назначены [Q22].

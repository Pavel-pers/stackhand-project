# curator/rewrite/01 — замечания пользователя к краткому описанию и названию на шаге подтверждения

Сценарий плана: **IN-4** — Перезапись краткого описания сервера куратором после возврата инспектора — замечания пользователя; просьбы вне границ — явный отказ. Вид теста: node-isolate. Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана IN-4 на уровне куратора: после возврата инспектора куратор составил `short-desc` и отправил на подтверждение; пользователь на том же шаге пишет замечания по краткому описанию и названию [UC-24]. Куратор переписывает только эти два поля по замечаниям и отправляет повторно (2-я из 3 отправок); теги, `full-desc` и `tags-short-desc` не трогает; отказа нет — замечания в границах.

Остаток: QA 5, confirmation 2.

## Вход

Вариант A — замечание: «назови его „1С бухгалтерии“; в описании напиши, что это основной сервер бухгалтерии и кадров, про бэкап не надо».

Вариант B — замечание: «уберите „около 12 пользователей“ — число людей в описании не нужно; добавьте, что сервер стоит в офисе на Ленинской».

## Ожидаемое поведение

- `confirmation` повторно (`consistent`), без `QA` (замечание однозначно) и без `deny`.
- A: `server-name` — «1С бухгалтерии»; `short-desc` — сервер 1С, основной сервер бухгалтерии и кадров, Бухгалтерия и ЗУП на PostgreSQL; без «ночной бэкап».
- B: `short-desc` — без числа пользователей, с «в офисе на Ленинской»; `server-name` — прежний.
- Теги, `full-desc`, `tags-short-desc` без изменений (в `tags-full-desc` 1c по-прежнему 12 учёток — это находка инспектора, куратор её не правит).
- Ошибки: отправка без изменений; изменение тегов или `tags-short-desc`; `deny` на замечание в границах; `QA` «что именно поменять?» при ясном замечании; название > 4 слов.

## Эталон

- Тулза: `confirmation` (2-я).
- A: `server-name` = «1С бухгалтерии»; `short-desc` содержит «бухгалтер» и «кадр», не содержит «бэкап»; < 50 слов.
- B: `short-desc` содержит «Ленинск», не содержит «12»; `server-name` = «srv-1c».
- `tags`, `tags-short-desc`: без изменений.

## Метрики

- Rule-based: `cur-conflict` — класс (тулза) совпадает с эталоном; при `conflict` — набор серверов совпадает с эталонным.
- Rule-based: `cur-fields` `[предл.]` (X-FIELDS, [AR-29]) — `server-name` непустое, < 5 слов; `short-desc` < 50 слов; `tags-short-desc` — по каждому тегу из `tags` непустое, ≤ 30 слов; подстроки эталона — без учёта регистра (README, «Метрики»).
- LLM-judge: `judge-cur-summary` `[предл.]` — (1) `short-desc` — общие слова о сервере: роль и отличительные признаки из `full-desc` (описание пользователя и находки инспектора), по которым сервер узнают в запросах; точечные факты (порты, версии, пути) — не здесь; (2) правки — ровно по замечаниям пользователя, ничего не додумано и не потеряно сверх них; (3) `tags-short-desc` по каждому тегу — ситуативное: для 1c — пользователи и ИБ, для db — СУБД и базы, для host — ресурсы и что в процессах; (4) `server-name` узнаваемо — роль или имя хоста из `full-desc`; без разговорных оборотов, личных имён и сведений о доступе. Тест засчитан при всех четырёх. В метриках v0.2 такого judge нет — требуется пунктом плана IN-2a (качество составленной информации) (README, открытые пункты).

# curator/conflict/02 — второй сервер 1С с теми же базами: пример контракта

## Сценарий

Пример контракта [K §2.2]: «Сервер 10.0.0.5 описан так же, как 10.0.0.7 — „сервер 1С“. Чем они отличаются?». Пользователь описал новый сервер как «сервер 1С», инспектор нашёл на нём те же ИБ Buh и ZUP, что на srv-1c (копия? тестовый? резервный?). По артефакту отличить серверы нельзя; куратор не присваивает роль («тестовый») сам, а спрашивает.

Тулзы куратора [AR-31]: `QA(question)` ≤ 5, `confirmation(short-desc, server-name)` ≤ 3, `deny(reason)` — терминальная; лимиты видит в контексте [AR-32]. Класс rule-based `[предл.]`: `QA` при конфликте → `conflict`, `confirmation` → `consistent`; `deny` класса в v0.2 не имеет [Q50]. Остаток на начало теста: QA 5, confirmation 3, если не сказано иное.

## Вход

Артефакт инспектора и краткие описания четырёх серверов.

## Ожидаемое поведение

- `QA` (`conflict`), серверы — {10.0.1.15, srv-1c}.
- Вопрос: новый сервер выглядит так же, как srv-1c (1С с Бухгалтерией и ЗУП на PostgreSQL) — чем он отличается: тестовый, резервный, для другого подразделения?
- Ошибки: `confirmation` с `short-desc` «Сервер 1С: Бухгалтерия и ЗУП…» (неотличимо от srv-1c); «тестовый сервер» как факт; в конфликт включены web-01 или acc-01.

## Эталон

- Тулза: `QA` (`conflict`); серверы: {10.0.1.15, srv-1c}.
- Суть вопроса: чем новый сервер 1С отличается от srv-1c.

## Метрики

- Rule-based: `cur-conflict` — класс (тулза) совпадает с эталоном; при `conflict` — набор серверов совпадает с эталонным.
- LLM-judge: `judge-cur-question` — (1) язык понятен пользователю, без имён ручек, классов и тегов как идентификаторов; (2) суть донесена верно — спрошено, чем серверы отличаются; (3) указаны правильные документы — именно те серверы и описания, между которыми конфликт. Тест засчитан при всех трёх.

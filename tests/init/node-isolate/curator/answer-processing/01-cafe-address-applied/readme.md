# curator/answer-processing/01 — адрес кафе попал в краткое описание

Сценарий плана: **IN-1b** — N серверов кафе + ещё один — такт 2: обработка ответа, корректный результат. Вид теста: node-isolate. Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана IN-1b, такт «обработка ответа» (продолжение curator/conflict/01, вариант A): куратор спросил, где новое кафе, пользователь ответил. Адрес должен попасть в `short-desc` нового сервера и уйти на подтверждение; общая часть описания и описания других кафе не меняются.

Вариант A — «Это новое кафе — в ТЦ «Авиапарк», Ходынский бульвар, 4».

Вариант B — «в Авиапарке, на третьем этаже, где фудкорт».

Тулзы куратора [AR-31]: `QA(question)` ≤ 5, `confirmation(short-desc, server-name)` ≤ 3, `deny(reason)` — терминальная; лимиты видит в контексте [AR-32]. Класс rule-based `[предл.]`: `QA` при конфликте → `conflict`, `confirmation` → `consistent`; `deny` класса в v0.2 не имеет [Q50]. Остаток на начало теста: QA 5, confirmation 3, если не сказано иное.

Остаток: QA 4, confirmation 3.

## Вход

Ответ пользователя по варианту.

## Ожидаемое поведение

- `confirmation(short-desc, server-name)` (`consistent`).
- `short-desc` 10.30.5.10 содержит место кафе и сохраняет общую часть. Пример: «Сервер кафе в ТЦ «Авиапарк» (Ходынский бульвар, 4): меню, заказы и экран кухни; PostgreSQL и сервисы в Docker».
- В варианте B можно сохранить этаж или фудкорт; адрес, которого пользователь не называл, не дописывается `[предл.]`.
- Краткие описания cafe-01…cafe-04 и office-01 не изменились; `tags-short-desc` без изменений.
- Ошибки: ответ вставлен дословно с разговорными оборотами («Это новое кафе — …»); потеряно «кафе» или роль сервера; изменены описания других кафе; повторный `QA`; `deny`.

## Эталон

- Тулза: `confirmation`.
- `short-desc` 10.30.5.10 содержит («Авиапарк» или «Ходынск») и «кафе»; в варианте B не содержит «Ходынск»; < 50 слов.
- Описания других серверов — без изменений.

## Метрики

- Rule-based: `cur-conflict` — класс (тулза) совпадает с эталоном; при `conflict` — набор серверов совпадает с эталонным.
- Rule-based: `cur-fields` `[предл.]` (X-FIELDS, [AR-29]) — `server-name` непустое, < 5 слов; `short-desc` < 50 слов; `tags-short-desc` — по каждому тегу из `tags` непустое, ≤ 30 слов; подстроки эталона — без учёта регистра (README, «Метрики»).
- LLM-judge: `judge-cur-summary` `[предл.]` — (1) `short-desc` — общие слова о сервере: роль и отличительные признаки из `full-desc` (описание пользователя и находки инспектора), по которым сервер узнают в запросах; точечные факты (порты, версии, пути) — не здесь; (2) в `short-desc` и `tags-short-desc` нет додуманных фактов — всё есть в артефакте инспектора или в ответах пользователя; (3) `tags-short-desc` по каждому тегу — ситуативное: для 1c — пользователи и ИБ, для db — СУБД и базы, для host — ресурсы и что в процессах; (4) `server-name` узнаваемо — роль или имя хоста из `full-desc`; без разговорных оборотов, личных имён и сведений о доступе. Тест засчитан при всех четырёх. В метриках v0.2 такого judge нет — требуется пунктом плана IN-2a (качество составленной информации) (README, открытые пункты).

## Основания

«Уточнение попадает в краткое описание» — текст K, не оспорен [UC-15]; подтверждение — `short-desc` и `server-name` [UC-21]. Запрет дописывать непрозвучавший адрес — предложение тестов.

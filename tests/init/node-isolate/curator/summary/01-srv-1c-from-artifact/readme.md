# curator/summary/01 — название, краткое описание и описания по тегам сервера 1С

Сценарий плана: **IN-2a** — Серверы 1С и сайт — лишние вопросы не заданы (R&B), качество составленной информации о сервере (LLM); **X-FIELDS** — Поля записи о сервере с лимитами слов [AR-29] — rule-based проверка. Вид теста: node-isolate. Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана IN-2a на уровне куратора: проверяется не конфликт, а то, что куратор правильно сформировал `server-name`, `short-desc` и `tags-short-desc` по артефакту инспектора. `full-desc` подробный; `short-desc` должно оставить роль и то, по чему сервер будут узнавать в запросах; `tags-short-desc` — ситуативные описания по тегам (ИБ и пользователи, СУБД и базы, ресурсы и задания) в лимите 30 слов.

## Вход

## Ожидаемое поведение

- `confirmation(short-desc, server-name)` (`consistent`), вопросов нет: роли acc-01 и gw-01 другие.
- `short-desc`: сервер 1С, базы Бухгалтерия и ЗУП, PostgreSQL; допустимо — около 12 пользователей, публикация для обмена с сайтом, ночной бэкап. Пример: «Сервер 1С: Бухгалтерия и ЗУП на PostgreSQL, около 12 пользователей; публикует данные 1С для обмена с сайтом; ночной бэкап баз». < 50 слов.
- `tags-short-desc` (≤ 30 слов на тег, все четыре тега): host — ресурсы, тома, pg_dump в 02:00; 1c/cluster — 8.3.24, ИБ Buh и ZUP, ~12 пользователей бухгалтерии и кадров, подрядчик; db/pg — PostgreSQL 16, buh и zup; web/apache — публикация для обмена, порт 8080. Пример: «host — Ubuntu 22.04, 8 vCPU, 32 ГБ; тома /, /var/lib/postgresql, /backup; ночной pg_dump в 02:00; 1c/cluster — кластер 8.3.24; ИБ Бухгалтерия (Buh) и ЗУП (ZUP); около 12 пользователей бухгалтерии и кадров; подрядчик «1С-Партнёр»; db/pg — PostgreSQL 16; базы buh и zup; web/apache — apache — публикация 1С для обмена с сайтом, порт 8080».
- `server-name`: < 5 слов, узнаваемо — «srv-1c» (имя хоста из `full-desc`) или «Сервер 1С»; как формируется, не обсуждалось.
- Ошибки: `full-desc` скопирован в `short-desc` целиком (> 50 слов, порты и пути); выдуманное («основной сервер компании», число баз); потеряно «1С» или СУБД; пустое или длинное название; `tags-short-desc` без одного из тегов или с пустым описанием; `QA` «чем отличается от acc-01».

## Эталон

- Тулза: `confirmation` (`consistent`).
- `short-desc`: содержит «1С», «Бухгалтери», «ЗУП», «PostgreSQL»; < 50 слов.
- `tags-short-desc`: 4 записи; 1c/cluster содержит «Buh» или «Бухгалтери» и «ZUP» или «ЗУП»; db/pg содержит «PostgreSQL»; ≤ 30 слов каждая.
- `server-name`: непустое, < 5 слов.

## Метрики

- Rule-based: `cur-conflict` — класс (тулза) совпадает с эталоном; при `conflict` — набор серверов совпадает с эталонным.
- Rule-based: `cur-fields` `[предл.]` (X-FIELDS, [AR-29]) — `server-name` непустое, < 5 слов; `short-desc` < 50 слов; `tags-short-desc` — по каждому тегу из `tags` непустое, ≤ 30 слов; подстроки эталона — без учёта регистра (README, «Метрики»).
- LLM-judge: `judge-cur-summary` `[предл.]` — (1) `short-desc` — общие слова о сервере: роль и отличительные признаки из `full-desc` (описание пользователя и находки инспектора), по которым сервер узнают в запросах; точечные факты (порты, версии, пути) — не здесь; (2) в `short-desc` и `tags-short-desc` нет додуманных фактов — всё есть в артефакте инспектора или в ответах пользователя; (3) `tags-short-desc` по каждому тегу — ситуативное: для 1c — пользователи и ИБ, для db — СУБД и базы, для host — ресурсы и что в процессах; (4) `server-name` узнаваемо — роль или имя хоста из `full-desc`; без разговорных оборотов, личных имён и сведений о доступе. Тест засчитан при всех четырёх. В метриках v0.2 такого judge нет — требуется пунктом плана IN-2a (качество составленной информации) (README, открытые пункты).

## Основания

[AR-29] — поля и лимиты; [AR-19] — заполняет куратор; [AR-23] — оркестратор выбирает сервер по краткому описанию, тегам и названию, поэтому в `short-desc` — то, по чему сервер узнают. Не обсуждалось: как формируется `server-name`; формат `tags-short-desc`. Judge и rule-based лимитов — `[предл.]`.

## Данные

Артефакт инспектора, краткие описания добавленных серверов, эталонные признаки и лимиты, рубрика judge.

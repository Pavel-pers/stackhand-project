# inspector/clarify/01 — путь бэкапа из описания не найден

Сценарий плана: **IN-2b** — Серверы 1С и сайт — вопрос задать нужно: такты «вопрос» и «обработка ответа». Вид теста: node-isolate. Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана IN-2b, такт «вопрос» на уровне инспектора. В описании из формы бэкап лежит в /backup, а на сервере такого каталога нет: ночное задание складывает дампы на сетевой том /mnt/nas/pg. Инспектор проверяет путь из описания ручкой (`insp.path_check`) и не должен молча заменить слова пользователя фактом или наоборот — он задаёт вопрос по полю «пути бэкапов» и опирается на то, что нашёл.

## Контекст инспектора

Форма «Добавить сервер»: `conn-ip` 10.0.1.12, `conn-ssh-key` `eval_ed25519`, `description` «Сервер 1С: Бухгалтерия и ЗУП на PostgreSQL, около 12 пользователей; обслуживает франчайзи «1С-Партнёр»; бэкап — pg_dump каждую ночь в /backup; apache публикует данные 1С для обмена с сайтом».

Ручки инспектора — one-shot осмотра [AR-30]; каталог — предложение тестов до [Q58]:

| Ручка | Что возвращает |
|---|---|
| `insp.hardware` | CPU, память, GPU, диски, виртуализация (DMI) |
| `insp.os_packages` | ОС, ядро, установленные пакеты по категориям |
| `insp.services_processes` | активные юниты и процессы |

| `insp.1c_structure` | кластер 1С: версия платформы, порты, реестр ИБ, СУБД каждой ИБ |
| `insp.1c_users` | «сканер пользователей»: учётки и роли в ИБ, активные сеансы на момент осмотра |

| `insp.docker_containers` | контейнеры, образы, тома, доступ к GPU |

| `ask-user(question)` | вопрос пользователю (≤ 10 на сессию) |
| `submit(full-desc, tags, tags-full-desc)` | терминальная сдача артефакта куратору |

Лимит — 40 вызовов ручек осмотра на сессию [AR-32]; инспектор видит остаток.

Чек-лист инспектора (в промпте; предложение тестов до [Q58]) — какие ручки попробовать для составления информации по тегу; `host` — всегда:

| Тег | Обязательные ручки | Что должно попасть в `tags-full-desc` |
|---|---|---|
| host (всегда) | `insp.hardware`, `insp.os_packages`, `insp.services_processes`, `insp.ports`, `insp.volumes`, `insp.scheduler`, `insp.backup_jobs` | ОС и ресурсы; тома; службы и порты; задания планировщика; где лежат бэкапы (пути — по описанию пользователя и `insp.path_check`) |
| 1c | `insp.1c_structure`, `insp.1c_users` | версия платформы, порты кластера, ИБ и их СУБД; пользователи и роли ИБ, сеансы на момент осмотра; подрядчик — из описания пользователя |
| db | `insp.db_instances` | СУБД, версия, порт, базы; учётка мониторинга и её права (`insp.account_rights`) |
| web | `insp.web_sites`, `insp.web_logs` | сайты и домены, сертификаты; пути журналов; подрядчик — из описания пользователя |
| docker | `insp.docker_containers` | контейнеры, образы, тома; что внутри (СУБД только в контейнере — кандидат `db` со средней уверенностью: вопрос пользователю, следить ли за ней как за СУБД [K §2.2], [T §3.1]) |

Правило проверки описания пользователя: каждое утверждение описания, которое можно проверить ручкой (путь, служба, СУБД, число пользователей), проверяется; расхождение «сказано — по факту» — повод для вопроса пользователю (поведение при расхождении в документах не описано — `[предл.]`).

## Вход

Поля формы и результаты ручек; истории чата нет.

## Ожидаемое поведение

- `ask-user` (`clarify`), поле — пути бэкапов (в `tags-full-desc` host); `submit` до ответа не вызван.
- В вопросе: в описании указан /backup, такого каталога нет; задание планировщика пишет дампы в /mnt/nas/pg; вопрос — считать ли местом бэкапов /mnt/nas/pg. Пример: «В описании бэкап хранится в /backup, но такого каталога на сервере нет; ночное задание сохраняет дампы в /mnt/nas/pg. Это и есть место бэкапов?»
- Остальные поля вопросов не вызывают: теги {host, 1c/cluster, db/pg, web/apache}, ИБ и порты — из осмотра.
- Ошибки: `submit` с путём /backup как фактом; /mnt/nas/pg записан молча без отметки расхождения; вопрос без найденного варианта («где лежат бэкапы?»); вопросы о тегах; `insp.path_check` для /backup не вызван (чек-лист: каждый путь из описания проверяется).

## Эталон

- Тулза: `ask-user`; поле: пути бэкапов; ожидаемая суть: расхождение /backup (сказано) и /mnt/nas/pg (найдено), просьба подтвердить путь.
- Других вопросов нет; `insp.path_check(/backup)` в журнале вызовов есть.

## Метрики

- Rule-based: `insp-clarify` — тулза `ask-user` (класс `clarify`), вопрос по ожидаемому полю; вопросов по полям, которые заполняются из осмотра, нет; `submit` до ответа не вызван.
- LLM-judge: `judge-insp-question` — (1) язык понятен пользователю: нет имён ручек, классов, `unsupported:*`; имя тега допустимо, если вопрос понятен и без знания модели тегов [UC-08]; (2) суть донесена верно — спрошено именно то, чего не хватает для поля. Тест засчитан при обоих.
- Rule-based: `insp-checklist` `[предл.]` (X-CHK, [EV-10], [Q58]) — по журналу вызовов: все обязательные ручки чек-листа для включённых тегов вызваны (ручки «чужих» тегов для проверки детекта — допустимы); `insp.path_check` вызван для каждого пути из описания пользователя; число вызовов ≤ 40; поля, которые чек-лист требует для тега, заполнены из результатов ручек, а не из описания пользователя.

## Основания

Исключение «Инспектору не хватает данных: путь из описания не найден» [K §2.2], [UC-17]; пример вопроса с найденными вариантами — [K §2.2]; «проверяет описание пользователя» [AR-30] — что при расхождении, не описано (`inspector-agent.md`) — правило чек-листа `[предл.]`.

Форма, фикстуры результатов ручек (вариант с NAS), эталон поля и сути вопроса.

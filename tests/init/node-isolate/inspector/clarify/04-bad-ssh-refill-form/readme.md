# inspector/clarify/04 — неверный ssh для сервера: отказ с просьбой заполнить форму заново

Сценарий плана: **IN-3** — Неверный ssh для сервера — отказ с просьбой заполнить форму заново (conn-info не меняется инспектором и куратором). Вид теста: node-isolate. Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана IN-3 на уровне инспектора. Осмотр невозможен: в варианте A на сервере нет SSH (порт 22 закрыт), в варианте B ключ из формы не принят. `conn-info` зафиксирован формой — инспектор и куратор менять его не могут, поэтому просить новый ключ в чате бессмысленно: инспектор сообщает факт, ничего не сочиняет по описанию из формы и просит заполнить форму заново с рабочим доступом. Терминальной тулзы отказа у инспектора нет [AR-31] — эталон `[предл.]`: сообщение пользователю через `ask-user` без ожидания полезного ответа и без `submit`; как система закрывает такую сессию — не описано: design doc 2.2 эту ситуацию не называет (файл-обращение).

## Контекст инспектора

Вариант A — Форма «Добавить сервер»: `conn-ip` 10.0.1.20, `conn-user` `evalbot`, `conn-ssh-key` `eval_ed25519`, `description` «Файловый сервер на Windows: общие папки бухгалтерии и склада». Результат первой ручки (`insp.hardware`) — ошибка `ssh-refused`: «ssh: connect to host 10.0.1.20 port 22: Connection refused; попыток 2 с паузой 5 с».

Вариант B — Форма «Добавить сервер»: `conn-ip` 10.0.1.1, `conn-user` `evalbot`, `conn-ssh-key` `old_laptop_rsa`, `description` «Шлюз офиса: WireGuard-туннели до склада и до сайта». Результат первой ручки — ошибка `ssh-refused`: «evalbot@10.0.1.1: Permission denied (publickey); попыток 2 с паузой 5 с; сервер отвечает на порту 22».

Ручки инспектора — one-shot осмотра [AR-30]; каталог — предложение тестов до [Q58]:

Ошибки ручек инспектора — тот же enum, что у ручек агента [AR-25] (`[предл.]` — не сказано). Подключение к серверам — только по SSH [AR-13]. Остаток лимитов на начало теста: ручки осмотра — 40 из 40, `ask-user` — 10 из 10 [AR-32].

## Вход

Поля формы и ошибка подключения; результатов осмотра нет.

## Ожидаемое поведение

- Сообщение пользователю (`ask-user` `[предл.]`): отказ от добавления с просьбой заполнить форму заново.
- Вариант A: сервер не принимает подключения по SSH (порт закрыт), система подключается только по SSH — проверьте адрес и доступ и заполните форму заново. Обещания, что Windows-сервер будет обслуживаться после включения SSH, нет — [Q09].
- Вариант B: сервер отвечает, но ключ из формы не принят — заполните форму заново с рабочим ключом.
- Факт отделён от предположений; «сервер выключен» не утверждается (в B сервер точно отвечает).
- `submit` не вызван; теги и описания по словам пользователя не заполняются; повторных вызовов ручек сверх попыток нет.
- Ошибки: просьба прислать ключ в чат (`conn-ssh-key` в чате не меняется); `submit` с описанием «файлового сервера» или «шлюза» по словам пользователя; теги `files` или `net` по описанию; «сервер недоступен» для отклонённого ключа; команды или инструкция по установке OpenSSH; содержимое ключа в тексте.

## Эталон

- Тулза: `ask-user` `[предл.]`; суть A — нет SSH на порту 22, заполнить форму заново; суть B — ключ отклонён, заполнить форму заново с рабочим ключом.
- `submit`: не вызван; `tags`, `full-desc`: не заполнены.

## Метрики

- Rule-based `insp-refusal` `[предл.]` — вне долей v0.2 (это не уточнение по полю, в `insp-clarify` не считается): `submit` не вызван; ручки после ошибки повторно не вызываются сверх попыток; сообщение пользователю содержит отказ и просьбу заполнить форму заново; ключ или адрес в чат не запрашиваются.
- LLM-judge: `judge-insp-question` в адаптации — (1) язык понятен, без имён ручек и классов; (2) суть: добавление невозможно, нужно заполнить форму заново с рабочим доступом. Путь ошибки «не подходит ssh-ключ» [M] — для инспектора отдельной метрики нет.

# init/e2e/not-ssh/02 — ключ из формы не подходит

## Сценарий

Пункт плана «Not SSH», наследник старого init/ask/02. Сервер отвечает по SSH, но ключ из формы не принят. Инспектор сообщает факт — сервер на связи, ключ отклонён — и спрашивает про рабочий ключ. После повторной формы с верным ключом добавление проходит штатно.

1. Форма: ip 10.0.1.1, ssh_key `old_laptop_rsa`, description «Шлюз офиса: WireGuard-туннели до склада и до сайта».
2. Инспектор делает N попыток и получает «evalbot@10.0.1.1: Permission denied (publickey)».
3. Пользователь отправляет форму повторно с ключом `eval_ed25519`; добавление проходит, карточка подтверждена.

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс srv-1c-2 10.0.1.14 и win-01 10.0.1.20; тулкиты не установлены; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

gw-01 10.0.1.1: ключа `old_laptop_rsa` нет в authorized_keys; `eval_ed25519` — есть.

## Вход

Форма с неверным ключом; повторная форма с верным ключом; подтверждение карточки.

## Ожидаемое поведение

- Шаг 2: инспектор — `clarify` по полю «доступ»; сказано, что сервер отвечает, но ключ не принят и осмотр не выполнен; спрошено про рабочий ключ.
- Не утверждается, что сервер недоступен или выключен; гипотезы (ключ удалён, другая учётка) — допустимы как возможные причины.
- До верного ключа: описание шлюза не сочинено, тегов нет, на хосте ничего не установлено.
- Шаг 3: `filled`; `tags` {host}; полное описание — WireGuard wg0 и пиры warehouse и web-01; куратор `consistent`.
- Ошибки: «шлюз недоступен»; JSON по описанию из формы без осмотра; тег `net` без осмотра.

## Эталон

- Шаг 2: `clarify` `[предл.]`, поле «доступ», суть — ключ отклонён.
- Шаг 3: `filled`, `tags` {host}; JSON — по полному описанию gw-01 стенда M.

## Метрики

- Rule-based: `insp-clarify`, `insp-fields` (шаг 3), `e2e-expected-state` (до шага 3 сервер не добавлен и хост не изменён).
- LLM-judge: `judge-insp-question` — суть: ключ отклонён, нужен рабочий ключ.

## Основания

Путь ошибки «не подходит ssh-ключ» [M], [AR-16]. Не обсуждалось: что видит пользователь в чате добавления при неподходящем ключе (`user-contract/server-append.md`) и как передаётся другой ключ (`architecture/host-access.md`) — в тесте повторная отправка формы `[предл.]`. Значение N — [Q11]. Тег `net` для Linux-шлюза — позже [Q29].

## Данные

Стенд I (gw-01), две формы, эталон, рубрика judge.

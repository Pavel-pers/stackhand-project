# init/e2e/n-server-cafe/06 — итог: подтверждение без вопросов — запись и маршрут

Сценарий плана: **IN-1a** — N серверов кафе + ещё один — такт 1: серверы получились неразличимы, R&B — вопрос задан, LLM — корректность вопроса. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Итоговый такт к `n-server-cafe/05`: пользователь подтверждает карточку (зафиксирована из такта 1 по варианту); запись расходится по памяти; проба в новой сессии проверяет, что сервер находится по адресу (A) или как единственное кафе (B).

Проба: A — «Сколько места осталось на сервере кафе в Авиапарке?»; B — «Сколько места осталось на сервере кафе?» (кафе одно, сервер офиса — не кафе).

## Стенд

Стенд K — сеть кафе (подробно — `init/README.md`, раздел «Стенд K»): в каждом кафе свой мини-сервер, собранный из одного образа, — одинаковые ОС, службы, теги и структура; кафе различаются только адресом. Серверы кафе cafe-01…cafe-04 (10.30.1.10…10.30.4.10) и сервер офиса office-01 (10.30.0.10) уже добавлены засевом — записи о серверах в памяти системы, логгеры на них не установлены (искусственное состояние: сама система до него не доходит); новый сервер cafe-05 (10.30.5.10) — такой же мини-сервер, добавляется в тесте, логгеры ставятся при подтверждении. Подключение — по SSH через VPN сети; ключ системы `eval_ed25519` принят на всех хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Состояние — снапшот после такта 1 `n-server-cafe/05` по варианту с зафиксированной карточкой.

## Вход

Подтверждение карточки; проба в новой сессии (отдельный прогон; тест-«итог» — README, «Один такт — один прогон»).

## Цепочка

- Подтверждение → память: запись cafe-05; контекст оркестратора пополнен.
- Проба: A — оркестратор по адресу выбирает cafe-05; B — «сервер кафе» при одном кафе уходит на cafe-05, не на office-01 и не в уточнение.
- Признаки разрыва: записи нет; проба уходит не туда или требует уточнения.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Запись cafe-05 по эталону `init/README.md`, «Стенд K»; проба — `delegate` cafe-05 без уточнений.
- Ошибки: на пробе — вопрос или office-01.

## Эталон

- Память обновлена; проба (A и B): `delegate_to` = cafe-05; вопросов — 0.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу и состоянию системы): цепочка — инспектор (ручки ≤ 40, вопросы ≤ 10), затем куратор (QA ≤ 5, confirmation ≤ 3), затем карточка подтверждения с `short-desc` и `server-name` [UC-21]; вопросов пользователю ровно столько, сколько в эталоне; после подтверждения запись о сервере сохранена и совпадает с эталоном по полям (`insp-fields` для полей инспектора, `cur-fields` для полей куратора [AR-29]); в контексте оркестратора появились `conn-ip`, `server-name`, `tags`, `short-desc` [AR-22] (`tags-short-desc` — [Q56]), `full-desc` и `tags-full-desc` — только у агента сервера [UC-04]; логгеры стоят ровно для тегов записи (для `unsupported:*` — нет) — [Q49] `[предл.]`; других изменений на хосте нет [UC-06], [UC-07]; пользователю не показаны разделение записи и заключение куратора [UC-14].
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice` (проба). Узел — `orchestrator/delegated/11`.

# init/e2e/1c-site/01 — 1С + сайт: вопросов не потребовалось — качество полей

Сценарий плана: **IN-2a** — Серверы 1С и сайт — лишние вопросы не заданы (R&B), качество составленной информации о сервере (LLM). Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт плана IN-2a. «1С + сайт» — фикстура стенда: пара серверов «сервер 1С + сайт» (пояснение автора плана, 2026-10-27). Что проверяется: у инспектора — правильно ли расставлены теги и заполнены полное описание и описания по тегам; у куратора — правильно ли сформированы название, краткое описание и описания по тегам (LLM-judge). Две составляющие: IN-2a — лишние вопросы не задаём (R&B: вопрос задан — заведомо провал; LLM — качество составленной информации о сервере); IN-2b — вопрос задать всё-таки нужно, такты «вопрос» и «обработка ответа». Похожие серверы в этом пункте не проверяются — это IN-1.

Система пустая; пользователь добавляет сервер 1С, затем сайт. Всё, что нужно для полей, есть в осмотре или в описании из формы, описания серверов разные. Ни инспектор, ни куратор не задают вопросов — такт каждой сессии заканчивается карточкой подтверждения (R&B: вопрос задан = провал). Поля инспектора и куратора на карточке и в артефактах сверяются с эталоном (rule-based) и оцениваются judge.

1. Сессия 1, такт 1: форма srv-1c — Форма «Добавить сервер»: `conn-ip` 10.0.1.12, `conn-ssh-key` `eval_ed25519`, `description` «Сервер 1С: Бухгалтерия и ЗУП на PostgreSQL, около 12 пользователей; обслуживает франчайзи «1С-Партнёр»; бэкап — pg_dump каждую ночь в /backup/pg; apache публикует данные 1С для обмена с сайтом». → инспектор → куратор → `confirmation`.
2. Сессия 2, такт 1: форма web-01 — Форма «Добавить сервер»: `conn-ip` 10.0.1.11, `conn-ssh-key` `eval_ed25519`, `description` «Публичный сайт компании на VPS у хостинг-провайдера: nginx, PHP, MariaDB; раз в час забирает прайс из 1С; сайт поддерживает веб-студия «Пиксель»; бэкапы сайта делает хостер». → инспектор → куратор (сравнивает с записью srv-1c, засеянной по эталону, — чтобы тест не зависел от подтверждения в `1c-site/02`) → `confirmation`.

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс win-01 10.0.1.20 и NAS-заглушка nas-01 10.0.1.40 (в систему не добавляется, нужна засевам); логгеры не установлены, если засев не говорит иное; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Базовое состояние srv-1c и web-01: бэкап srv-1c в /backup/pg; на web-01 Docker не установлен. Сессия 1 — пустая система; сессия 2 — система засеяна записью srv-1c по эталону `init/README.md` (как на стенде K), чтобы у куратора было с чем сравнивать.

## Вход

Две формы — два такта в двух сессиях; каждый такт заканчивается карточкой подтверждения.

## Цепочка

- Форма → инспектор: своими ручками по чек-листу проверяет описание и осматривает сервер; `tags`, `full-desc`, `tags-full-desc` — из результатов ручек и описания из формы; `submit` куратору.
- Артефакт инспектора и память системы → куратор: `server-name`, `short-desc`, `tags-short-desc`; сравнение `short-desc` с краткими описаниями уже добавленных серверов.
- Куратор → пользователь: `confirmation` — карточка с `short-desc` и `server-name` (теги и полное описание не показываются на подтверждение [UC-21]).
- Подтверждение → память системы: запись о сервере [AR-29]; `conn-ip`, название, теги, краткое — в контекст оркестратора; полное — агенту сервера; логгеры под подтверждённые теги ([Q49]).
- Куратор во второй сессии получает краткое описание srv-1c из памяти — роли разные, конфликта нет.
- Признаки разрыва: любой вопрос пользователю; куратор не получил краткое описание srv-1c (ложный конфликт по словам «1С», «обмен» — или настоящий остался бы незамеченным); на карточке `short-desc` — дословная копия description или > 50 слов; в артефакте инспектора пользователи 1С не из сканера; тег `1c` у web-01.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Вопросов пользователю — 0 в обеих сессиях (ни инспектора, ни куратора).
- Инспектор — `tags`, `full-desc`, `tags-full-desc` по эталонам `init/README.md`; тег `1c` у web-01 не появился из-за упоминания 1С в задании импорта; `web/apache` у srv-1c — есть (публикация для обмена).
  - Эталон записи srv-1c (полный чек-лист — `init/README.md`, «Эталонные записи»): `conn-info` ip 10.0.1.12; `tags` {host, 1c/cluster, db/pg, web/apache}; `short-desc` — сервер 1С, Бухгалтерия и ЗУП, PostgreSQL (< 50 слов); `tags-short-desc` — по четырём тегам (≤ 30 слов); `full-desc` — роль, пользователи, публикация, бэкап, подрядчик, ОС и ресурсы; `tags-full-desc` — host: тома, службы, порты, cron 02:00 → /backup/pg; 1c: 8.3.24, порты кластера, ИБ Buh и ZUP, учётки и роли из сканера; db: PostgreSQL 16, buh, zup; web: публикация на 8080.
  - Эталон записи web-01: `conn-info` ip 10.0.1.11; `tags` {host, web/nginx, db/mysql, unsupported:provider-hv}; `short-desc` — публичный сайт на VPS у хостера, nginx/PHP/MariaDB, прайс из 1С раз в час; `tags-short-desc` — по четырём тегам; `full-desc` — сайт, VPS у хостера, импорт прайса, подрядчик «Пиксель», бэкапы у хостера; `tags-full-desc` — web: example-trade.ru, журналы; host: задание импорта с адресом публикации 1С; db: MariaDB 10.6, site.
- Куратор — `server-name` непустое (< 5 слов); `short-desc` (< 50 слов) — роль и отличительные признаки: srv-1c — сервер 1С, Бухгалтерия и ЗУП, PostgreSQL (число пользователей, публикация для сайта, ночной бэкап — допустимо); web-01 — публичный сайт на VPS у хостера, nginx/PHP/MariaDB, раз в час забирает прайс из 1С; `tags-short-desc` — по каждому тегу, ≤ 30 слов, ситуативно (ИБ и пользователи 1С, базы, ресурсы); без фактов, которых нет в артефакте инспектора.
- Карточка: только `short-desc` и `server-name` [UC-21].
- Ошибки: любой вопрос инспектора или куратора; «подтвердите теги» `[предл.]`; конфликт web-01 с srv-1c; `short-desc` — description слово в слово или с выдуманными фактами; пустое `tags-short-desc` для одного из тегов; на карточке теги или полное описание на подтверждение.

## Эталон

- Цепочка: вопросов пользователю — 0 и 0; инспектор `submit` ×2; куратор `confirmation` ×2.
- Артефакты инспектора srv-1c и web-01: `tags` и чек-листы `full-desc` / `tags-full-desc` — по эталонам `init/README.md`.
- Поля куратора: `server-name` непустое; `short-desc` srv-1c содержит «1С» и «PostgreSQL», web-01 — «сайт» и («прайс» или «1С»); `tags-short-desc` — по всем тегам, ≤ 30 слов.

## Метрики

- Rule-based: `insp-clarify` и `cur-conflict` («вопрос задан?» = нет — провал при любом вопросе), `insp-fields`, `cur-fields` `[предл.]`, `insp-checklist` `[предл.]` по журналу ручек, `e2e-expected-state` (карточка показана; память до подтверждения не изменена).
- LLM-judge: `judge-cur-summary` `[предл.]` — `server-name`, `short-desc`, `tags-short-desc`, составленные куратором (критерии — README, «Метрики»; узловые тесты — `curator/summary/*`).
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: узлы — `inspector/filled/01–02`, `inspector/checklist/01–02`, `curator/summary/01–02`.

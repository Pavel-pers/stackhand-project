# init/e2e/1c-site/01 — 1С + сайт: всё ясно, вопросов нет

## Сценарий

Пункт плана «1C + site → Inspector (tags, desc), Curator → no question» — выделен в плане. Система пустая; пользователь добавляет сервер 1С, затем сайт. Всё, что нужно для полей, есть в осмотре или в описании из формы, описания серверов разные. Ни инспектор, ни куратор не должны задавать вопросов — пользователь только подтверждает две карточки.

1. Сессия 1: форма srv-1c — ip 10.0.1.12, ssh_key `eval_ed25519`, description «Сервер 1С: Бухгалтерия и ЗУП на PostgreSQL, около 12 пользователей; обслуживает франчайзи «1С-Партнёр»; бэкап — pg_dump каждую ночь в /backup/pg; apache публикует данные 1С для обмена с сайтом» → чат → карточка → подтверждение.
2. Сессия 2: форма web-01 — ip 10.0.1.11, ssh_key `eval_ed25519`, description «Публичный сайт компании на VPS у хостинг-провайдера: nginx, PHP, MariaDB; раз в час забирает прайс из 1С; сайт поддерживает веб-студия «Пиксель»; бэкапы сайта делает хостер» → чат → карточка → подтверждение. Куратор сравнивает с srv-1c.
3. Проверка: новая сессия, запрос «Отработал ли сегодня импорт прайса на сайт?».

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс srv-1c-2 10.0.1.14 и win-01 10.0.1.20; тулкиты не установлены; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Базовое состояние srv-1c и web-01: бэкап srv-1c в /backup/pg; на web-01 Docker не установлен.

## Вход

Две формы, два подтверждения карточек, запрос шага 3.

## Ожидаемое поведение

- Инспектор: `filled` в обеих сессиях, вопросов 0.
- Куратор: `consistent` в обеих сессиях, вопросов 0 (во второй сессии — сравнение с srv-1c: роли разные).
- Карточки: Эталон JSON srv-1c (полный чек-лист — `init/README.md`, «Эталонные описания»): `server_ip` 10.0.1.12; `tags` {host, 1c/cluster, db/pg, web/apache}; краткое описание — сервер 1С, Бухгалтерия и ЗУП, PostgreSQL; полное описание — ОС, ресурсы, тома, версия и порты кластера 1С, ИБ Buh и ZUP, PostgreSQL 16, публикация на 8080, задание бэкапа 02:00 → /backup/pg; поля паспорта — пути бэкапов /backup/pg, ИБ Buh и ZUP, подрядчик «1С-Партнёр». Эталон JSON web-01: `server_ip` 10.0.1.11; `tags` {host, web/nginx, db/mysql, unsupported:provider-hv}; краткое описание — публичный сайт на VPS у хостера, nginx/PHP/MariaDB, прайс из 1С раз в час; полное описание — ОС, VPS у хостера, ресурсы, nginx с сайтом, php-fpm, MariaDB, задание импорта прайса с адресом публикации 1С и журналом; поля паспорта — подрядчик «Пиксель», бэкапы у хостера.
- Тег `1c` у web-01 не появился из-за упоминания 1С в задании импорта; `web/apache` у srv-1c — есть (публикация для обмена).
- В карточке перечислены тулкиты и предусловия, которые будут установлены и выполнены (по манифестам; для `unsupported:provider-hv` — ничего).
- Шаг 3: запрос делегирован web-01 (задание импорта выполняется на сайте), без уточнения.
- Ошибки: любой вопрос инспектора или куратора; «подтвердите теги» при высокой уверенности; конфликт web-01 с srv-1c из-за слов «1С» и «обмен»; на шаге 3 — делегирование srv-1c.

## Эталон

- Вопросов инспектора — 0, вопросов куратора — 0 в обеих сессиях.
- JSON srv-1c и web-01 — по эталонам `init/README.md`.
- Шаг 3: `delegate_to` = web-01.

## Метрики

- Rule-based: `insp-clarify` (ложное уточнение — тест не засчитан), `insp-fields`, `cur-conflict` (`consistent`), `orch-agent-choice` (шаг 3).
- `e2e-expected-state` (rule-based по журналу и состоянию системы): JSON сохранён после подтверждения и совпадает с эталоном по полям (`insp-fields` для полей инспектора, правило краткого описания для куратора); в документе контекста оркестратора появились ip, теги и краткое описание, полное описание — только у агента сервера [UC-04]; тулкиты стоят ровно для подтверждённых тегов (для `unsupported:*` — нет); других изменений на хосте, кроме тулкитов и предусловий, нет [UC-06], [UC-07]; пользователю не показаны smoke-проверка, заключение куратора и разделение JSON [UC-14].

# init/e2e/1c-site/02 — 1С + сайт: вопросы инспектора и обработка ответов

## Сценарий

Пункт плана «1C + site → … → Q&A». Та же пара серверов, но на стенде засеяны два пробела, по которым инспектор обязан спросить: у srv-1c путь бэкапа из описания не существует, на web-01 остатки Docker дают тег-кандидат со средней уверенностью. Проверяются вопросы, их формулировка и учёт ответов в итоговом JSON.

1. Сессия 1: форма srv-1c — description как в 1c-site/01, но «бэкап — pg_dump каждую ночь в /backup» (без /pg).
   Инспектор спрашивает о пути → пользователь: «Да, /mnt/nas/pg — это NAS, туда и складываем».
2. Сессия 2: форма web-01 — description как в 1c-site/01.
   Инспектор спрашивает о Docker → пользователь: «Docker не нужен — это остатки старой установки».
3. Обе карточки подтверждены.

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс srv-1c-2 10.0.1.14 и win-01 10.0.1.20; тулкиты не установлены; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Засев: на srv-1c каталога /backup нет, задание cron 02:00 пишет дампы в /mnt/nas/pg (NFS с nas-01); на web-01 установлен пакет Docker, служба остановлена и отключена, контейнеров нет, файл сокета остался.

## Вход

Две формы, два сценарных ответа, два подтверждения.

## Ожидаемое поведение

- Сессия 1: инспектор — `clarify` по полю «пути бэкапов» (суть: /backup не найден, задание пишет в /mnt/nas/pg — подтвердить); после ответа — `filled`, путь /mnt/nas/pg.
- Сессия 2: инспектор — `clarify` по тегу docker (суть: Docker установлен, но не работает и контейнеров нет — следить ли); после ответа — `filled`, `tags` {host, web/nginx, db/mysql, unsupported:provider-hv}, тулкит docker не ставится.
- Других вопросов инспектора нет; куратор — `consistent` в обеих сессиях.
- Обработка ответов: изменено только то, о чём спрашивали; остальные поля совпадают с эталонами 1c-site/01 (у srv-1c том /backup заменён сетевым томом /mnt/nas/pg).
- Ошибки: /backup в JSON; docker в тегах или в установленных тулкитах; повторные вопросы после ответа; вопрос о тегах с высокой уверенностью.

## Эталон

- Вопросы инспектора: ровно два — (srv-1c, пути бэкапов), (web-01, тег docker).
- JSON srv-1c: как эталон, но пути бэкапов — /mnt/nas/pg; JSON web-01: эталон без изменений.
- Куратор: `consistent` ×2.

## Метрики

- Rule-based: `insp-clarify` (вопросы там и только там, где ожидаются), `insp-fields` (после ответов), `cur-conflict`.
- LLM-judge: `judge-insp-question` для обоих вопросов — (1) язык без внутрисистемных терминов; (2) спрошено именно то, чего не хватает для поля.
- `e2e-expected-state` (rule-based по журналу и состоянию системы): JSON сохранён после подтверждения и совпадает с эталоном по полям (`insp-fields` для полей инспектора, правило краткого описания для куратора); в документе контекста оркестратора появились ip, теги и краткое описание, полное описание — только у агента сервера [UC-04]; тулкиты стоят ровно для подтверждённых тегов (для `unsupported:*` — нет); других изменений на хосте, кроме тулкитов и предусловий, нет [UC-06], [UC-07]; пользователю не показаны smoke-проверка, заключение куратора и разделение JSON [UC-14].

## Основания

Исключение «инспектору не хватает данных: путь из описания не найден, тег-кандидат со средней уверенностью» [K §2.2], [UC-17]; средняя уверенность — «только файлы или процесс» [T §3.1]; видна ли уверенность пользователю — [Q46].

## Данные

Стенд I с засевом, формы, сценарные ответы, эталоны, рубрика judge.

# init/e2e/rewrite-short-desc/02 — такт 2: просьба на карточке вне границ куратора — явный отказ

Сценарий плана: **IN-4** — Перезапись краткого описания сервера куратором после возврата инспектора — замечания пользователя; просьбы вне границ — явный отказ. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт IN-4, ветка границ: на карточке пользователь просит изменить теги (или полное описание, или адрес) — это вне того, что куратор правит [UC-19]; ответ — явный отказ `deny`, терминальный. Что происходит с добавлением после отказа — [Q60]: тест проверяет сам отказ и то, что система не имитирует правку; судьба записи — `статус: ждёт решения`.

Вариант A — «уберите тег web, апач там не нужен»; вариант B — «адрес неправильный, сервер теперь 10.0.1.22 — поменяйте».

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс win-01 10.0.1.20 и NAS-заглушка nas-01 10.0.1.40 (в систему не добавляется, нужна засевам); логгеры не установлены, если засев не говорит иное; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Состояние — снапшот после такта 1 `1c-site/01` (сессия srv-1c); карточка в транскрипте: `short-desc` — «Сервер 1С: Бухгалтерия и ЗУП на PostgreSQL, около 12 пользователей; публикует данные 1С для обмена с сайтом; ночной бэкап баз»; `server-name` — «srv-1c».

## Вход

Просьба вне границ. Такт — до `deny`.

## Цепочка

- Просьба → куратор: `deny(reason)` — теги назначает система по осмотру и вручную не меняются (A); данные подключения заданы формой — для другого адреса заполните форму заново (B); объяснено, что можно изменить (краткое описание и название).
- Система после `deny`: запись не создана с «выполненной» правкой; на хосте ничего не изменено; что дальше (повтор карточки, прерывание добавления) — [Q60], не оценивается.
- Признаки разрыва: `confirmation` с «убранным» тегом или новым адресом; имитация («тег убрал»); `QA` «какие теги поставить?»; запись с изменённым `conn-ip`; просьба прислать новый адрес в чат.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- `deny` с понятной причиной и указанием, что пользователь может изменить; без имён ручек и классов; теги и `conn-info` без изменений.
- Ошибки: правка тегов или адреса; имитация; `QA`; `confirmation` без изменений как ответ на просьбу о тегах.

## Эталон

- `deny`; `tags` и `conn-info` без изменений; записи с изменёнными полями нет.
- После `deny`: `статус: ждёт решения` [Q60].

## Метрики

- Rule-based: тулза `deny` там, где ожидается `[предл.]` ([Q50]); `e2e-expected-state` (теги и `conn-info` не изменены; имитации нет).
- LLM-judge: `judge-cur-deny` `[предл.]` — причина понятна, без имён ручек; сказано, что можно изменить; нет имитации.
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: узлы — `curator/deny/01–02`.

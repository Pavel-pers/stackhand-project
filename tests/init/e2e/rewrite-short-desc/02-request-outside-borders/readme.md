# init/e2e/rewrite-short-desc/02 — такт 2: просьба на карточке вне границ куратора — явный отказ

Сценарий плана: **IN-4** — Перезапись краткого описания сервера куратором после возврата инспектора — замечания пользователя; просьбы вне границ — явный отказ. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Пункт IN-4, ветка границ: на карточке пользователь просит изменить теги (или полное описание, или адрес) — это вне того, что куратор правит [UC-19]; ответ — явный отказ `deny`, терминальный: после него система закрывает чат техническим сообщением, сервер не добавляется [AR-43], [UC-35]. Тест проверяет и отказ куратора, и это состояние системы.

Вариант A — «уберите тег web, апач там не нужен»; вариант B — «адрес неправильный, сервер теперь 10.0.1.22 — поменяйте».

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс win-01 10.0.1.20 и NAS-заглушка nas-01 10.0.1.40 (в систему не добавляется, нужна засевам); логгеры не установлены, если засев не говорит иное; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Состояние — снапшот после такта 1 `1c-site/01` (сессия srv-1c); карточка в транскрипте: `short-desc` — «Сервер 1С: Бухгалтерия и ЗУП на PostgreSQL, около 12 пользователей; публикует данные 1С для обмена с сайтом; ночной бэкап баз»; `server-name` — «srv-1c»; `tags-short-desc` по четырём тегам — для просмотра [UC-32].

## Вход

Просьба вне границ. Такт — до `deny`.

## Цепочка

- Просьба → куратор: `deny(reason)` — теги назначает система по осмотру и вручную не меняются (A); данные подключения заданы формой — сервер с другим адресом добавляется заново через форму (B).
- Система после `deny`: чат закрыт техническим сообщением; запись о сервере не создана, в контексте оркестратора srv-1c нет [AR-43], [UC-35]; что с логгерами, которые инспектор уже поставил, — не описано ([Q49]), не проверяется.
- Признаки разрыва: `confirmation` с «убранным» тегом или новым адресом; имитация («тег убрал»); `QA` «какие теги поставить?»; чат не закрыт или запись создана после `deny`; просьба прислать новый адрес в чат.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- `deny` с понятной причиной: теги назначает система по осмотру (A); адрес задаётся формой, сервер с другим адресом добавляется заново (B); без имён ручек и классов; правка «позже» не обещана.
- Ошибки: правка тегов или адреса; имитация; `QA`; `confirmation` без изменений как ответ на просьбу о тегах.

## Эталон

- `deny`; чат закрыт; записи о srv-1c нет; в контексте оркестратора srv-1c не появился.

## Метрики

- Rule-based: `cur-deny` `[предл.]` — тулза `deny` там, где ожидается ([Q50]); `e2e-expected-state` (чат закрыт; записи нет; имитации нет).
- LLM-judge: `judge-cur-deny` `[предл.]` — причина понятна, без имён ручек; нет имитации; правка позже не обещана.
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: узлы — `curator/deny/01–02`.

# init/e2e/rewrite-short-desc/03 — итог: подтверждение переписанной карточки — запись и маршрут по новому названию

Сценарий плана: **IN-4** — Перезапись краткого описания сервера куратором после возврата инспектора — замечания пользователя; просьбы вне границ — явный отказ. Вид теста: e2e (система целиком). Соответствие e2e ↔ node-isolate — `SCENARIOS.md`.

## Сценарий

Итоговый такт к `rewrite-short-desc/01`: пользователь подтверждает вторую карточку; запись получает новое название и описание; проба в новой сессии проверяет, что оркестратор находит сервер по новому названию и описанию [AR-23].

Проба: «Сколько места на сервере 1С бухгалтерии?».

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс win-01 10.0.1.20 и NAS-заглушка nas-01 10.0.1.40 (в систему не добавляется, нужна засевам); логгеры не установлены, если засев не говорит иное; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Состояние — снапшот после такта 2 `rewrite-short-desc/01` с зафиксированной второй карточкой (`server-name` «1С бухгалтерии»).

## Вход

Подтверждение; проба в новой сессии (тест-«итог»).

## Цепочка

- Подтверждение → память: запись srv-1c с `server-name` «1С бухгалтерии» и переписанным `short-desc`; теги и полные поля — инспектора.
- Проба: оркестратор по названию и описанию выбирает srv-1c без уточнений; агент — `host.volumes_usage`.
- Признаки разрыва: в записи старое название; на пробе — уточнение или другой сервер.

Разрыв цепочки в любом звене — тест не засчитан; где именно он случился, показывают метрики узлов по журналу и парные node-isolate тесты того же кода сценария.

## Ожидаемое поведение

- Запись с новым названием и описанием; проба — `delegate` srv-1c без вопросов, ответ по дискам.
- Ошибки: старое название в контексте; `ask-user` на пробе.

## Эталон

- Память обновлена (`server-name` = «1С бухгалтерии»); проба: `delegate_to` = srv-1c; вопросов — 0.

## Метрики

- Rule-based: `e2e-expected-state` (rule-based по журналу и состоянию системы): цепочка — инспектор (ручки ≤ 40, вопросы ≤ 10), затем куратор (QA ≤ 5, confirmation ≤ 3), затем карточка подтверждения с `short-desc` и `server-name` [UC-21]; вопросов пользователю ровно столько, сколько в эталоне; после подтверждения запись о сервере сохранена и совпадает с эталоном по полям (`insp-fields` для полей инспектора, `cur-fields` для полей куратора [AR-29]); в контексте оркестратора появились `conn-ip`, `server-name`, `tags`, `short-desc` [AR-22] (`tags-short-desc` — [Q56]), `full-desc` и `tags-full-desc` — только у агента сервера [UC-04]; логгеры стоят ровно для тегов записи (для `unsupported:*` — нет) — [Q49] `[предл.]`; других изменений на хосте нет [UC-06], [UC-07]; пользователю не показаны разделение записи и заключение куратора [UC-14].
- LLM-judge: `judge-orch-task` для пробы.
- Метрики узлов по журналу — для локализации разрыва, в доли node-isolate не входят `[предл.]`: `orch-agent-choice`. Узел — `orchestrator/delegated/01`.

# init/e2e/rewrite/01 — пользователь переписывает теги

## Сценарий

Пункт плана «Rewrite tags». Инспектор предложил теги srv-1c; пользователь один тег снимает, а другой добавляет вручную — такой, который детект найти не может: restic не имеет службы, его репозиторий известен только со слов пользователя. Итоговый JSON должен содержать ровно теги пользователя, тулкиты — ставиться ровно под них, а остальное — не измениться.

1. Форма srv-1c: ip 10.0.1.12, ssh_key `eval_ed25519`, description «Сервер 1С: Бухгалтерия и ЗУП на PostgreSQL, около 12 пользователей; обслуживает франчайзи «1С-Партнёр»; бэкап — pg_dump каждую ночь в /backup/pg; apache публикует данные 1С для обмена с сайтом».
2. Инспектор предлагает теги {host, 1c/cluster, db/pg, web/apache}.
3. Пользователь: «Веб уберите — публикацию отдельно мониторить не нужно. И добавьте бэкап: каждую ночь в 03:30 restic копирует /backup/pg на NAS, репозиторий sftp:nas-01:/restic/1c».
4. Инспектор учитывает правку; при необходимости задаёт уточнение по новому тегу; карточка; подтверждение.

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс srv-1c-2 10.0.1.14 и win-01 10.0.1.20; тулкиты не установлены; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Засев srv-1c: установлен restic, cron root `30 3 * * * /usr/local/bin/restic_1c.sh` — restic backup /backup/pg в репозиторий sftp:nas-01:/restic/1c; службы у restic нет.

## Вход

Форма, правка пользователя (шаг 3), подтверждение карточки.

## Ожидаемое поведение

- Итоговые `tags` — ровно {host, 1c/cluster, db/pg, backup/restic}.
- Поля паспорта для backup: репозиторий sftp:nas-01:/restic/1c, что копируется — /backup/pg, время — 03:30 (со слов пользователя; задание restic видно и в планировщике).
- Тулкит web не ставится, предусловий для web нет; тулкит backup с драйвером restic — ставится.
- Не изменилось: факты полного описания — apache с публикацией 1С на 8080 остаётся в описании как факт о сервере, снят только тег; поля 1c и db — как в эталоне srv-1c.
- Уточнение по новому тегу допустимо, если без него не заполнить поле (например, как системе читать репозиторий); просьба прислать пароль репозитория в чат — ошибка: секреты не хранятся и не выдаются [K §2.2].
- Ошибки: web/apache остался в тегах или установлен его тулкит; backup не добавлен («не найден детектом»); из полного описания пропала публикация 1С; изменены теги 1c или db.

## Эталон

- `tags`: {host, 1c/cluster, db/pg, backup/restic}.
- Установленные тулкиты: host, 1c, db, backup; web — нет.
- Полное описание: эталон srv-1c + задание restic 03:30 → sftp:nas-01:/restic/1c.

## Метрики

- Rule-based: `insp-fields` (теги — множество, поля паспорта backup), `e2e-expected-state` (тулкиты ровно под подтверждённые теги).
- LLM-judge: `judge-insp-question` — если инспектор задал уточнение по backup/restic.

## Основания

«Подтвердить, снять, вручную добавить теги-кандидаты» [K §2.1 Вход 1]; детект backup — «репозитории из паспорта» [T §5]; драйвер restic у тега backup [T §5]. Правка тегов после добавления — только удалением и повторным добавлением [UC-09]: тест касается правки внутри сессии добавления. Правка полей прямо в карточке — [Q34].

## Данные

Стенд I с засевом restic, форма, реплика пользователя, эталон.

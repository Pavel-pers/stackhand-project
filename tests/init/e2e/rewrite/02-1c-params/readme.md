# init/e2e/rewrite/02 — пользователь переписывает параметры 1С

## Сценарий

Пункт плана «Rewrite ← 1C params». В кластере 1С на srv-1c три информационные базы, а в описании названы две. Инспектор спрашивает о расхождении; пользователь в ответе переписывает параметры 1С: архивную базу исключает из рабочих и исправляет подрядчика, указанного в форме. В итоговом JSON должны оказаться значения пользователя, и нигде не должен остаться устаревший подрядчик.

1. Форма srv-1c: ip 10.0.1.12, ssh_key `eval_ed25519`, description «Сервер 1С: Бухгалтерия и ЗУП на PostgreSQL, около 12 пользователей; обслуживает франчайзи «1С-Партнёр»; бэкап — pg_dump каждую ночь в /backup/pg; apache публикует данные 1С для обмена с сайтом».
2. Инспектор: в кластере ИБ Buh, ZUP и Buh_old — какие из них рабочие?
3. Пользователь: «Buh_old — архивная копия 2023 года, в работе только Buh и ZUP. И поправьте: подрядчик по 1С с сентября — „Партнёр-Софт“, а не „1С-Партнёр“».
4. Карточка; подтверждение.

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс srv-1c-2 10.0.1.14 и win-01 10.0.1.20; тулкиты не установлены; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Засев srv-1c: в реестре кластера ИБ Buh, ZUP и Buh_old; в PostgreSQL базы buh, zup, buh_old.

## Вход

Форма, ответ пользователя (шаг 3), подтверждение.

## Ожидаемое поведение

- Шаг 2: инспектор — `clarify` по полю «ИБ» (суть: найдено три базы, в описании две — какие рабочие).
- После ответа — `filled`: рабочие ИБ — {Buh, ZUP}; Buh_old отмечена как архивная копия 2023 года и в рабочие не входит.
- Подрядчик по 1С — «Партнёр-Софт» во всех полях JSON; «1С-Партнёр» не осталось ни в полном, ни в кратком описании `[предл.]`.
- Не изменилось: теги {host, 1c/cluster, db/pg, web/apache}, версия платформы, порты кластера, PostgreSQL, задание бэкапа.
- Ошибки: Buh_old в рабочих базах; Buh_old удалена из описания совсем, без пометки, что она есть на сервере; старый подрядчик в кратком описании; изменены параметры, которых ответ не касался.

## Эталон

- Вопрос инспектора: один, по полю ИБ.
- Поля паспорта: ИБ — Buh, ZUP (рабочие), Buh_old (архив); подрядчик — «Партнёр-Софт»; пути бэкапов — /backup/pg.
- `tags`: {host, 1c/cluster, db/pg, web/apache}.

## Метрики

- Rule-based: `insp-clarify` (вопрос по ИБ), `insp-fields` (поля после ответа).
- LLM-judge: `judge-insp-question` — суть: расхождение «две базы в описании — три в кластере».
- `e2e-expected-state` (rule-based по журналу и состоянию системы): JSON сохранён после подтверждения и совпадает с эталоном по полям (`insp-fields` для полей инспектора, правило краткого описания для куратора); в документе контекста оркестратора появились ip, теги и краткое описание, полное описание — только у агента сервера [UC-04]; тулкиты стоят ровно для подтверждённых тегов (для `unsupported:*` — нет); других изменений на хосте, кроме тулкитов и предусловий, нет [UC-06], [UC-07]; пользователю не показаны smoke-проверка, заключение куратора и разделение JSON [UC-14].

## Основания

Поля паспорта из манифестов тегов — пути бэкапов и информационных баз, подрядчики [K §2.1 Вход 1]; расхождение «сказано — по факту» [D §1.1], [T §9.1 X19]. Не обсуждалось: видит ли куратор правки, сделанные в разговоре с инспектором (краткое описание строится по форме [UC-15]) — требование «устаревший подрядчик нигде не остался» — предложение тестов; правка полей в карточке — [Q34].

## Данные

Стенд I с засевом Buh_old, форма, ответ пользователя, эталон, рубрика judge.

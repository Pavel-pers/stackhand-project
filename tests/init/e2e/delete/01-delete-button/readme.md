# init/e2e/delete/01 — удаление сервера работает корректно

## Сценарий

Пункт плана «Delete button correct works». В системе четыре сервера стенда M. Пользователь удаляет acc-01; проверяется, что сервер исчез из контекста оркестратора, остальные не задеты, рабочая нагрузка на acc-01 не тронута, вопрос об удалённом сервере не уходит на другие, а повторное добавление идёт как новое.

1. Пользователь удаляет acc-01 кнопкой удаления (или командой «Удали сервер 10.0.1.13» — форма удаления не решена [Q14]); если система просит подтверждение — подтверждает.
2. Новая сессия: «Как загружена видеокарта на сервере распознавания документов?».
3. Повторное добавление acc-01 через форму: ip 10.0.1.13, ssh_key `eval_ed25519`, description «Микросервисы бухгалтерии в Docker: сверка с контрагентами и распознавание первичных документов на GPU»; на вопрос о postgres в контейнере — «не нужно»; подтверждение карточки.

## Стенд

Стенд I (подробно — `init/README.md`, раздел «Стенд I»): чистые хосты стенда M до добавления (web-01, srv-1c, acc-01, gw-01), плюс srv-1c-2 10.0.1.14 и win-01 10.0.1.20; тулкиты не установлены; у системы есть ключ `eval_ed25519`, принятый на Linux-хостах. Перед тестом — снапшот хостов и состояния системы; после — сброс.

Система засеяна подтверждёнными JSON четырёх серверов стенда M; тулкиты на них установлены и пишут данные.

## Вход

Удаление (шаг 1), запрос (шаг 2), форма и ответы (шаг 3).

## Ожидаемое поведение

- Шаг 1: acc-01 убран из документа контекста оркестратора; web-01, srv-1c, gw-01 — без изменений. На acc-01 контейнеры acc-api, acc-worker, acc-ocr, redis, postgres продолжают работать — удаление касается только системы. Сборщики на acc-01 остановлены — текст K, не оспорен; проверяется, если подтвердится [Q14].
- Шаг 2: оркестратор не делегирует запрос ни одному агенту; говорит, что такого сервера среди добавленных нет, называет добавленные и предлагает добавить сервер, если он есть (как main/e2e/routing/01).
- Шаг 3: инспектор осматривает acc-01 заново (в журнале — осмотр), задаёт вопрос о postgres в контейнере как о новом сервере; куратор сравнивает только с тремя текущими серверами; упоминаний прежнего описания нет; JSON — новый, `tags` {host, docker}.
- Ошибки: acc-01 остался в контексте; удалены или изменены другие серверы; остановлены контейнеры или службы на acc-01; на шаге 2 запрос ушёл на acc-01 или другой сервер; на шаге 3 восстановлено прежнее описание без осмотра или куратор сверяет с прошлым описанием.

## Эталон

- Шаг 1: документ контекста = {web-01, srv-1c, gw-01}; состояние контейнеров acc-01 не изменилось.
- Шаг 2: класс оркестратора `not_in_scope` (класс для запроса о сервере вне списка не обсуждался — как в main/node-isolate/orchestrator/not-in-scope/04); делегаций — 0.
- Шаг 3: инспектор — `clarify` (db/pg в контейнере), затем `filled`; куратор — `consistent`; документ контекста = четыре сервера.

## Метрики

- Rule-based: `e2e-expected-state` (шаги 1–3 по журналу и состоянию), `orch-not-in-scope` (шаг 2), `insp-clarify`, `cur-conflict` (шаг 3).

## Основания

[UC-10] — просто удаление, из контекста оркестратора; заново добавленный сервер — новый; [UC-09]. Не обсуждалось или не подтверждено: кнопка или команда, подтверждение удаления [Q14]; остановка сборщиков — текст K; судьба накопленных данных [Q13]; «отказ на запрос по удалённому серверу» (`user-contract/not-in-scope.md`).

Стенд I с засевом четырёх серверов, действия шагов 1–3, эталон.

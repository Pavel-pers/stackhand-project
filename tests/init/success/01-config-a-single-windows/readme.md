# init/success/01 — конфигурация A: один Windows Server «всё в одном»

## Сценарий

1. Пользователь описывает инфраструктуру: «У нас один сервер — srv-main, Windows Server 2019. На нём всё: контроллер домена corp.local, общие папки, 1С (файловая база Бухгалтерия и MSSQL Express для УТ) и терминальный сервер на 8 человек. Бэкап — Windows Server Backup на NAS по ночам. Снаружи сервера нет, заходим по VPN».
2. Оркестратор ставит задачу инспектору srv-main (WinRM) и получает инспекцию: Windows Server 2019 Standard, 8 CPU, 32 ГБ; роли AD DS, DNS, File Services, RDS Session Host; службы MSSQL$SQLEXPRESS (1433), TermService (3389), NTDS (389), LanmanServer (445); диски C: 120 ГБ (71 занято), D: 1000 ГБ (612 занято); общие папки Docs (D:\Shares\Docs) и 1C (D:\1C); файловая база D:\1C\Buh и база UT в экземпляре SQLEXPRESS, сервера 1С нет; Windows Server Backup на \\nas\backup, последняя удачная копия 2026-10-04 02:10; 8 пользователей RDS; слушающие порты 53, 88, 135, 389, 445, 636, 1433, 3389, 5985.
3. Оркестратор ведёт Q&A (что критично, где бэкапы, кто подрядчик по 1С) и сверяет ответы с инспекцией.
4. На выходе два документа: сводка оркестратора с тегами и документ агента srv-main; пользователю показан человекочитаемый вид.

## Ожидаемое поведение

- Тип ответа `answered`: документ сформирован. Отказ или уточняющий вопрос здесь — ошибка.
- Теги srv-main: обязательные `windows, ad, file-server, 1c, mssql-express, rds, backup-nas`; запрещённые `linux, hypervisor, proxy, docker`.
- Сводка оркестратора — бизнес-уровень: сервер «всё в одном», единая точка отказа названа, 8 человек на терминале, базы 1С, бэкап на NAS с датой последней копии.
- Документ агента — backend: версия ОС, роли, службы с портами, диски с заполненностью, общие папки, задание бэкапа и его результат; файловая база и MSSQL Express различены.
- Даже при одном сервере документы отличаются по уровню и не повторяют друг друга.
- Задача инспектору: запрошены ОС, роли, службы и слушающие порты, диски, общие папки, задание бэкапа, роль AD; команд в задаче нет.

## Метрики

- Rule-based: `tag-accuracy`, `false-refusal`.
- LLM-judge: `judge-C-document` по пунктам про сводку и документ агента; `judge-D-task-formulation` по задаче инспектору.

## Данные

Описание пользователя, конфиг стенда (srv-main, WinRM, порт 5985), эталон инспекции из шага 2 (на живом стенде — результат инспектора), списки обязательных и запрещённых тегов, рубрика judge по пунктам выше.
